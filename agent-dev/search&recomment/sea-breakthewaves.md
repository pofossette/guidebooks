下面用**字符流程图**把 Sea-BreakTheWaves 的运行链路和功能实现方式拆开讲。它整体可以理解为一个 **“内容入库 + 智能检索 + 个性化推荐 + 用户记忆 + 可观测运维”** 的生成式推荐系统后端。项目 README 明确说明，它基于 Go 构建，面向内容理解、候选召回、智能决策、用户记忆和可观测链路的一体化推荐服务。([GitHub][1])

# 2. 内容入库链路：文章 / 文档如何进入系统

内容入库是整个推荐和搜索能力的基础。它负责把原始内容变成可以检索、推荐、重排的数据资产。

```text
外部内容 / 文档 / 文章
          │
          ▼
┌────────────────────┐
│ POST /api/v1/docs/ingest │
│      文档入库接口        │
└─────────┬──────────┘
          │
          ▼
┌────────────────────┐
│   doc_ingest Skill  │
│   入库技能模块       │
└─────────┬──────────┘
          │
          ▼
┌────────────────────┐
│      Chunk 切分      │
│  长文本切成小片段     │
└─────────┬──────────┘
          │
          ▼
┌────────────────────┐
│  Embedding 生成      │
│  Qwen / DashScope   │
└─────────┬──────────┘
          │
          ├──────────────────────┐
          │                      │
          ▼                      ▼
┌────────────────────┐   ┌────────────────────┐
│   Milvus 向量库      │   │  Postgres 元数据    │
│  存 chunk 向量       │   │  存文章/片段信息     │
└────────────────────┘   └────────────────────┘
          │
          ▼
┌────────────────────┐
│ Neo4j，可选          │
│ 图谱关系 / GraphRAG  │
└────────────────────┘
```

实现方式上，README 明确说文档入库支持文本切分、Embedding 生成、写入 Milvus 向量库、写入 Postgres 元数据存储，并可选写入 Neo4j 用于 GraphRAG / 图谱检索增强；对应接口是 `POST /api/v1/docs/ingest`。([GitHub][1])

这条链路的核心作用是：

```text
原始内容
  → 可检索 chunk
  → 可向量召回内容
  → 可用于推荐候选池
  → 可用于搜索结果返回
  → 可用于 GraphRAG 扩展
```

# 3. 推荐链路：用户请求如何生成推荐结果

推荐链路由 `RecoAgent` 统筹，它不是简单地“查数据库返回文章”，而是会综合用户请求、意图、策略、记忆、候选池和 rerank。

```text
用户打开首页 / 请求推荐
          │
          ▼
┌──────────────────────────┐
│ POST /api/v1/reco/recommend │
│        推荐接口              │
└────────────┬─────────────┘
             │
             ▼
┌──────────────────────────┐
│        RecoAgent          │
│ 推荐流程总调度             │
└────────────┬─────────────┘
             │
             ▼
┌──────────────────────────┐
│  1. 用户请求解析            │
│  解析 user_id、场景、数量等 │
└────────────┬─────────────┘
             │
             ▼
┌──────────────────────────┐
│  2. 意图识别 intent.parse  │
│  判断用户当前想看什么       │
└────────────┬─────────────┘
             │
             ▼
┌──────────────────────────┐
│  3. 策略路由 policy.route │
│  选择推荐策略 / 场景策略    │
└────────────┬─────────────┘
             │
             ▼
┌──────────────────────────┐
│  4. 读取用户记忆与历史      │
│  长期偏好 / 短期兴趣 / 曝光 │
└────────────┬─────────────┘
             │
             ▼
┌──────────────────────────┐
│  5. 候选池补充与召回        │
│  pool_manage + milvus_search │
└────────────┬─────────────┘
             │
             ▼
┌──────────────────────────┐
│  6. LLM / Rerank 精排      │
│  语义排序 / 个性化排序      │
└────────────┬─────────────┘
             │
             ▼
┌──────────────────────────┐
│  7. 结果校验与过滤          │
│  去重 / 过滤已看 / 过滤不喜欢 │
└────────────┬─────────────┘
             │
             ▼
┌──────────────────────────┐
│  8. 返回推荐结果            │
│  文章 / 标题 / 标签 / 理由   │
└────────────┬─────────────┘
             │
             ▼
┌──────────────────────────┐
│  9. 曝光与副作用处理        │
│  写历史 / 更新候选池 / 记日志 │
└──────────────────────────┘
```

README 对推荐主流程的描述包括：用户请求解析、意图识别、推荐策略路由、用户记忆与行为上下文读取、候选池补充与召回、LLM / rerank 精排、结果校验与输出、曝光 / 副作用处理；对应接口是 `POST /api/v1/reco/recommend`。([GitHub][1])

可以把推荐实现方式概括为：

```text
用户上下文
  + 用户记忆
  + 历史行为
  + 候选池
  + 向量召回
  + LLM / Rerank
  = 个性化推荐结果
```

# 4. 内容搜索链路：用户搜索时如何返回结果

搜索链路由 `ContentSearchAgent` 负责，和推荐链路不同，它更偏“用户主动搜索”，不强依赖用户记忆。

```text
用户输入搜索 query
          │
          ▼
┌────────────────────┐
│ POST /api/v1/search │
│    搜索接口          │
└─────────┬──────────┘
          │
          ▼
┌────────────────────────┐
│   ContentSearchAgent    │
│   内容搜索 Agent         │
└─────────┬──────────────┘
          │
          ▼
┌────────────────────────┐
│  1. Query 意图分析       │
│  判断用户搜索目的         │
└─────────┬──────────────┘
          │
          ▼
┌────────────────────────┐
│  2. Query Embedding     │
│  将搜索词转为向量         │
└─────────┬──────────────┘
          │
          ▼
┌────────────────────────┐
│  3. Milvus 向量召回      │
│  找相似 chunk / 文章      │
└─────────┬──────────────┘
          │
          ▼
┌────────────────────────┐
│  4. Rerank 精排          │
│  Qwen Rerank / 模型重排  │
└─────────┬──────────────┘
          │
          ▼
┌────────────────────────┐
│  5. 组装结构化结果        │
│  文章、片段、标题、标签等  │
└─────────┬──────────────┘
          │
          ▼
       返回搜索结果
```

README 明确说内容搜索 Agent 的流程是“问题 → 检索意图 → 向量召回 → rerank → 返回内容结果”，并且具备 query 意图分析、embedding 召回、rerank 精排、返回文章 / 片段 / 标题 / 标签等结构化结果的能力。([GitHub][1])

搜索和推荐的区别可以这样看：

```text
推荐：
用户未必主动输入明确 query
系统根据用户状态主动分发内容

搜索：
用户输入明确 query
系统围绕 query 找最相关内容
```

# 5. Skill Registry：功能模块如何被组织和调用

Sea-BreakTheWaves 的一个核心设计是“技能化架构”。Agent 不直接把所有逻辑写死，而是通过 Skill Registry 调用不同能力。

```text
RecoAgent / ContentSearchAgent
          │
          ▼
┌────────────────────────┐
│     Skill Registry      │
│  注册、发现、调用 Skill   │
└─────────┬──────────────┘
          │
          ├─────────────────────────────┐
          │                             │
          ▼                             ▼
┌────────────────┐             ┌────────────────┐
│  doc_ingest     │             │ milvus_search  │
│  文档入库        │             │ 向量搜索         │
└────────────────┘             └────────────────┘

┌────────────────┐             ┌────────────────┐
│  pool_manage    │             │ user_history   │
│  候选池管理      │             │ 用户历史管理      │
└────────────────┘             └────────────────┘

┌────────────────┐             ┌────────────────┐
│ memory_manage   │             │    rerank      │
│ 用户记忆读写     │             │ 重排序能力       │
└────────────────┘             └────────────────┘
```

README 中列出的核心 skills 包括 `doc_ingest`、`milvus_search`、`pool_manage`、`user_history`、`memory_manage` 和 `rerank`，并说明这种结构的好处是能力边界清晰、易扩展替换、方便 Agent 编排调用，适合演进为更复杂的多工具推荐系统。([GitHub][1])

换句话说，它的功能实现不是“大函数一路写到底”，而更像：

```text
Agent 负责决策和编排
Skill 负责具体能力
Storage / Infra 负责数据落地
Observability 负责监控和排错
```

# 6. 用户记忆链路：系统如何理解用户偏好

用户记忆是个性化推荐的关键。项目把用户状态拆成长期、短期、周期和历史行为四层。

```text
用户行为
点击 / 浏览 / 点赞 / 不喜欢 / 搜索 / 问卷
          │
          ▼
┌────────────────────────┐
│    user_history Skill   │
│    记录用户行为历史       │
└─────────┬──────────────┘
          │
          ▼
┌────────────────────────┐
│   memory_manage Skill   │
│   更新用户记忆            │
└─────────┬──────────────┘
          │
          ├──────────────────────────┐
          │                          │
          ▼                          ▼
┌────────────────┐           ┌────────────────┐
│ 长期记忆         │           │ 短期记忆         │
│ 稳定偏好         │           │ 最近兴趣         │
└────────────────┘           └────────────────┘

┌────────────────┐           ┌────────────────┐
│ 周期记忆         │           │ 用户历史         │
│ 时间桶偏好       │           │ 曝光/交互轨迹    │
└────────────────┘           └────────────────┘
          │
          ▼
┌────────────────────────┐
│ Memory Chunk + 向量召回 │
│ 只取相关记忆片段进上下文 │
└────────────────────────┘
```

README 说明，项目将用户状态建模为长期记忆、短期记忆、周期记忆和用户历史，并会把记忆拆成 Memory Chunks，支持基于向量检索召回相关片段，避免把整段记忆直接塞进 Prompt，以提升效率和质量。([GitHub][1])

这条链路解决的是推荐系统里的核心问题：

```text
不是每次推荐都从零开始
而是让系统持续知道：
用户长期喜欢什么
最近关注什么
周期性会看什么
已经看过/不喜欢什么
```

# 7. 候选池与异步补池：推荐结果从哪里来

候选池机制让推荐链路更接近真实业务系统。系统不会每次都从全量内容重新计算，而是维护可消费的候选集合。

```text
用户请求推荐
          │
          ▼
┌────────────────────────┐
│  检查用户候选池          │
│  是否足够 min_size       │
└─────────┬──────────────┘
          │
      ┌───┴─────────────┐
      │                 │
      ▼                 ▼
候选足够            候选不足
      │                 │
      │                 ▼
      │       ┌────────────────────┐
      │       │ 异步补池 poolrefill │
      │       │ 召回更多候选内容     │
      │       └─────────┬──────────┘
      │                 │
      │                 ▼
      │       ┌────────────────────┐
      │       │ Milvus / 策略召回    │
      │       │ 过滤不喜欢 / 已曝光  │
      │       └─────────┬──────────┘
      │                 │
      │                 ▼
      │        写入候选池
      │
      ▼
┌────────────────────────┐
│ 从候选池取 take_size 条 │
└─────────┬──────────────┘
          ▼
┌────────────────────────┐
│ Rerank / LLM 精排       │
└─────────┬──────────────┘
          ▼
┌────────────────────────┐
│ 推荐后 remove / 曝光记录 │
└────────────────────────┘
```

README 的项目结构中单独列出 `poolrefill`，说明它负责推荐候选池的异步填充机制；同时核心 skills 中也有 `pool_manage`，用于候选池维护。([GitHub][1])

候选池的实现思路可以概括为：

```text
先准备一批可能感兴趣的内容
推荐时快速取出
再用模型重排
推荐后记录曝光并更新池子
```

这比“每次请求全链路实时计算”更适合实际服务，因为它能降低延迟、提升吞吐，并支持异步补充候选。

# 10. 可观测链路：如何定位推荐系统问题

项目接入了日志、指标、链路追踪和可视化。

```text
一次推荐请求
      │
      ▼
┌────────────────────┐
│ Gin Middleware      │
│ 生成 trace_id        │
└─────────┬──────────┘
          │
          ▼
┌────────────────────┐
│ RecoAgent 调用链路   │
│ intent / policy / skill │
└─────────┬──────────┘
          │
          ▼
┌────────────────────┐
│ Skill 调用耗时记录   │
│ Milvus / Postgres / LLM │
└─────────┬──────────┘
          │
          ├──────────────────┐
          │                  │
          ▼                  ▼
┌────────────────┐   ┌────────────────┐
│ Prometheus 指标 │   │ Jaeger Trace    │
│ QPS / latency  │   │ 链路耗时         │
└────────────────┘   └────────────────┘
          │
          ▼
┌────────────────────┐
│ Grafana 看板         │
│ 服务状态 / 性能趋势   │
└────────────────────┘
```

README 中说明项目内置 Zap + Lumberjack 日志、Prometheus 指标、OpenTelemetry + Jaeger 链路追踪，以及 Grafana 可视化；默认暴露 `/metrics` 和 `/health`，可用于推荐链路耗时分析、Agent 调用质量观察、异常排查、健康检查和容量评估。([GitHub][1])

这对 Agent 推荐系统非常关键，因为推荐结果不好时，问题可能出在：

```text
意图识别错了
候选池不足
向量召回质量差
rerank 失效
用户记忆污染
数据库慢
LLM 调用超时
异步补池失败
```

有 trace、metrics 和日志后，才能逐层定位。

```text
                         ┌────────────────────┐
                         │    Client / App     │
                         └─────────┬──────────┘
                                   │
                                   ▼
                         ┌────────────────────┐
                         │   Gin HTTP Server   │
                         └─────────┬──────────┘
                                   │
        ┌──────────────────────────┼──────────────────────────┐
        │                          │                          │
        ▼                          ▼                          ▼
┌────────────────┐        ┌────────────────┐        ┌────────────────┐
│ 文档入库链路     │        │ 推荐链路         │        │ 搜索链路         │
│ docs/ingest     │        │ reco/recommend  │        │ search          │
└───────┬────────┘        └───────┬────────┘        └───────┬────────┘
```

# 12. 功能实现方式总结

从工程实现角度，它的核心不是某一个算法，而是几类模块协同：

```text
1. Gin 路由层
   负责暴露 HTTP API：
   docs/ingest、reco/recommend、search、questionnaire、metrics、health

2. Agent 层
   RecoAgent 负责推荐决策
   ContentSearchAgent 负责内容搜索

3. Skill 层
   doc_ingest、milvus_search、pool_manage、user_history、memory_manage、rerank

4. 存储层
   Postgres 存元数据、用户历史、记忆等结构化数据
   Milvus 存向量，用于语义召回
   Neo4j 可选，用于 GraphRAG 和关系检索
   Redis 可用于缓存
   Kafka 用于异步消息流

5. 模型层
   Embedding 用于内容和 query 向量化
   Rerank 用于精排
   LLM 用于意图理解、策略判断和生成式推荐增强

6. 可观测层
   Prometheus 看指标
   Jaeger 看链路
   Grafana 做可视化
   日志用于排错
```

README 的项目结构也与这个分层对应：`agent` 放推荐和搜索 Agent，`chunk` 放文档切分，`embedding` 放向量 schema 与 embedding 服务，`infra` 放 Postgres / Milvus / Neo4j / OTel 初始化，`kafka` 放消费与重试，`metrics` 放 Prometheus 指标，`middleware` 放 Trace 和错误处理中间件，`poolrefill` 放异步补池，`service` 放精排 / 问卷 / 搜索等核心服务，`skills` 和 `skillsys` 分别放技能实现与注册调用框架。([GitHub][1])

# 13. 最简版运行链路记忆图

最后可以用这张最简图记住它：

```text
内容进来
  │
  ▼
切分 → 向量化 → Milvus / Postgres / Neo4j
  │
  ▼
形成可检索内容资产
  │
  ├──────────────► 搜索：Query → 向量召回 → Rerank → 返回结果
  │
  └──────────────► 推荐：用户记忆 + 候选池 + 召回 → Rerank / LLM → 返回推荐
                                      │
                                      ▼
                              曝光 / 点击 / 反馈
                                      │
                                      ▼
                              更新历史与记忆
                                      │
                                      ▼
                              下一次推荐更个性化
```

所以，这个项目的运行逻辑可以概括成一句话：

> **先把内容结构化、向量化、可检索化；再通过 Agent + Skill 编排，把用户记忆、候选池、向量召回和模型精排组合起来，完成推荐与搜索；最后用日志、指标和 Trace 保证链路可观测、可调试、可持续演进。**
