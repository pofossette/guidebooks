# Archlinux Missionary：现状与目标差异清单

## 文档目的

这份清单只做一件事：把“源码真实现状”和“文档里的目标设计”分开。

在这个项目里，最容易导致误判的不是单个代码文件，而是：

- README / 架构文档说得更远
- 源码实现先把最小闭环跑通
- 两者还没有完全同步

因此，下面所有条目都按“文档怎么说 / 代码怎么做 / 应该如何理解”来写。

## 2. 明确存在漂移的部分

| 主题 | 文档里怎么写 | 当前代码怎么做 | 应如何理解 |
| --- | --- | --- | --- |
| CLI 交互库 | `docs/architecture.md` 写 `readline/promises + @inquirer/prompts` | `apps/cli/user-io/terminal-user-io.ts` 只使用 `node:readline/promises` | 当前实现以原生 readline 为准，`@inquirer/prompts` 仍是目标设计 |
| DeepSeek provider | README 写 DeepSeek 底层使用 `@ai-sdk/deepseek` | `packages/adapters/llm/deepseek-provider.adapter.ts` 实际使用 `@ai-sdk/openai-compatible` | 当前策略是“走 OpenAI-compatible 兼容层”，不是“单独的 DeepSeek SDK” |
| 存储层 | README / 架构文档写 `SQLite + Drizzle ORM` | `WorkspaceStorageAdapter` 与 retrieval index 都动态导入 `bun:sqlite`，schema/migration 是手写 SQL | 当前存储是真正的 Bun SQLite + SQL；Drizzle 还未落地 |
| 日志 | 文档表格列出 `Pino` | manifests 中无 Pino，源码中也没有稳定 logger 接入 | Pino 应视为目标设计，而非现状 |
| Bash AST 解析 | 文档写 `tree-sitter + tree-sitter-bash` | manifests 无 direct dependency，业务代码无相关 import；策略文档也写“AST 细化仍待补” | 当前只有最小命令分析和审批边界，tree-sitter 未落地 |
| 队列与并发库 | 文档写 `p-queue + p-limit` | manifests 无 direct dependency；`p-limit` 只作为别的包的 transitive dependency 出现 | 这是目标设计，不是现有业务实现 |
| 适配器层可见性 | 部分元文档对包地图描述不完整 | `packages/adapters` 在现状里是核心包，并由 `apps/cli/bootstrap.ts` 直接装配 | 阅读仓库时必须把 `adapters` 当成一等公民 |

## 3. 源码本身还存在的工程不一致

这些问题不属于“文档夸大”，而是仓库内部仍需整理的点。

### 3.1 `packages/testing` 的 `zod` 版本漂移

- `packages/testing/package.json` 声明的是 `zod@^3.23.0`
- 但测试包源码也在 `import { z } from "zod"`
- 其余主线包普遍依赖 `zod@^4.1.5`

建议理解：

- 这不是有意的双栈策略
- 更像未清理的依赖遗留

### 3.2 文档和实现的成熟度标签不完全同步

源仓库的设计/约束文档已经很丰富，但它们的成熟度信息主要散落在：

- `docs/design/README.md`
- `docs/strategy/*`
- `CLAUDE.md`

问题在于：

- 首次读 README 的读者，不一定会继续读这些状态文档
- 所以容易把“规划中/进行中”误认为“已实现”

## 4. 对后续读者最安全的理解方式

如果你后续继续读这个项目，建议遵循下面的优先级：

1. **运行时现状**
   以 `apps/cli/bootstrap.ts`、`apps/cli/main.ts`、各包 `package.json`、实际 import 为准。
2. **目标设计**
   以 `docs/architecture.md`、`docs/constraints/*`、`docs/design/*` 为准。
3. **两者冲突时**
   先把设计文档理解成“目标状态”，除非源码已经明确落地。

换句话说：

- `bootstrap.ts` 回答“现在怎么跑”
- `docs/architecture.md` 回答“长期想怎么稳定下来”

## 5. 优先建议修正的地方

如果要降低后续维护成本，优先建议做这几件事：

1. 在源仓库 README 和 `docs/architecture.md` 的技术选型表里增加状态标记
2. 把 `DeepSeek -> @ai-sdk/deepseek` 的表述改成当前真实实现
3. 把 `@inquirer/prompts`、Pino、tree-sitter、Drizzle、`p-queue/p-limit` 明确改成“目标设计/待落地”
4. 处理 `packages/testing` 的 `zod` 版本不一致
5. 在所有高层包地图里把 `packages/adapters` 标成现状核心包

## 6. 结论

这个项目最大的阅读门槛，不是代码太难，而是“设计意图比现状更完整”。

只要先接受下面这句话，理解就会顺很多：

> 当前仓库已经有稳定的 CLI 主闭环和明确的层次边界；但部分架构文档描述的是更远的目标，而不是今天已经全部实现的事实。
