# Archlinux Missionary：技术选型

## 文档口径

这份文档不是简单抄 `package.json`，也不是简单复述 `docs/architecture.md`。它同时回答两个问题：

1. 当前源码真正落地了哪些技术
2. 架构文档里还保留了哪些目标设计

状态说明：

- `已实现`：可以从源码 import、运行入口或 package manifests 直接确认
- `进行中`：已经有部分实现，但还不是完整能力
- `目标设计`：主要存在于设计/架构文档，还不是当前代码事实

## 1. 选型原则

从当前仓库能看出的选型倾向很明确：

1. **先把边界做对，再补深度能力**
   所以优先出现的是 `ports / adapters / domain / application` 的分层，而不是大而全框架。
2. **优先选小而硬的基础件**
   比如 `yargs`、`zod`、`yaml`、`semver`、`minimatch`，都是职责非常清楚的底层库。
3. **多 provider，但不做 provider 绑死**
   所以用了 `ai` + provider adapter，而不是把业务层直接写死到某一家 SDK。
4. **当前以工程可控性优先**
   所以先落地的是 `Biome`、`Vitest`、`knip`、`husky`、`lint-staged` 这类工程工具。

## 3. 核心选型结论

### 3.1 Bun + pnpm + TypeScript 是“运行时和工程管理分离”的组合

当前仓库没有选择“Node 运行时 + npm scripts 一把梭”，而是分成两层：

- Bun 负责运行和 `bun:sqlite`
- pnpm 负责 monorepo 依赖管理和 workspace 一致性
- TypeScript 负责全局类型边界

这样做的好处：

- Bun 让 CLI 入口和 SQLite 访问都更直接
- pnpm 对 workspace 包和锁文件管理更强
- TypeScript `paths` 让扁平 monorepo 包边界更清晰

不选常见替代的原因：

- 不选纯 Node 运行时：会失去当前已经在用的 `bun:sqlite` 与 Bun 运行路径
- 不选 npm / Yarn classic：对 workspace 约束和一致性不如 pnpm 明确
- 不引入 Nx / Turborepo：当前仓库规模还没大到需要重型任务编排器

### 3.2 CLI 选择 yargs，而不是更轻的 Commander 或更重的框架

当前 CLI 命令树已经较长，包含嵌套子命令、参数和多条支持命令。`yargs` 的价值在于：

- 层级子命令表达强
- 帮助信息、参数声明和 handler 组织成熟
- 对这种“命令很多但没有 GUI”的项目很合适

不选其他常见方案：

- 不选 `commander`：能做，但在深子命令和复杂参数组织上没有现在这套 `yargs` 树直接
- 不选 oclif / Nest Commander 之类更重方案：会引入额外框架结构，不符合这个仓库当前“扁平 package + 明确边界”的风格

### 3.3 交互层先用 Node 原生 readline，而不是直接上富交互库

现状代码里，`TerminalUserIO` 基于 `readline/promises` 自行控制 live status、审批问答、sudo notice、转录状态。这说明当前优先级是“可控”和“边界清晰”，不是“组件现成”。

为什么这样合理：

- 原生 API 足够完成当前问答、审批、状态流式输出
- 不会过早绑定到某个 prompt UI 框架
- 更适合和 runtime event sink 做低层整合

为什么现在不把 `@inquirer/prompts` 当成现状：

- 当前仓库没有 direct dependency
- 当前交互代码没有对应 import
- 所以它应该写成目标设计，而不是已实现能力

### 3.4 LLM 侧选择“AI SDK + provider adapter”而不是“每家 SDK 各写一套业务逻辑”

当前最重要的选型不是某一个 provider，而是 `ai` 作为统一抽象层：

- provider 统一挂到 `ProviderRegistry` / `ProviderGateway`
- 业务层拿到的是统一的 model selection / generateText 能力
- runtime 已经接上 `ToolLoopAgent`

这套选型的优势：

- 多 provider 支持不会污染业务层
- 可以保留 provider 差异，但不让上层到处写 if/else
- 更贴近这个项目的“多 agent + tool calling”需求

为什么不选常见替代：

- 不选 LangChain / LlamaIndex：当前项目更需要稳定边界和最小抽象，不需要额外 agent 框架
- 不直接把业务写到 OpenAI SDK / 智谱 SDK：会让 provider 切换和测试都变重

### 3.5 OpenAI-compatible 适配器是一个关键的复用决策

当前源码没有使用 `@ai-sdk/deepseek`。DeepSeek 和 LMStudio 都走 `@ai-sdk/openai-compatible`，OpenAI 在 base URL 不是官方域名时也能切过去。

这个决策的好处：

- 统一处理“OpenAI 兼容协议”的 provider
- 减少每家 provider 独立适配代码
- 对自托管 / 网关代理更友好

所以这里真正的选型不是“有没有 DeepSeek 支持”，而是“DeepSeek 支持以兼容层方式落地”。

### 3.6 Zod-first 是当前代码库最稳定的基础约束

`zod` 基本贯穿了：

- shared DTO
- config schema
- agent / prompt / tool contracts
- domain state / events
- application 输入输出边界

这说明仓库明确偏向“运行时验证 + 类型推导一体化”。

为什么选 `zod`：

- TS 推导体验成熟
- 适合做 boundary schema
- 项目里已经形成统一写法

为什么不选同类：

- 不选 `io-ts`：学习和使用成本更高，函数式风格更重
- 不选 `typebox`：更偏 JSON Schema 工作流，而当前仓库大量是本地 TS 契约
- 不选 `valibot`：也可行，但当前仓库已经全局采用 Zod，没有迁移动机

### 3.7 当前存储是真正的 Bun SQLite，不是文档里那个“SQLite + Drizzle”

这点很重要。当前代码事实是：

- `WorkspaceStorageAdapter` 动态导入 `bun:sqlite`
- schema 初始化和 migration 用手写 SQL
- retrieval index 也直接使用 SQLite / FTS5

这套做法的优势：

- 对当前仓库足够直接
- 没有引入 ORM 抽象成本
- 更容易快速迭代 schema 和存储路径迁移

为什么现在不把 Drizzle 写成现状：

- manifests 没有 direct dependency
- adapters 没有 Drizzle import
- schema 和 migration 都是 SQL 字符串

因此，Drizzle 应归类为目标设计，不是当前实现。

### 3.8 测试和工程工具链偏向“少工具，但每个工具都硬”

当前组合是：

- `Vitest`：测试
- `coverage-v8`：覆盖率
- `Biome`：格式化 + lint
- `knip`：死依赖/死导出检查
- `husky` + `lint-staged`：提交前门禁
- `commitlint`：commit message 规范
- `manypkg`：workspace 一致性

这套组合的共同特点是：

- 配置比 `ESLint + Prettier + Jest + 各类插件` 更轻
- 更适合 ESM + Bun + TS 的仓库
- 能在不引入重型平台的情况下，把代码质量门槛抬起来

## 4. 当前明确存在的漂移和技术债

以下内容在写技术文档时必须单列，不可混写为“既成事实”：

1. `docs/architecture.md` 写了 `@inquirer/prompts`，但当前交互代码只使用 `readline/promises`
2. `README.md` 写了 DeepSeek 底层用 `@ai-sdk/deepseek`，但当前代码实际使用 `@ai-sdk/openai-compatible`
3. `README.md` / `docs/architecture.md` 写了 `SQLite + Drizzle ORM`，但当前代码是 `bun:sqlite` + 手写 SQL
4. 文档写了 `Pino`，但当前没有实际 logger 依赖和接入
5. 文档写了 `tree-sitter` / `tree-sitter-bash`，但当前 direct dependency 和 import 都未落地
6. 文档写了 `p-queue` / `p-limit`，但当前业务代码没有 direct dependency
7. `packages/testing` 单独声明了 `zod@3`，和全仓库 `zod@4` 主线不一致

更细的证据和解读，见 [现状与目标差异清单.md](现状与目标差异清单.md)。

## 5. 结论

如果只用一句话概括当前技术选型：

> 这是一个以 Bun + TypeScript + pnpm workspace 为基础、以 AI SDK + provider adapter 为模型层、以 Zod 为契约层、以 Bun SQLite 为当前存储层、以 Vitest/Biome/Knip 为工程门禁的终端优先多 agent 系统。

它的特点不是“技术新奇”，而是：

- 边界明确
- 依赖克制
- 当前实现和未来设计有清楚分层

逐个包的理由和替代方案，见 [包说明与选型附录.md](包说明与选型附录.md)。
