# Archlinux Missionary：文档导航与后续思考

## 1. 这组文档怎么读

建议顺序：

1. [快速了解.md](快速了解.md)
   先建立对系统职责、命令面、分层和主链路的整体认识。
2. [技术选型.md](技术选型.md)
   再看高层技术栈、当前已实现能力和目标设计的差异。
3. [包选型附录.md](包选型附录.md)
   最后逐项看每个内部包、每个第三方包为什么存在。
4. [现状与目标差异清单.md](现状与目标差异清单.md)
   如果你准备继续改代码或继续补文档，这份差异清单最值得先读。

## 2. 当前最值得继续跟踪的问题

### 2.1 文档与实现漂移是否要在源仓库同步修正

目前 `guidebooks` 里的说明已经把“现状”和“目标设计”拆开了，但源仓库自身的 `README.md` / `docs/architecture.md` 仍然会让首次读者误以为以下能力已经稳定落地：

- Drizzle ORM
- `@inquirer/prompts`
- Pino
- tree-sitter 命令分析
- `p-queue` / `p-limit`

如果后续继续维护这个项目，建议直接在源仓库文档里同步加状态标记。

### 2.2 `packages/testing` 的依赖一致性需要处理

当前大多数包都在使用 `zod@4`，但 `packages/testing/package.json` 仍然声明了 `zod@3`。这更像历史遗留或未清理，而不是有意做出的双版本策略。

### 2.3 存储层到底要不要继续往 Drizzle 收敛

现状的 `bun:sqlite + 手写 SQL` 很直接，也和当前仓库规模匹配；但设计文档长期写的是 `SQLite + Drizzle ORM`。这意味着项目后续至少要做一个决策：

- 要么把设计文档下修到当前事实
- 要么继续把代码往 Drizzle 靠拢

### 2.4 命令分析路线是否继续投入 tree-sitter

当前仓库已经有最小命令分析和审批边界，系统是能跑的。是否继续引入 tree-sitter，本质上是一个“复杂度换精度”的问题，而不是基础能力是否存在的问题。

### 2.5 是否真的需要 richer prompt/skill/provider 体系

源码里已经有 `prompts`、`skills`、`provider gateway`、`workflow` 这些扩展位，但不少能力还在“设计先行、实现跟进”的状态。后续应优先回答：

- 哪些扩展位是 MVP 后必须落地的
- 哪些只是设计储备，不值得短期继续扩张

## 3. 这份资料的使用建议

### 3.1 如果你是新接手项目的人

先不要被所有设计文档吓住。先以 `apps/cli/main.ts`、`apps/cli/bootstrap.ts` 和 `packages/application` 为准理解现状，再回头看目标设计。

### 3.2 如果你是要补功能的人

先看 [现状与目标差异清单.md](现状与目标差异清单.md)。很多功能讨论如果不先区分“当前事实”和“设计目标”，很容易做出错误判断。

### 3.3 如果你是要做架构清理的人

优先处理这三类问题：

1. 文档口径不一致
2. 依赖版本漂移
3. 设计文档承诺过多但实现尚未跟上
