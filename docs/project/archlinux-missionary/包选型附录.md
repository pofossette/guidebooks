# Archlinux Missionary：包选型附录

## 文档目标

这份附录专门回答“为什么要这样拆包”和“为什么用这个库、不用同类别的库”。

内容分三部分：

1. workspace 内部包
2. 第三方运行时依赖
3. 开发与质量工具链

## 1. workspace 内部包逐项说明

| 包 | 当前职责 | 为什么单独成包 | 为什么不放到别处 | 当前状态 |
| --- | --- | --- | --- | --- |
| `@archlinux-missionary/cli` | 命令解析、REPL、presenter、终端输入输出、组合根 | 用户界面和组合根天然应该隔离，便于后续替换展示层 | 不放到 `application`，因为 `yargs`、`readline`、终端文案不应污染用例层 | 已实现 |
| `@archlinux-missionary/application` | 会话运行时、审批编排、工作流引擎、检索同步、读模型、skill runtime 等 use case | 这是业务流程编排层，负责把 domain 和 ports 串起来 | 不放到 `domain`，因为它需要副作用和 port；不放到 `cli`，因为它必须可被不同入口复用 | 已实现 |
| `@archlinux-missionary/domain` | 纯状态、事件、reducer、权限策略、命令分析、systemd/unit、user profile 规则 | 纯业务规则需要稳定、可测试、可脱离外部环境运行 | 不放到 `application`，否则状态迁移和基础设施编排会糊在一起 | 已实现 |
| `@archlinux-missionary/ports` | provider、shell、repositories、prompt registry、runtime events、user io 等接口契约 | 先定义边界，再选技术实现，是这个项目最重要的架构约束之一 | 不把接口写在 adapter 边上，否则依赖会倒向具体实现 | 已实现 |
| `@archlinux-missionary/adapters` | LLM provider、shell、storage 的具体实现 | 基础设施天然需要集中，不应散落在业务包中 | 不放到 `application`，否则 provider / SQLite / child_process 会直接侵入用例层 | 已实现 |
| `@archlinux-missionary/tools` | model-visible 工具定义、schema、registry、retrieval 工具 | “工具”比“shell 执行器”更高一层，既有权限元数据，也有 agent 可见 contract | 不放到 `adapters/shell`，因为工具不只是 shell；不放到 `application`，因为工具不是具体用例 | 已实现 |
| `@archlinux-missionary/prompts` | 系统 prompt、fragment、registry | prompt 是资产，不应散落在 service 里 | 不放到 `application`，否则 prompt 文本和编排逻辑会耦合；不放到 `agents`，因为角色定义不等于 prompt 内容 | 已实现 |
| `@archlinux-missionary/agents` | agent profile、schema、contract、registry | 角色定义是运行时约束的一部分，应该独立于 prompt 文本和业务流程 | 不放到 `prompts`，避免“角色 = 提示词”混淆；不放到 `application`，避免 profile 跟用例层绑死 | 已实现 |
| `@archlinux-missionary/config` | 配置 schema、环境变量读取、文件配置、XDG/项目路径推导 | 配置读取不只 CLI 用到，bootstrap、脚本和未来其他入口都可能复用 | 不放到 `cli`，否则配置层和命令层耦合；不放到 `shared`，因为它不是纯类型/工具 | 已实现 |
| `@archlinux-missionary/shared` | DTO、ID、provider 公共类型、时间相关基础件 | 这些内容跨多个层使用，但又不属于某个具体领域 | 不放到 `domain`，因为并非所有共享类型都是业务领域概念；不放到 `ports`，因为它们不是接口 | 已实现 |
| `@archlinux-missionary/skills` | skill 发现、manifest、trust、冲突检测、装载辅助 | skills 是一种扩展机制，不等同于 core tools 或 prompts | 不放到 `tools`，因为 skill 是打包后的扩展单元，不只是一个工具定义 | 进行中 |
| `@archlinux-missionary/workflows` | workflow definition、retry policy、workflow error | 工作流基础件比具体 application use case 更抽象，适合作为独立复用点 | 不放到 `application`，否则通用工作流基础件会和具体业务用例混住 | 已实现，但内容仍偏基础 |
| `@archlinux-missionary/testing` | eval pipelines 与测试辅助占位 | 测试基建以后可以沉淀为独立公共面，先预留包边界是合理的 | 不继续散落在 `application` 或 `domain`，否则测试资产难复用 | 进行中，当前仍偏占位 |

## 2. 第三方运行时依赖逐项说明

### 2.1 CLI、配置和基础解析

| 包 | 当前使用点 | 为什么选择它 | 为什么不选同类方案 |
| --- | --- | --- | --- |
| `dotenv` `17.3.1` | `apps/cli/main.ts`、`scripts/run-agent-evals.ts` 直接 `import "dotenv/config"` | 零侵入加载 `.env`，适合 CLI 和脚本入口 | 不手写环境变量加载器，避免重复处理 `.env`、转义和初始化顺序 |
| `yargs` `18.0.0` | `apps/cli/main.ts` 的命令树 | 对嵌套命令、参数声明和帮助信息支持成熟 | 不选 `commander`，因为当前命令树较长且有不少嵌套子命令；不选更重的 CLI 框架，避免引入额外结构 |
| `yaml` `2.8.3` | `packages/config/file-backed-config.ts`、`packages/skills/skill-discovery.service.ts` | API 简洁、TS 友好，适合解析本地配置和 skill manifest | 不选 `js-yaml`，因为当前需求更偏工程内解析，不需要更老的兼容面 |
| `semver` `7.7.4` | `packages/skills/skill-loader.service.ts` | 版本范围判断是标准问题，直接用业界标准库更稳 | 不手写版本比较，避免边界条件和 prerelease 处理错误 |
| `minimatch` `10.0.1` | `packages/domain/permission/*` | 权限和路径匹配只需要清晰 glob 语义，小而直接 | 不选 `micromatch`，因为当前不需要更重的模式能力；不手写 regex，避免可维护性差 |

### 2.2 LLM 抽象与 provider 适配

| 包 | 当前使用点 | 为什么选择它 | 为什么不选同类方案 |
| --- | --- | --- | --- |
| `ai` `6.0.0` | `packages/adapters/llm/ai-sdk-provider.adapter.ts`、`packages/application/agent-runtime/react-loop.service.ts` | 同时覆盖 `generateText`、流式输出、tool calling、`ToolLoopAgent`，非常适合这个项目的 agent/runtime 场景 | 不选 LangChain/LlamaIndex，因为项目更需要轻抽象和可控边界，而不是再套一层 agent 框架 |
| `@ai-sdk/openai` `3.0.0` | `openai-provider.adapter.ts` | 官方 OpenAI 路径用独立 provider 最直接 | 不直接用 OpenAI 官方 SDK，把 provider 逻辑绑死到某一家不利于网关切换 |
| `@ai-sdk/openai-compatible` `2.0.0` | `openai-provider.adapter.ts`、`deepseek-provider.adapter.ts`、`lmstudio-provider.adapter.ts` | 统一处理 OpenAI 兼容协议，极大降低多 provider 维护成本 | 不为 DeepSeek/LMStudio 各写一套 HTTP 适配；不把兼容逻辑散到业务层 |
| `ollama-ai-provider-v2` `3.5.0` | `ollama-provider.adapter.ts` | 本地模型有独立协议和常见部署方式，专门 provider 更清晰 | 不强行把 Ollama 当成 OpenAI 兼容层，避免接口语义偏差 |
| `zhipu-ai-provider` `0.2.2` | `zhipu-provider.adapter.ts` | 智谱有自己的 provider 能力，直接接更省适配成本 | 不自己拼 raw HTTP，避免重复处理认证、模型创建和响应格式 |
| `tiktoken` `1.0.22` | `ai-sdk-provider.adapter.ts` | 当前项目已经在做 token accounting、context budget 和截断，`tiktoken` 精度足够高 | 不用字符数估算，误差太大；不换成更粗糙 tokenizer，会直接影响上下文预算 |

### 2.3 契约和数据校验

| 包 | 当前使用点 | 为什么选择它 | 为什么不选同类方案 |
| --- | --- | --- | --- |
| `zod` `4.1.5` | 几乎所有 workspace 包 | 运行时校验和 TS 推导一体化，已经成为当前仓库事实标准 | 不选 `io-ts`，风格更重；不选 `typebox`，更偏 JSON Schema 工作流；不选 `valibot`，因为全仓库已经形成 Zod 习惯 |

补充说明：

- `packages/testing/package.json` 目前仍声明了 `zod@3.23.0`
- 但测试包源码也在 `import { z } from "zod"`
- 这更像依赖一致性问题，不应被视为一条新的选型路线

## 3. 开发与质量工具链逐项说明

| 包 | 当前使用点 | 为什么选择它 | 为什么不选同类方案 |
| --- | --- | --- | --- |
| `typescript` `5.8.3` | 根 `tsconfig.base.json`、全仓库 TS 代码 | 当前架构高度依赖明确边界和类型契约，TS 是基础设施 | 不用 JSDoc + JS，因为 ports、DTO、schema 和 monorepo 导出面都需要更强静态约束 |
| `vitest` `3.2.4` | `vitest.config.ts`、全仓库 `*.test.ts` | ESM、TS、Vite 生态兼容好，跑测试轻快 | 不选 Jest，当前仓库没有明显需要 Jest 生态的地方，且 ESM 配置更重 |
| `@vitest/coverage-v8` `3.2.4` | `vitest.config.ts` | 直接走 V8 覆盖率，配置简单 | 不单独接 Istanbul 工具链，减少一层复杂度 |
| `@biomejs/biome` `2.2.4` | `pnpm lint`、`pnpm format`、`lint-staged` | 一把工具同时做 formatter + linter，配置比 ESLint + Prettier 更轻 | 不继续用双工具链，减少规则冲突和维护成本 |
| `knip` `6.0.4` | `pnpm lint` | 比单纯 lint 更擅长抓无用依赖、导出和类型资产 | 不选 `depcheck`，因为 `knip` 对 TS/workspace/export 分析更实用 |
| `husky` `9.1.7` | `.husky/pre-commit`、`.husky/commit-msg` | 用标准方式安装和维护 git hooks | 不让每个开发者手配本地 hooks，无法保证一致性 |
| `lint-staged` `16.2.1` | `.husky/pre-commit` 和根 `package.json` | 只校验暂存区，提交前速度更可控 | 不在 pre-commit 全量跑整个仓库，开发反馈更慢 |
| `@manypkg/cli` `0.25.1` | `pnpm manypkg`、`pnpm validate:architecture` | 对 monorepo package manifest 一致性检查很直接 | 不自己写 workspace 清单脚本，维护成本高 |
| `@commitlint/cli` `20.5.0` | `.husky/commit-msg` | 让 commit message 变成可自动校验的契约 | 不依赖人工 review 才发现命名混乱 |
| `@commitlint/config-conventional` `20.5.0` | `commitlint.config.js` | 直接复用 conventional commits 作为基线，再加本项目的 type 扩展 | 不完全自定义规范，避免团队和工具生态脱节 |
| `@types/bun` `1.3.1` | `tsconfig.base.json` 中 `types: ["bun"]` | 当前代码显式使用 `bun:sqlite` 和 Bun 运行时语义，类型必须补齐 | 不自己维护 Bun ambient declarations，维护负担大 |
| `@types/semver` `7.7.1` | 为 `semver` 的 TS 使用补齐类型 | 当前仓库直接在 TS 中调用 `semver` | 不用 `any`，因为 skill compatibility 本身是边界逻辑 |
| `@types/yargs` `17.0.33` | 为 `yargs` CLI 表面补齐类型 | 顶层命令树和 handler 大量依赖 CLI 参数类型 | 不靠隐式类型推断硬扛，CLI 面一旦变复杂就容易失控 |

## 4. 非 npm 包但同样关键的工程选择

这些不是 `package.json` 里的 package，但对理解整体选型同样重要：

| 选择 | 当前用途 | 为什么这样选 | 为什么不选常见替代 |
| --- | --- | --- | --- |
| Bun | 运行 CLI、提供 `bun:sqlite` | 让 runtime 和 SQLite 路径都更直接 | 不纯用 Node，因为当前代码已经依赖 Bun 特性 |
| pnpm workspace | 管理 monorepo 包 | workspace 边界清晰，锁文件和依赖提升可控 | 不选 npm/yarn classic，因为 workspace 体验和约束不如 pnpm 明确 |

## 5. 总结

这份仓库的“包级决策”可以概括成一句话：

> 内部包强调边界分层；第三方包强调小而硬、职责单一；工程工具强调少而稳、自动化门禁。

如果只看表面，会觉得它用了很多包；但逐项拆开会发现，大多数包其实都在回答一个具体问题：

- 谁负责边界
- 谁负责校验
- 谁负责 provider 适配
- 谁负责工程门禁

这也是这个仓库比“直接堆一个 AI CLI 工程”更可维护的地方。
