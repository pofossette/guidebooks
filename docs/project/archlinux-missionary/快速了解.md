# Archlinux Missionary：架构与功能快速了解

## 文档定位

这份文档回答的是三个问题：

1. 这个项目现在已经能做什么
2. 它的真实运行时结构是什么
3. 源码应该从哪里开始看

本文采用“现状 + 目标设计并重”的口径：

- `已实现`：源码和 package manifests 已经能直接证明
- `进行中`：源码有局部落地，但还不是完整能力
- `目标设计`：主要存在于 `README.md`、`docs/architecture.md`、`docs/design/*`

## 1. 一句话理解项目

`archlinux-missionary` 是一个终端优先、以 Arch Linux 场景为中心的多 agent CLI 助手。它的核心目标不是“做一个花哨的 AI 壳”，而是把下面这条链路做成可恢复、可审计、带审批边界的系统能力：

`用户目标 -> 信息收集 -> 计划/命令分析 -> 风险解释 -> 用户审批 -> 命令执行 -> 结果回写`

## 2. 当前项目已经是什么

### 2.1 已实现的产品形态

- `已实现`：唯一交付界面是 CLI / REPL，入口在 `apps/cli/main.ts`
- `已实现`：主路径围绕 `init -> ask -> status -> resume`
- `已实现`：支持 provider 配置、权限规则、离线文档检索、artifact 清理、skills、workflow、systemd 导出/安装等辅助命令
- `已实现`：使用多 agent 角色分工，至少包含 `dispatcher`、`collector`、`validator`、`executor`
- `已实现`：把“先校验、再审批、再执行”做成硬边界

### 2.2 明确不是当前交付重点的东西

- `目标设计 / 未交付`：GUI
- `目标设计 / 未交付`：TUI
- `目标设计 / 未交付`：默认在线优先检索
- `目标设计 / 未交付`：复杂多 provider fallback 编排
- `目标设计 / 未交付`：完整 packaging / distribution / PKGBUILD

## 3. 先从哪里看源码

如果你第一次读这个项目，建议按下面顺序：

1. `README.md`
   先建立产品目标、主命令面和文档地图。
2. `apps/cli/main.ts`
   看 CLI 暴露了哪些命令，哪些是主路径，哪些是支持命令。
3. `apps/cli/bootstrap.ts`
   这是现状的组合根。它最能说明“系统真正由哪些对象拼起来”。
4. `packages/application/index.ts`
   看应用层公开了哪些 use case。
5. `packages/domain/index.ts`
   看核心领域状态、事件、策略都有哪些聚合。
6. `packages/adapters/*`
   看 provider、shell、storage 这些基础设施如何落地。
7. `docs/architecture.md` 和 `docs/constraints/README.md`
   看设计意图、模块边界和未来目标。

## 4. 真实运行时主链路

结合 `apps/cli/main.ts` 与 `apps/cli/bootstrap.ts`，当前源码里的主对象图可以简化成：

```text
CLI 命令 / bare entry
  -> bootstrapCli()
  -> loadConfigState()
  -> ProviderRegistry + ProviderGateway
  -> WorkspaceStorageAdapter
  -> NodeShellRunnerAdapter
  -> createToolRegistry() + DynamicToolRegistry
  -> createSkillRuntimeService()
  -> application services
  -> domain reducers / policies
  -> adapters 执行外部交互
```

更具体一点：

```text
用户输入
  -> apps/cli/main.ts 解析命令
  -> apps/cli/bootstrap.ts 组装 runtime
  -> packages/application/* 编排会话、审批、检索、任务、作业
  -> packages/domain/* 决定状态迁移和权限/命令策略
  -> packages/tools/* 暴露给 agent 的工具
  -> packages/adapters/* 对接 LLM / shell / storage
  -> presenters / TerminalUserIO 回显结果
```

## 5. 分层和包地图

| 层 | 主要目录 | 当前职责 |
| --- | --- | --- |
| Interface | `apps/cli` | 命令解析、REPL、终端输入输出、presenter、组合根 |
| Application | `packages/application` | 会话运行时、审批编排、工作流引擎、检索同步、读模型、skills runtime |
| Domain | `packages/domain` | 纯领域状态、事件、reducer、权限策略、命令分析、systemd 规则、user profile 规则 |
| Ports | `packages/ports` | 面向上层的稳定接口契约 |
| Adapters | `packages/adapters` | LLM provider、shell 执行、存储落地 |
| Assets / Support | `packages/prompts`、`packages/tools`、`packages/skills`、`packages/shared`、`packages/workflows`、`packages/config` | prompt 资产、工具注册、技能装配、共享 DTO/ID/时间、配置和工作流基础件 |

## 6. 四类内置 agent 怎么协作

| Agent | 当前职责 | 何时出场 |
| --- | --- | --- |
| `dispatcher` | 面向用户、做总编排、汇总结果、推动下一步 | 几乎所有主会话路径 |
| `collector` | 收集只读事实、查文档、查配置、查系统状态 | 需要补上下文时 |
| `validator` | 分析候选命令、解释风险、触发审批链 | 一旦计划涉及命令执行 |
| `executor` | 执行已批准计划并回传结果 | 审批通过之后 |

这个拆分的核心价值不是“为了多 agent 而多 agent”，而是把以下边界固定下来：

- 收集和变更分离
- 风险解释和真正执行分离
- 用户交互和基础设施实现分离

## 7. 功能面快速扫读

| --- | --- |
| `missionary init` | 采集初始系统快照并落盘 |

## 8. 当前代码事实和目标设计的关系

这个仓库不是“代码完全等于文档”，而是“代码与设计文档并行演进”。理解时要抓住下面几点：

- `已实现`：Bun 运行时、pnpm workspace、TypeScript、yargs、AI SDK provider gateway、Zod、Bun SQLite、Vitest、Biome
- `进行中`：检索、skills runtime、workflow/runtime observability、provider policy、read models
- `目标设计`：Drizzle ORM、Pino、tree-sitter AST 命令分析、`@inquirer/prompts`、`p-queue` / `p-limit`

换句话说：

- `bootstrap.ts` 更适合回答“现在是怎么跑起来的”
- `docs/architecture.md` 更适合回答“目标上希望怎么长期稳定”
