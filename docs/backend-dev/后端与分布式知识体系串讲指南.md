# 后端与分布式知识体系串讲指南

这篇文档的目标不是把所有技术点铺满，而是把后端开发里最容易学散的几条线：

- 网络与操作系统
- API 与应用服务
- 数据库与缓存
- 消息队列与异步任务
- 高性能、高可用与分布式
- 系统设计与工程治理

压成一条可以反复复习的主线。

如果你现在的状态是：

- 做过接口，但说不清一次请求为什么会慢、为什么会失败
- 学过 Redis、MQ、微服务、RPC，但脑子里没有顺序
- 看系统设计题时总觉得每个点都知道一点，但串不起来

那这篇文档就是用来补这张总地图的。

## 一、先明确：后端到底在解决什么问题

前端更靠近用户交互，后端更靠近 **状态、资源、协作和稳定性**。

后端真正要回答的问题通常只有 6 类：

1. 请求怎么进来，怎么被正确处理
2. 数据存在哪，怎么保证不乱
3. 并发上来后，系统为什么还能扛住
4. 某个组件挂了，为什么不会把整条链路拖死
5. 多个服务、多台机器之间怎么协作
6. 出问题后，怎么定位、恢复和演进

所以你学后端，不是在背技术名词，而是在补这 6 类问题的答案。

## 二、先搭底座：后端不是从框架开始，而是从机器开始

很多人一上来就学 `NestJS`、`Spring Boot`、`Express`，这当然没错，但容易有个问题：

**会写代码，不知道代码跑起来后发生了什么。**

后端底层地图应该先补两块：

### 1. 计算机网络

网络解决的是：

**两台机器上的程序，怎么可靠通信。**

你至少要能把下面这些东西串起来：

- 分层模型：应用层、传输层、网络层分别在干嘛
- `DNS`：域名怎么解析成 IP
- `TCP`：为什么可靠，为什么有三次握手、四次挥手
- `HTTP`：请求和响应语义怎么表达
- `HTTPS`：为什么能加密，证书和 TLS 在做什么
- `SSE` / `WebSocket`：流式通信为什么适合实时场景

你平时写接口时遇到的很多问题，本质上都属于网络问题：

- 为什么连接会超时
- 为什么请求会重试
- 为什么网关前面要有负载均衡
- 为什么长连接能减少频繁建连成本

对应文档：

- [计算机网络知识串讲指南](./计算机网络知识串讲指南.md)

### 2. 操作系统

操作系统解决的是：

**一台机器上的 CPU、内存、磁盘、文件、进程、线程和 IO 怎么被管理。**

你至少要能把这些概念串起来：

- 进程和线程
- CPU 调度和上下文切换
- 用户态与内核态
- 虚拟内存、分页、缺页
- 文件系统
- 阻塞 IO、非阻塞 IO、IO 多路复用、`epoll`

为什么这块重要？

因为后端性能问题经常不是“代码写得不优雅”，而是：

- 线程开太多，切换成本爆炸
- 连接太多，阻塞住了
- 内存没控住，触发 OOM
- 磁盘 IO 抖动，数据库慢下来

对应文档：

- [操作系统知识串讲指南](./操作系统知识串讲指南.md)

## 三、进入第一层：请求是怎么走完整条链路的

真正学后端，最值得先建立的是“请求生命周期”。

先把一次普通请求理解成这条链路：

`Client -> CDN / LB -> Gateway -> App -> Cache / DB / MQ / Search -> Response`

如果是现代 Agent 或实时系统，还可能变成：

`Client -> Gateway -> Auth -> Rate Limit -> App -> LLM / Tool / RAG / Queue -> Stream Response`

围绕这条链路，后端最常见的工作有：

### 1. 接口设计

接口设计不只是定义 URL。

你要同时考虑：

- 路由怎么命名
- 参数怎么校验
- 状态码怎么表达
- 错误码怎么统一
- 请求是否幂等
- 是否需要分页、过滤、排序
- 是否需要同步返回还是异步返回

### 2. 中间件 / Hook / Filter

请求进服务后，不会直接撞到业务逻辑，中间通常会经过一层请求处理链。

这一层一般负责：

- 日志
- request id 注入
- 鉴权
- 参数校验
- 限流
- 上下文传递
- 错误统一处理

你可以把它理解成：

**在真正执行业务代码之前，先把横切问题统一收口。**

- [NestJS](./NestJS/)

## 四、第二层：业务代码真正落地时，核心是“状态”

后端和脚本最大的区别在于：

**后端要长期管理状态。**

这就引出了数据库、缓存、对象存储、搜索系统这些数据组件。

### 1. 先学关系型数据库，因为大多数业务状态都在这里

关系型数据库最适合存：

- 用户
- 订单
- 账户
- 配置
- 会话
- 任务状态

为什么它是主线？

因为它同时提供了几个后端最关键的能力：

- 结构化建模
- SQL 查询
- 索引优化
- 事务
- 并发控制
- 可靠持久化

学习顺序建议按这条线：

**表设计 -> SQL -> 索引 -> 执行计划 -> 事务 -> MVCC -> 锁 -> WAL -> 性能优化 -> 高可用扩展**

对应文档：

- [PostgreSQL 知识体系快速构建指南](./PostgreSQL%20知识体系快速构建指南.md)
- [PostgreSQL](./PostgreSQL/)

### 2. NoSQL、文档库与搜索系统是在补关系库的边界

关系型数据库很强，但不是所有问题都该交给它。

常见边界有三类：

#### 文档型数据

如果数据天然半结构化，字段变化频繁，或者业务更适合按文档整体读写，那么文档数据库会更顺手。

对应文档：

- [MongoDB](./MongoDB/)

#### 全文检索与复杂搜索

如果你需要：

- 关键词匹配
- 相关性排序
- 高亮
- 多字段检索
- 大规模搜索

那就应该想到搜索系统，而不是继续硬压数据库。

对应文档：

- [Elasticsearch](./Elasticsearch/)

#### 短期热点数据与状态加速

如果你的问题是“读太多、延迟太高、数据库顶不住”，那就该想到缓存。

对应文档：

- [Redis](./Redis/)

## 五、第三层：缓存不是为了炫技，而是为了解决读压力和时延

很多人学 Redis 容易学成数据结构背诵。

其实更好的问题是：

**数据库明明能查，为什么还要加一层缓存？**

答案通常有三种：

1. 热点读太多，数据库扛不住
2. 某些数据读取代价高，想降低延迟
3. 某些状态需要一个高频、短期、低成本的存储层

缓存需要重点理解的不是命令，而是这几类工程问题：

- 缓存穿透
- 缓存击穿
- 缓存雪崩
- 缓存一致性
- 过期策略
- 分布式锁
- 限流与计数

一句话记忆：

**缓存的价值不是“比数据库快”，而是“把高频压力从数据库卸下来”。**

## 六、第四层：同步链路扛不住时，就要进入异步化

只要系统开始做这些事：

- 发短信
- 发邮件
- 生成报表
- 切片上传
- 审核
- embedding
- 重试任务
- 大批量导入导出

你就会发现：这些工作不适合都堵在一次 HTTP 请求里。

这时消息队列和后台任务系统就开始出现。

### 1. 消息队列在解决什么

消息队列主要解决 4 个问题：

1. 解耦
2. 异步
3. 削峰
4. 可靠投递

学习 MQ 时不要只记 RabbitMQ、Kafka、RocketMQ 的名字，而是先问：

- 为什么需要生产者和消费者解耦
- 什么叫 ack
- 什么叫重复消费
- 什么叫顺序消息
- 什么叫积压
- 什么叫死信队列
- 为什么最终一致性常常靠 MQ 做补偿

对应文档：

- [MQ](./MQ/)

### 2. 后台任务系统比“有个队列”更完整

很多业务不是简单“发个消息就完了”，而是还要：

- 重试
- 记录进度
- 幂等
- 取消
- 恢复
- 死信处理
- 并发控制

所以你要建立的不是“我会用某个队列库”，而是：

**我知道长任务为什么不能放在同步链路里，以及异步任务怎么保证最终完成。**

对应文档：

- [Agent 后端基础](./agent-backend/)

## 七、第五层：后端真正难的地方在并发与一致性

单机、单线程、单数据库、单请求时，很多事情看起来都不难。

一旦进入并发环境，问题马上复杂起来：

- 两个请求同时修改同一行数据怎么办
- 用户重复提交怎么办
- 支付回调多次到达怎么办
- 多个 worker 同时抢一个任务怎么办
- 某一步成功、某一步失败时，数据怎么办

这时你就要把“一致性”作为一条主线来学。

### 1. 单库内的一致性

先处理数据库事务能覆盖的问题：

- 原子性
- 隔离级别
- 行锁 / 乐观锁
- 幂等键
- 唯一约束

很多工程问题，在单库阶段就能解决，没必要过早上分布式大招。

### 2. 跨系统的一致性

当链路跨到：

- 数据库
- Redis
- MQ
- 外部服务
- 多个微服务

就很难再靠一个本地事务包住全部流程。

这时需要理解：

- 最终一致性
- 状态机
- 补偿
- Outbox
- Saga
- TCC 的适用边界

一句话记忆：

**一致性问题的本质，不是“怎么永远不出错”，而是“出错后怎么把状态收回来”。**

## 八、第六层：系统变大后，才真正进入分布式

很多人把“部署多台机器”直接等同于分布式，但这只是开始。

分布式真正要解决的是：

**系统拆成多个节点后，它们怎么通信、怎么发现彼此、怎么协同、怎么保证状态不乱。**

这一层建议按 4 条主线学。

### 1. 理论主线：CAP、BASE、共识

你不需要一上来就背算法细节，但要先接受一个事实：

**网络不可靠，所以多节点系统一定要做取舍。**

这条线回答的是：

- 为什么一致性和可用性常常不能同时拉满
- 为什么最终一致性是大量业务系统的现实选择
- 为什么需要共识算法来维护某些关键元数据

### 2. 通信主线：RPC、网关、服务发现

服务拆开后，必须解决：

- 服务地址怎么找
- 请求怎么路由
- 接口怎么治理
- 配置怎么统一下发

所以你会碰到：

- RPC
- API 网关
- 注册中心
- 配置中心

### 3. 数据主线：分布式 ID、锁、事务

单机内很多“理所当然”的事情，拆到多节点后都不再自然成立：

- 自增 ID 够不够用
- 多实例怎么抢锁
- 跨服务事务怎么处理

这条线的核心问题是：

**共享状态一旦不在同一个进程、不在同一个数据库，协调成本就出现了。**

### 4. 治理主线：观测、限流、熔断、隔离

分布式系统真正的难点之一不是“能跑起来”，而是：

**某个节点抖动时，为什么不会把全部服务带崩。**

所以你后面一定会碰到：

- 服务治理
- 超时
- 重试
- 熔断
- 限流
- 舱壁隔离
- 灰度发布

## 九、第七层：微服务不是银弹，而是组织复杂度后的结果

当系统还小的时候，单体应用通常更简单。

只有当你开始遇到这些问题时，微服务才可能变得合理：

- 业务边界明显分化
- 团队规模变大
- 发布节奏不同
- 某些模块流量、资源需求差异很大
- 单体代码和依赖关系已经难以维护

微服务带来的收益通常是：

- 模块边界更清晰
- 独立扩缩容
- 独立发布
- 技术栈更灵活

但代价也很直接：

- 网络调用代替进程内调用
- 排障链路更长
- 一致性问题更复杂
- 运维和治理成本显著上升

所以学习微服务时，重点不是“会不会拆服务”，而是：

**知道什么时候不该拆，什么时候拆了也能治理得住。**

## 十、第八层：高性能、高可用其实贯穿全程

很多人会把这两块当成独立专题，但更准确的理解是：

- 高性能在回答：系统为什么会慢，慢在哪，怎么扛住更大流量
- 高可用在回答：系统为什么不会轻易挂，挂了为什么还能恢复

### 1. 高性能看四层

- 入口层：CDN、负载均衡、网关
- 应用层：池化、批处理、异步化、并发控制
- 数据层：索引、缓存、读写分离、分库分表
- 链路层：削峰、降级、流式处理

### 2. 高可用看五类动作

- 超时
- 重试
- 熔断
- 降级
- 隔离

外加两个前提：

- 幂等
- 可观测性

因为没有幂等，重试可能把系统打乱；没有可观测性，故障根本找不到。

## 十一、第九层：系统设计就是把前面所有知识装进一个回答框架

系统设计不是新知识，而是前面所有知识的压缩表达。

你遇到一道系统设计题时，脑子里最好按这条主线展开：

1. 需求和规模
2. 核心接口
3. 核心数据模型
4. 主链路
5. 缓存 / 搜索 / 队列怎么介入
6. 一致性怎么保证
7. 高峰流量怎么扛
8. 故障怎么兜底
9. 监控、日志、追踪怎么做
10. 后续怎么扩展

如果你能按这个结构回答，大部分后端和分布式题目都不会完全失控。

## 十二、把整个知识体系压成一张学习路径

如果你想从零到能做后端、能聊分布式，推荐按下面顺序推进。

### 第 1 阶段：补底座

- 网络
- 操作系统
- Linux 基础命令与日志查看
- HTTP / TCP / 进程线程 / IO 模型

目标：

能解释一次请求为什么会超时、为什么会阻塞、为什么会有连接和线程成本。

### 第 2 阶段：学单体后端主线

- 一个 Node.js / NestJS / Fastify 服务怎么组织
- 路由、校验、中间件、错误处理
- 数据库表设计、SQL、索引、事务
- Redis 缓存、限流、幂等

目标：

能独立做出一个结构清晰、能稳定跑的业务后端。

### 第 3 阶段：学异步与可靠性

- MQ
- 后台任务
- 重试、死信、补偿
- 最终一致性

目标：

能把长任务和核心交易链路拆开，并知道失败后怎么补。

### 第 4 阶段：学分布式与治理

- RPC、网关、注册发现、配置中心
- 分布式锁、分布式 ID、分布式事务
- 可观测性、限流、熔断、降级

目标：

能解释多服务系统为什么能协作，以及为什么不会被局部故障拖垮。

### 第 5 阶段：学系统设计与容量演进

- 单机到多机
- 单库到分库分表
- 单体到微服务
- 高性能、高可用、扩容路径

目标：

能把“一个功能怎么写”升级为“一个系统怎么设计、怎么演进”。

## 十三、面试或复习时，最实用的一段总串讲

如果你要在几分钟内把后端和分布式知识体系串起来，可以按下面这段表达：

“后端开发本质上是在处理请求、状态、并发和稳定性。底层先要补网络和操作系统，因为请求要通过 HTTP/TCP 进入服务，服务本身又受进程线程、内存和 IO 模型影响。进入应用层后，要先理解接口设计和中间件链路，再往下是数据库、缓存、搜索和对象存储这些状态系统，其中关系型数据库是主线，因为表设计、索引、事务、锁和并发控制决定了大部分业务数据是否可靠。读压力和热点问题通常用 Redis 解决，长任务和削峰则通过 MQ 和后台任务系统处理。当系统跨进程、跨节点、跨服务后，就进入分布式问题，包括服务发现、RPC、网关、配置中心，以及分布式锁、分布式 ID、最终一致性和分布式事务。再往上，高性能负责解决系统为什么会慢，高可用负责解决系统为什么不会一挂到底，系统设计则是把这些知识压缩进需求、数据模型、主链路、瓶颈、故障处理和扩展方案的一套回答框架里。” 

## 十四、这篇最重要的结论

后端和分布式不是一堆并列专题，而是一条逐层展开的主线：

- 网络和操作系统，决定请求为什么能到、代码为什么能跑
- 应用服务和中间件，决定请求怎么被正确处理
- 数据库、缓存、搜索和队列，决定状态怎么存、怎么读、怎么异步协作
- 并发控制和一致性，决定系统在复杂场景下会不会乱
- 分布式与微服务，决定多节点系统怎么通信、治理和演进
- 高性能、高可用与系统设计，决定系统在真实流量和真实故障下还能不能稳住

把这条主线建立起来，后面再学任何中间件、框架和架构题，都会更容易归位。
