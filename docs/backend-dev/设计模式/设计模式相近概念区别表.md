# 设计模式相近概念区别表

这篇不是系统讲某一个模式，而是解决一个更实际的问题：

**很多模式你都听过，但一到面试或写代码时，总是分不清它们到底差在哪。**

所以这篇专门按“相近概念对比”的方式来整理，适合作为速查表。

## 一、装饰器模式 vs 代理模式

这两个最容易混。

| 对比项 | 装饰器模式 | 代理模式 |
|---|---|---|
| 核心目的 | 给对象动态增强能力 | 控制对真实对象的访问 |
| 关注点 | 功能扩展 | 访问控制、转发、隔离 |
| 是否强调原有接口一致 | 是 | 是 |
| 常见附加行为 | 日志、缓存、重试、统计 | 权限校验、延迟加载、远程调用、保护对象 |
| 调用者感知 | 通常感知不到是“增强版”对象 | 通常也感知不到，但本质是“先过代理” |
| 一句话判断 | 给对象加能力 | 替对象挡在前面 |

### 怎么快速区分

- 如果你的重点是“在原功能前后再包一层能力”，更像装饰器模式。
- 如果你的重点是“先由一个中间人决定能不能访问真实对象”，更像代理模式。

### TS 后端里的典型例子

- 装饰器模式：给 `UserService` 外面包一层缓存、日志、指标采集
- 代理模式：通过一个 `AuthProxy` 决定请求能不能调用真实服务

## 二、工厂模式 vs 单例模式

这两个常被一起提，但它们根本不在一个维度。

| 对比项 | 工厂模式 | 单例模式 |
|---|---|---|
| 核心问题 | 对象怎么创建 | 对象创建多少个 |
| 关注点 | 封装创建逻辑 | 控制实例数量 |
| 是否关心具体实现切换 | 很关心 | 不一定关心 |
| 是否强调全局唯一 | 不强调 | 强调 |
| 典型场景 | 按配置创建不同短信服务、存储服务 | 配置中心、连接池、日志实例 |
| 一句话判断 | 决定“造谁” | 决定“只造一个” |

### 怎么快速区分

- 你在纠结“根据条件返回哪种实现”，这是工厂模式。
- 你在纠结“这个资源是不是只该有一个实例”，这是单例模式。

### 一个常见误区

很多人会把“工厂 + 单例”混成一个东西。其实它们可以组合：

- 工厂负责创建
- 工厂内部返回单例实例

但这不代表两者是同一模式。

## 三、策略模式 vs 状态模式

这两个在代码结构上经常长得像，但出发点不一样。

| 对比项 | 策略模式 | 状态模式 |
|---|---|---|
| 核心目的 | 在多种算法/方案之间切换 | 根据内部状态改变行为 |
| 行为切换依据 | 外部选择或配置 | 对象当前状态 |
| 是否强调状态流转 | 不强调 | 很强调 |
| 典型问题 | 支付方式、排序策略、路由策略 | 订单流转、工单流转、任务生命周期 |
| 一句话判断 | 换方案 | 换状态 |

### 怎么快速区分

- 同一件事有多种做法，用户或配置来选，这是策略模式。
- 同一个对象在不同阶段行为不同，而且状态之间会流转，这是状态模式。

### TS 后端里的典型例子

- 策略模式：不同大模型 provider 的调用策略
- 状态模式：任务 `pending -> running -> done -> failed` 的行为切换

## 四、适配器模式 vs 外观模式

这两个都像“包一层”，但目的不同。

| 对比项 | 适配器模式 | 外观模式 |
|---|---|---|
| 核心目的 | 转换接口，让不兼容对象能一起工作 | 对复杂子系统提供统一简化入口 |
| 关注点 | 接口兼容 | 使用体验和复杂度收敛 |
| 是否一定有旧接口/第三方接口 | 很常见 | 不一定 |
| 典型场景 | 封装第三方 SDK、统一不同存储接口 | 给一组复杂服务提供一个简单调用入口 |
| 一句话判断 | 接口不兼容，帮你翻译 | 系统太复杂，帮你收口 |

### 怎么快速区分

- 如果原始对象“接口对不上”，你在做适配器。
- 如果原始系统“太复杂不好用”，你在做外观模式。

## 五、责任链模式 vs 策略模式

这两个都可能让你少写 `if/else`，但执行方式不同。

| 对比项 | 责任链模式 | 策略模式 |
|---|---|---|
| 核心目的 | 按顺序让多个处理者依次尝试或接力处理 | 从多个方案里选一个执行 |
| 执行方式 | 可能经过多个节点 | 通常只选一个策略 |
| 是否强调链路顺序 | 强调 | 不强调 |
| 典型场景 | 中间件、审批流、校验链 | 折扣策略、路由策略、序列化策略 |
| 一句话判断 | 一路往后传 | 选一个来做 |

### 怎么快速区分

- 如果请求要经过多个环节层层处理，是责任链。
- 如果只是从若干算法中选一个，是策略。

## 六、模板方法模式 vs 策略模式

这两个都在处理“流程里有变化点”，但组织方式不同。

| 对比项 | 模板方法模式 | 策略模式 |
|---|---|---|
| 核心目的 | 固定流程骨架，把部分步骤留给子类实现 | 把可变算法独立成可替换对象 |
| 复用方式 | 继承 | 组合 |
| 对扩展点的约束 | 流程顺序较固定 | 更灵活 |
| 典型场景 | 导入流程、任务执行框架、统一工作流骨架 | 不同排序、过滤、推荐、支付算法 |
| 一句话判断 | 骨架固定，细节可改 | 算法独立，随时可换 |

### 怎么快速区分

- 如果主流程很稳定，只是某几个步骤可变，更像模板方法。
- 如果你希望把整套处理逻辑当成插件替换，更像策略。

## 七、观察者模式 vs 发布订阅模式

很多文章会混着讲，但工程上最好分开理解。

| 对比项 | 观察者模式 | 发布订阅模式 |
|---|---|---|
| 核心关系 | 观察者直接订阅目标对象 | 通过事件中心或消息中间件解耦 |
| 耦合程度 | 相对更直接 | 更松耦合 |
| 是否需要中间代理 | 不一定 | 一般需要 |
| 典型场景 | 进程内事件回调、UI 更新 | 消息总线、领域事件、异步通知 |
| 一句话判断 | 对象直接通知观察者 | 通过中间通道广播消息 |

### 怎么快速区分

- 进程内一个对象状态变化后直接通知监听者，更像观察者。
- 借助事件总线、MQ、消息中心进行广播，更像发布订阅。

## 八、组合模式 vs 聚合对象

很多人看到树形结构就说“这是组合模式”，其实不一定。

| 对比项 | 组合模式 | 普通对象聚合 |
|---|---|---|
| 核心目的 | 统一对待单个对象和对象组合 | 只是把多个对象放在一起 |
| 是否强调一致接口 | 强调 | 不一定 |
| 典型场景 | 文件夹和文件、菜单和子菜单、组织树 | 一个服务里引用多个 helper |
| 一句话判断 | 叶子节点和容器节点用同一套操作 | 只是组合，不一定是模式 |

### 怎么快速区分

- 如果叶子和容器能用同一接口处理，这是组合模式。
- 如果只是一个类里有很多成员对象，那通常不是组合模式。

## 九、命令模式 vs 责任链模式

| 对比项 | 命令模式 | 责任链模式 |
|---|---|---|
| 核心目的 | 把请求封装成对象 | 把请求沿链路传递给多个处理者 |
| 关注点 | 请求抽象、排队、撤销、记录 | 多节点分步处理 |
| 典型场景 | 任务队列、操作日志、撤销重做 | 中间件、审批、过滤器 |
| 一句话判断 | 把“做什么”封成对象 | 把“谁来处理”串成链 |

## 十、记忆口诀

- 装饰器和代理：`一个加功能，一个管访问`
- 工厂和单例：`一个管创建方式，一个管实例数量`
- 策略和状态：`一个换方案，一个换阶段`
- 适配器和外观：`一个翻译接口，一个收拢复杂度`
- 责任链和策略：`一个走整条链，一个挑一个方案`
- 模板方法和策略：`一个固定骨架，一个自由替换`

## 这篇最重要的结论

很多设计模式看起来像，通常不是因为它们真的一样，而是因为：

- 都在“包一层”
- 都在“减少 if/else”
- 都在“隔离变化”

真正区分它们，要看三个问题：

1. 这个模式主要在解决什么问题？
2. 变化点是在“创建、访问、流程、算法、状态”里的哪一类？
3. 调用方看到的是“一个对象被增强了”，还是“一个流程被分发了”，还是“一个接口被统一了”？
