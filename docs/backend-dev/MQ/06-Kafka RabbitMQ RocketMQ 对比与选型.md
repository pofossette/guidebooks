# 06. Kafka、RabbitMQ、RocketMQ 对比与选型

MQ 选型最忌讳一句话：

**别人都用 Kafka，所以我也用 Kafka。**

正确思路应该是先看业务需求，再看中间件特性。

## 一、先看你到底在解决什么问题

选型前先问自己：

- 我更重视吞吐，还是更重视低延迟？
- 我是事件流平台，还是业务任务队列？
- 我是否非常在意顺序消息？
- 我是否需要延迟消息、事务消息、死信机制？
- 团队有没有现成运维经验？

这些问题不清楚，产品名背再多也没意义。

## 二、三者的粗略定位

| 产品 | 更常见定位 |
|---|---|
| Kafka | 高吞吐事件流、日志采集、数据管道 |
| RabbitMQ | 传统业务消息队列、路由分发 |
| RocketMQ | 业务消息场景较全，顺序、事务、延迟支持常被强调 |

这只是粗略定位，不是绝对边界。

## 三、Kafka 的特点

更常被用于：

- 日志采集
- 埋点流转
- 大规模事件流
- 数据平台和流式处理链路

常见印象：

- 吞吐高
- 分区模型清晰
- 生态成熟
- 更偏日志流平台思路

代价通常是：

- 理解门槛相对高
- 业务消息某些能力要自己补工程方案
- 运维和参数调优不算轻

## 四、RabbitMQ 的特点

更常被用于：

- 传统业务异步任务
- 灵活路由
- 中小规模业务消息系统

常见印象：

- 上手相对直观
- 路由模型灵活
- 适合很多典型业务异步场景

代价通常是：

- 在超大吞吐场景下不如 Kafka 那么常见
- 大规模堆积和流式场景通常不是它的主战场

## 五、RocketMQ 的特点

更常被用于：

- 电商业务链路
- 顺序消息要求较强的场景
- 延迟消息、事务消息较常见的业务系统

常见印象：

- 业务消息能力比较全面
- 国内资料和落地案例较多
- 在事务消息、顺序消息上讨论频率高

代价通常是：

- 团队如果没有相关经验，上手和运维也不算零成本
- 海外生态和社区普及度通常不如 Kafka 广

## 六、怎样做务实选型

可以按这张思路表快速判断：

| 需求 | 更常见选择倾向 |
|---|---|
| 海量日志、事件流、大数据链路 | Kafka |
| 传统业务异步、灵活路由 | RabbitMQ |
| 电商型业务消息、顺序/事务/延迟要求明显 | RocketMQ |
| 小系统、轻量任务队列 | Redis Streams / BullMQ / 数据库任务表 |

## 七、不要忽略团队现实

选型不只是技术对比，还包括：

- 团队谁会运维
- 是否已有现成集群
- 监控和告警是否成熟
- 是否有历史系统包袱
- 是否需要跨语言生态

很多时候，**团队熟悉并能稳定运维的方案，比“理论上更强”的方案更好。**

## 八、面试里的回答模板

如果被问“Kafka、RabbitMQ、RocketMQ 怎么选”，可以这样回答：

1. 先说三者定位不同，不是简单谁更高级。
2. 再说 Kafka 偏高吞吐事件流，RabbitMQ 偏传统业务消息，RocketMQ 偏业务消息能力更全。
3. 最后补一句，实际选型还要看顺序、事务、延迟、吞吐、团队运维经验和现有基础设施。

这样的回答通常比单纯背参数更稳。
