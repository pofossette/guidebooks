# 02. 消息模型与核心概念

学 MQ 时，很多人最大的问题不是不会用，而是名词总是混着记。

这一篇专门把几个最核心的模型理顺。

## 一、点对点和发布订阅

### 1. 点对点

一条消息通常只会被一个消费者处理。

适合：

- 异步任务
- 订单处理
- 转码任务
- 审核任务

### 2. 发布订阅

一条消息可以被多个消费者组分别消费。

适合：

- 订单支付事件广播
- 用户注册事件广播
- 数据同步
- 审计日志分发

面试里常说的 `Topic`，很多时候更偏发布订阅语义。

## 二、Queue、Topic、Partition 到底是什么

不同 MQ 产品命名不完全一样，但可以先这么理解：

| 概念 | 通俗理解 |
|---|---|
| Queue | 一条消费通道，偏任务队列语义 |
| Topic | 一类消息主题，偏事件广播语义 |
| Partition | Topic 下的并行分片 |

`Partition` 很重要，因为它影响：

- 吞吐能力
- 消费并行度
- 顺序性边界

通常只能保证**单分区内有序**，很难保证全局绝对有序。

## 三、生产者、消费者、消费者组

### 1. 生产者

负责发送消息。

它要关心的问题包括：

- 发送是否成功
- 是否需要重试
- 是否要求顺序
- 是否要求事务或回查

### 2. 消费者

负责处理消息。

它要关心的问题包括：

- 什么时候确认消费成功
- 失败后怎么重试
- 重复消费怎么处理
- 是否需要并发消费

### 3. 消费者组

消费者组可以理解成一组共同消费同一类消息的实例。

它的价值是：

- 扩展消费能力
- 实现一个业务组内“分摊消息”
- 不同业务组可以各自独立消费同一主题

## 四、什么是 Ack

`Ack` 就是确认消息已经处理完成。

这里最关键的问题不是“有没有 Ack”，而是：

**你是在什么时候 Ack。**

如果业务还没真正处理成功就先确认，后面失败就可能丢消息。

更稳的做法通常是：

1. 拉到消息
2. 执行业务逻辑
3. 业务成功后再确认

## 五、什么是 Offset

`Offset` 可以理解成消费进度。

尤其在 `Kafka` 体系里，它表示消费者已经读到哪里。

这会引出一个很高频的问题：

**先提交 Offset，还是先处理业务？**

如果先提交再处理，处理失败时消息可能相当于“被跳过”。
如果先处理再提交，重复投递概率会变高。

所以很多 MQ 系统默认更偏向：

**至少一次投递，而不是绝不重复。**

## 六、顺序到底是在哪一层保证

顺序不是“整个 MQ 天然有序”，而是要看：

- 同一个 Topic 还是不同 Topic
- 同一个分区还是不同分区
- 同一个消费者线程还是多线程并发
- 消费失败是否重试插队

业务如果非常依赖顺序，通常要把同一业务主键路由到同一分区，例如：

- 同一订单 ID
- 同一用户 ID
- 同一账户 ID

## 七、死信队列和重试队列

### 1. 重试队列

消费失败后，先按规则重试。

适合处理：

- 临时网络抖动
- 下游服务短暂超时
- 数据库瞬时连接异常

### 2. 死信队列

多次重试仍失败的消息进入死信队列。

它的价值不是“丢弃”，而是让你：

- 保留现场
- 方便人工排查
- 后续补偿或重放

## 八、延迟消息

有些场景需要“不是现在消费，而是过一会再消费”。

例如：

- 订单超时取消
- 支付超时检查
- 优惠券到期提醒
- 重试延后执行

这就需要延迟消息或定时消息能力。

## 九、学到这里先记住一句话

MQ 的核心不是“把消息丢进去”，而是：

**在可接受的吞吐、延迟和复杂度下，把消息可靠地送到正确的消费者，并让消费者能把它正确处理完。**
