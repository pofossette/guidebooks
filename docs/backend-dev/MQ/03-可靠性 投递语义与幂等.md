# 03. 可靠性、投递语义与幂等

真正让 MQ 难的，不是“怎么发消息”，而是：

**消息会不会丢、会不会重复、消费者怎么兜底。**

## 一、三种常见投递语义

| 语义 | 含义 | 风险 |
|---|---|---|
| At most once | 最多一次 | 可能丢消息 |
| At least once | 至少一次 | 可能重复 |
| Exactly once | 精确一次 | 成本高、限制多 |

真实业务里最常见的思路是：

**接受至少一次，然后通过幂等把重复消费变得可控。**

## 二、为什么会丢消息

消息丢失一般发生在 3 个环节。

### 1. 生产阶段

例如：

- 生产者发送失败
- 发送成功但没收到确认
- 网络闪断导致状态不确定

### 2. 存储阶段

例如：

- Broker 宕机
- 没有持久化成功
- 副本没同步完成

### 3. 消费阶段

例如：

- 业务还没执行成功就先 Ack
- 处理成功但提交进度失败
- 消费者崩溃导致状态不确定

## 三、为什么会重复

重复消费反而是更常见的情况。

常见原因：

- 生产者重试导致重复发送
- 消费者处理成功但 Ack 失败
- Broker 不确定消费者是否处理完成，于是再次投递
- 消费者重平衡后重新拉取旧消息

所以面试里如果你说“绝不重复”，通常会被继续追问。

## 四、幂等到底是什么

幂等指的是：

**同一条消息处理一次和处理多次，结果一致。**

例如给用户加积分：

- 第一次处理，积分 +10
- 第二次收到同一条消息，不再重复加

最终结果仍然只加一次。

## 五、常见幂等方案

### 1. 唯一业务键

例如支付流水号、订单号、消息唯一 ID。

通过数据库唯一索引保证“同一业务只落一次”。

### 2. 幂等表

消费前检查某个 `messageId` 是否已经处理过。

处理成功后记录：

```text
message_id -> processed
```

### 3. 状态机校验

只允许状态按合法方向流转。

例如订单：

- 待支付 -> 已支付
- 已支付 -> 已发货

如果已经是 `已支付`，再次执行支付消息就直接忽略。

### 4. 去重和业务更新放在同一事务里

这是很关键的一点。

如果你先记“已处理”，再改业务数据，中间失败就会造成假成功。

更稳的做法通常是：

1. 开事务
2. 校验消息是否处理过
3. 执行业务更新
4. 写入已处理记录
5. 提交事务

## 六、一个典型幂等消费示例

```ts
async function handleOrderPaid(event: OrderPaidEvent) {
  await db.transaction(async (tx) => {
    const processed = await tx.processedMessage.findUnique({
      where: { messageId: event.messageId },
    });

    if (processed) {
      return;
    }

    await tx.pointsAccount.update({
      where: { userId: event.userId },
      data: { balance: { increment: event.points } },
    });

    await tx.processedMessage.create({
      data: { messageId: event.messageId },
    });
  });
}
```

关键点不在代码，而在原则：

- 允许重复投递
- 不允许重复生效
- 去重记录和业务修改放在同一事务里

## 七、什么叫“精确一次”

很多面试会问 `Kafka exactly once`，这里要特别务实。

“精确一次”通常不是指：

**整个业务世界永远绝不重复。**

它更常表示：

- 在特定 MQ 系统能力内
- 在特定生产和消费模型下
- 减少重复写入或重复处理

但只要落到数据库、调用第三方服务、发券、扣余额这些外部动作，业务侧仍然需要幂等设计。

## 八、工程上更重要的结论

不要追求“重复永远不发生”，而要追求：

**重复发生时，系统仍然正确。**

这才是大多数 MQ 系统真正可落地的工程思路。
