# 00. 消息队列概念速览

这一篇只做一件事：先把消息队列最核心的概念装进脑子里。

## 一、消息队列是什么

消息队列可以理解成：

**生产者把消息放进去，消费者按约定把消息取出来处理。**

它通常位于两个系统之间：

```text
订单服务 -> MQ -> 积分服务
```

这样订单服务不需要同步等积分服务处理完成，主流程会更短。

## 二、消息队列最常解决什么问题

最常见是 4 类：

- 异步处理
- 系统解耦
- 削峰填谷
- 最终一致性

例如下单成功后，很多动作不一定要同步完成：

- 发短信
- 发积分
- 更新搜索索引
- 同步数据到分析系统

这些都可以异步做。

## 三、先记住哪些关键词

| 关键词 | 作用 |
|---|---|
| Producer | 生产消息 |
| Consumer | 消费消息 |
| Topic / Queue | 消息通道 |
| Partition | 分区，用于扩展吞吐和顺序控制 |
| Offset | 消费位置 |
| Ack | 消费确认 |
| Retry | 失败重试 |
| Dead Letter Queue | 多次失败后的死信队列 |

## 四、MQ 不是“用了就更高级”

很多人一学 MQ 就容易误判：

- 觉得异步一定更快
- 觉得解耦一定更简单
- 觉得 Kafka 一上就说明系统很高级

实际上用了 MQ 后，系统会多出新的复杂度：

- 消息可能重复
- 消息可能乱序
- 消息可能积压
- 链路排查更难
- 运维和监控成本更高

所以 MQ 解决的是一类问题，同时也引入另一类问题。

## 五、MQ 和同步调用的区别

同步调用：

```text
A -> B -> C -> 返回
```

特点：

- 主流程直观
- 调用结果立刻可见
- 下游慢会拖慢整个链路

异步消息：

```text
A -> MQ
     -> B 消费
     -> C 消费
```

特点：

- 主流程更轻
- 下游故障不一定直接打爆入口
- 短时间内状态可能不一致

## 六、常见产品大概怎么区分

先只建立非常粗的印象：

| 产品 | 粗略定位 |
|---|---|
| RabbitMQ | 传统消息队列，路由灵活 |
| Kafka | 高吞吐事件流平台 |
| RocketMQ | 兼顾业务消息、顺序、事务、延迟 |
| Redis Streams / BullMQ | 轻量队列方案 |

不要急着选型，先知道它们解决问题的侧重点不一样。

## 七、这一专题的主线

学习 MQ，建议一直抓住这条线：

**为什么发消息 -> 消息如何到达 -> 消费者如何处理 -> 失败如何重试 -> 重复如何去重 -> 状态如何最终一致**

如果这条线能打通，面试和工程实践里的大部分 MQ 问题都能落地。
