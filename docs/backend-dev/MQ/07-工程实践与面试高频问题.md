# 07. 工程实践与面试高频问题

前面几篇把主线拆开讲了，这一篇把它们重新串回真实工程。

## 一、一个更像真实项目的 MQ 链路

以“用户支付成功”举例：

```text
支付回调 -> 订单服务更新订单状态
         -> 写本地消息表
         -> 异步投递 OrderPaid
         -> 积分服务消费
         -> 通知服务消费
         -> 数据分析服务消费
```

如果把这个链路写成方案，你至少要回答 6 件事：

- 生产者发送失败怎么办
- 数据库和消息发送不一致怎么办
- 消费失败怎么办
- 重复消费怎么办
- 积压怎么办
- 怎么监控和重放

## 二、消费者代码要关注什么

一个更靠谱的消费者，通常至少会做这些事：

1. 做输入校验，避免脏消息污染系统。
2. 做幂等检查，避免重复处理。
3. 把核心业务更新和去重记录放在同一事务里。
4. 明确哪些异常可重试，哪些要进死信。
5. 埋点记录消息 ID、业务 ID、重试次数、耗时。

## 三、监控不只是看“有没有报错”

MQ 监控至少要有这些指标：

- 生产失败数
- 消费失败数
- 重试次数
- 死信数量
- 队列堆积长度
- 消费延迟
- 热点分区
- 单条消息处理耗时

如果没有这些指标，线上出问题时基本就是盲飞。

## 四、重放机制很重要

成熟一点的消息系统，通常要具备重放能力。

为什么要重放：

- 修复消费者 bug 后补处理历史消息
- 下游临时故障恢复后重新消费
- 对账发现少处理了一批消息

但重放前一定要先确认：

- 消费逻辑是否幂等
- 重放范围怎么圈定
- 是否会冲击下游系统

## 五、面试高频问法

### 1. 为什么用 MQ

重点答：

- 异步
- 解耦
- 削峰
- 最终一致性

同时补一句代价：

- 重复
- 积压
- 运维复杂

### 2. 如何保证消息不丢

重点答：

- 生产者确认
- Broker 持久化和副本
- 消费成功后再 Ack
- 重试和补偿

### 3. 如何避免重复消费

重点答：

- 业务幂等
- 唯一键
- 幂等表
- 状态机
- 事务内去重

### 4. 消息积压怎么办

重点答：

- 先定位瓶颈
- 扩容消费者
- 优化消费逻辑
- 调整分区
- 批处理
- 限流降级

### 5. 如何保证顺序消费

重点答：

- 同一业务主键路由到同一分区
- 控制消费并发
- 接受顺序和吞吐的权衡

## 六、给 TS / Node.js 后端开发者的建议

如果你是从前端或 Node.js 后端切过来，最容易忽略这几件事：

- 不要把 `BullMQ` 这类任务队列和通用 MQ 的语义完全混为一谈
- 不要只会写消费者函数，不会设计幂等表和重试策略
- 不要把异步处理理解成“丢个 job 就完了”，链路可观测性同样重要

## 七、最重要的收尾结论

MQ 不是为了让架构图更复杂，而是为了让系统在高峰、故障和跨服务协作下仍然可控。

真正拉开水平差距的，不是你会不会背 `Kafka`、`RabbitMQ`、`RocketMQ` 的定义，而是你能不能把下面这句话讲明白：

**消息如果重复、丢失、乱序、积压了，你的系统还能不能继续正确运行。**
