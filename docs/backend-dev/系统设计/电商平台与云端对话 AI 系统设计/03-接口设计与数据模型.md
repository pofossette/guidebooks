# 03. 接口设计与数据模型

这一章把接口和数据结构定到“能支撑恢复、幂等、异步回流”的粒度，而不是只停留在接口名。

## 对话接口

| 接口 | 作用 | 幂等要求 |
|---|---|---|
| `POST /api/chat/runs` | 创建 run | 必须带 `Idempotency-Key` |
| `GET /api/chat/runs/{runId}` | 查询 run 状态 | 读接口天然幂等 |
| `GET /api/chat/runs/{runId}/events` | SSE 订阅事件流 | 支持断线重连 |
| `POST /api/chat/runs/{runId}/cancel` | 取消运行中的 run | 重复取消返回当前状态 |

## 内部工具接口

| 接口 | 作用 | 同步性 |
|---|---|---|
| `POST /internal/tools/catalog/search` | 商品搜索 | 同步 |
| `POST /internal/tools/pricing/get` | 当前价格查询 | 同步 |
| `POST /internal/tools/inventory/get` | 库存快照查询 | 同步 |
| `POST /internal/tools/promotion/query` | 促销规则查询 | 同步或异步 |
| `POST /internal/tools/web-search/query` | 联网查询 | 异步优先 |

## 运行时对象

| 对象 | 作用 |
|---|---|
| `run` | 请求级聚合，统一承载状态、预算、owner、取消、超时 |
| `run_step` | ReAct loop 的一次检查点 |
| `tool_call` | 单次工具执行单元 |

## 推荐的消息信封

不管消息最后发到任务型 MQ 还是 Kafka，外面都包一层统一信封：

```json
{
  "event_id": "evt_123",
  "event_type": "tool_result_ready",
  "aggregate_type": "tool_call",
  "aggregate_id": "tc_456",
  "partition_key": "run_789",
  "schema_version": 3,
  "trace_id": "trace_abc",
  "occurred_at": "2026-06-11T12:00:00Z",
  "payload_inline": null,
  "payload_ref": "artifact://tool-results/tc_456/v3",
  "digest": "sha256:xxxx"
}
```

## 什么时候消息里直接带 payload

| 场景 | 做法 |
|---|---|
| 小 JSON，几十到几百字节 | 直接内联在消息里 |
| 工具原始响应很大 | 只放 `payload_ref` |
| 网页抓取原文、长回答附件 | 存 `tool_artifact`，消息只传指针 |
| 需要消费者二次校验 | 额外带 `digest` 和 `schema_version` |

## 为什么 pointer 不应该直接指向 Redis

- Redis 的 key 会过期，不适合作为恢复真相源。
- Redis 可能被淘汰或热 key 重建，无法保证结果稳定可审计。
- MQ 重放是分钟级甚至小时级行为，而 Redis 通常只适合短 TTL。
- 正确做法是：pointer 指向对象存储或持久表，Redis 只做加速缓存。

## 存储分层边界

| 存储 | 保存什么 | 不保存什么 |
|---|---|---|
| PostgreSQL | `run`、`run_step`、`tool_call`、幂等、状态机 | 大体积原始附件 |
| Redis | 幂等短键、lease、限流、SSE cursor、热点缓存 | 长期恢复数据 |
| Task MQ | `run_started`、`tool_call_dispatch`、`tool_result_ready` | 业务真相源 |
| Kafka | `price_changed`、`inventory_changed`、审计流、行为流 | 短时任务协调 |
| Object Storage | 长网页抓取原文、长模型输出、工具原始结果 | 高频小状态字段 |

## 数据所有权边界

聊天 Agent 可以读取商品、价格、库存和促销信息，但不能直接扣库存、改订单、发优惠券。所有有副作用的交易动作必须进入对应领域服务的主链路。
