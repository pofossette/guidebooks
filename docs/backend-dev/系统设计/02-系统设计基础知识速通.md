# 02. 系统设计基础知识速通

这篇会结合两个参考来源来写：

- `JavaGuide` 的系统设计知识主线
- `/home/wunai/Disks/Data/my-project/project-for-reference/system-design-primer` 里那种“按主题理解系统设计取舍”的组织方式

目标不是把你训练成“会背组件名词”的人，而是帮你建立两种能力：

1. 知道系统设计到底在看哪些知识块
2. 知道这些知识块之间到底怎么取舍

如果只记一句话，记这个：

**系统设计不是画图比赛，而是在约束条件下，对性能、可用性、一致性、复杂度和成本做取舍。**

## 一、系统设计到底在设计什么

很多人以为系统设计就是：

- 上 Redis
- 上 MQ
- 上分库分表
- 上微服务

这其实是结果，不是问题本身。

系统设计真正回答的是：

1. 这个系统要服务什么业务
2. 这个业务的核心链路是什么
3. 数据怎么存，状态怎么流转
4. 流量上来后哪里会慢
5. 某个点挂了后怎么不把全链路拖死
6. 规模继续增长时怎么演进

所以系统设计既不是纯编码问题，也不是纯运维问题，而是：

**业务 + 数据 + 并发 + 可靠性 + 工程治理** 的综合题。

## 二、系统设计先看什么：先看约束，不是先看技术

在 `system-design-primer` 里，一个很重要的思路是：

**先澄清 use case、约束和假设，再谈架构。**

这一步非常重要，因为不同约束会直接改变设计方案。

你至少要先问清楚这些：

### 1. 业务类型

- ToC 还是 ToB
- 核心是读多写少，还是写多读多
- 是交易系统、内容系统、搜索系统，还是 AI/Agent 系统

### 2. 规模

- 日活多少
- 峰值 QPS 多少
- 数据量多大
- 单条数据多大
- 增长速度怎样

### 3. 非功能目标

- 优先低延迟，还是优先高吞吐
- 优先强一致，还是优先高可用
- 容不容忍少量数据延迟
- 容不容忍部分功能降级

### 4. 资源约束

- 团队人力够不够
- 是否允许引入很多中间件
- 成本是不是敏感
- 首期是不是需要快速上线

很多错误方案，不是技术上错，而是：

**对约束没判断，直接上“看起来高级”的答案。**

## 三、系统设计的知识地图：最常见的九类问题

如果你想先建立地图，可以把系统设计拆成 9 类问题。

### 1. 功能问题

系统要支持哪些核心能力。

例如：

- 发帖、评论、点赞
- 下单、支付、退款
- 搜索、推荐、召回
- 上传、转码、下载

### 2. 数据问题

数据怎么建模、怎么存、怎么查。

例如：

- 用 SQL 还是 NoSQL
- 索引怎么建
- 分页怎么做
- 读写模式是什么

### 3. 性能问题

系统为什么会慢。

例如：

- 数据库查太慢
- 接口做了太多同步操作
- 热点太集中
- 下游依赖太慢

### 4. 可用性问题

某个节点挂了，系统为什么还能继续服务。

例如：

- 多实例
- 故障切换
- 冗余副本
- 超时和重试

### 5. 一致性问题

多个副本、多个服务、多次重试下，数据为什么不会乱。

例如：

- 事务
- 幂等
- 分布式锁
- 最终一致性

### 6. 扩展性问题

流量和数据量继续涨时，系统怎么扩。

例如：

- 水平扩展
- 读写分离
- 分库分表
- 服务拆分

### 7. 异步化问题

哪些操作不该阻塞主请求链路。

例如：

- 发消息
- 建索引
- 审核
- 报表
- embedding

### 8. 安全问题

谁能访问、谁能改、怎么审计、怎么防攻击。

例如：

- 认证
- 授权
- 数据脱敏
- 防刷与限流

### 9. 治理问题

系统出问题时，怎么知道、怎么排、怎么恢复。

例如：

- 日志
- 指标
- Trace
- 告警
- 灰度

## 四、系统设计里最核心的一组原则：所有方案都有取舍

`system-design-primer` 的骨架里有一个非常重要的点：

**每一种主题都不是“标准答案”，而是“某种 trade-off”。**

也就是：

- 你加缓存，读会更快，但一致性更复杂
- 你做复制，可用性会提高，但同步延迟会上来
- 你做分片，容量会上去，但查询和运维会更复杂
- 你拆微服务，边界更清晰，但治理成本会显著提高

所以系统设计不要问：

“这个技术是不是最好？”

而要问：

**“这个技术主要解决什么问题，又引入了什么新问题？”**

## 五、性能与扩展性：系统为什么会慢，怎么变大

### 1. 性能和扩展性不是一回事

很多人会把这两个词混起来。

更准确的理解是：

- 性能：当前系统处理一次请求有多快
- 扩展性：当负载持续增长时，系统还能不能继续撑住

一个系统可能单用户下很快，但高并发时变慢，这说明：

**性能局部不错，但扩展性不足。**

### 2. 延迟与吞吐量

这是 `system-design-primer` 里非常重要的一对概念。

- 延迟：一次操作从开始到结束花多久
- 吞吐量：单位时间内能处理多少请求或任务

通常目标不是单纯追求其中一个，而是：

**在可接受的延迟下，尽量提高吞吐。**

举例：

- 后台报表任务可以接受高延迟，但要高吞吐
- 用户点击“支付”通常要求低延迟，吞吐其次
- 视频转码可以走异步批处理，核心目标是总吞吐

### 3. 垂直扩展与水平扩展

#### 垂直扩展

直接把机器变强：

- 更多 CPU
- 更多内存
- 更快磁盘

优点：

- 简单
- 不改业务逻辑

缺点：

- 上限明显
- 成本增长快
- 单机仍可能是单点

#### 水平扩展

增加更多机器：

- 多实例应用
- 多个缓存节点
- 多个数据库副本

优点：

- 理论上更容易持续扩容
- 可用性通常更好

缺点：

- 复杂度上升
- 需要处理状态共享、路由、复制和一致性

一句话记忆：

**垂直扩展是在一台机器上挖潜，水平扩展是在多台机器间分摊。**

## 六、可用性与一致性：系统为什么不会一挂到底

### 1. 可用性是什么

可用性不是“绝对不出故障”，而是：

**当局部故障发生时，系统仍能尽量继续提供服务。**

常见手段：

- 多实例
- 故障切换
- 复制
- 限流
- 熔断
- 降级

### 2. 一致性是什么

一致性不是“数据库里永远没 bug”，而是：

**多个客户端、多个副本、多个服务看到的数据是否符合预期。**

例如：

- 写完后马上读，能不能读到最新值
- 两个副本的数据什么时候一致
- 一个流程跨多个系统时，状态怎么对齐

### 3. CAP 应该怎么理解

CAP 最有价值的地方，不是背定义，而是接受现实：

**网络分区一旦出现，分布式系统就必须在一致性和可用性之间做取舍。**

最常见的粗理解是：

- CP：优先一致性，必要时拒绝一部分请求
- AP：优先可用性，允许短时间读到旧数据

注意：

工程上不是天天在选 CAP 题，而是在做现实取舍。

例如：

- 账户扣款更偏向一致性
- Feed、评论数、点赞数更容易接受最终一致性
- 配置中心、选主元数据往往更偏一致性

### 4. 一致性模式

这也是 `system-design-primer` 的核心知识块之一。

#### 弱一致性

写完之后，读不一定马上看到。

适合：

- 音视频实时场景
- 实时协作中的部分非核心状态

#### 最终一致性

写完不是立刻可见，但过一段时间会同步过去。

适合：

- 缓存刷新
- 搜索索引更新
- 通知、埋点、统计
- 大量异步链路

#### 强一致性

写完之后，后续读立刻看到最新结果。

适合：

- 支付
- 库存
- 账户余额
- 核心交易状态

一句话记忆：

**系统设计里不是所有数据都必须强一致，关键是先分清哪些必须强一致。**

## 七、系统设计里最常见的基础组件，到底各自解决什么

### 1. DNS

DNS 负责把域名映射到 IP。

在系统设计里，它常常跟这些话题一起出现：

- 多机房流量路由
- 地域就近访问
- 灰度或权重切流
- TTL 与缓存传播延迟

你不一定要讲很深，但要知道：

**用户先找到你的入口，系统设计才有后面的事。**

### 2. CDN

CDN 主要解决：

- 静态资源就近分发
- 减少源站带宽和请求压力
- 降低跨地域访问延迟

适合：

- 图片
- 视频
- JS/CSS
- 下载文件

限制：

- 内容更新有缓存延迟
- 动态业务数据不一定适合

### 3. 负载均衡

负载均衡负责把请求分发到后端实例。

它主要解决：

- 避免单机过载
- 支持多实例扩容
- 提升可用性

常见补充点：

- 四层负载均衡更偏连接转发
- 七层负载均衡能按 HTTP 层信息做更灵活路由
- 负载均衡自己也不能成为单点

### 4. 反向代理 / 网关

这层常用来做：

- 统一入口
- 鉴权
- 限流
- 路由
- TLS 终结
- 静态资源分发
- 黑白名单

它是“外部请求进入系统”的第一道工程治理层。

### 5. 应用服务

应用服务承接业务逻辑。

主要做：

- 参数校验
- 业务编排
- 调数据库、缓存、队列、搜索和第三方服务
- 处理同步和异步边界

### 6. 数据库

数据库负责核心业务状态。

系统设计里最关键的数据库问题不是“你会不会 SQL”，而是：

- 数据模型怎么设计
- 索引怎么匹配查询
- 事务边界怎么划
- 容量上来后怎么扩

### 7. 缓存

缓存主要解决：

- 高频读
- 热点访问
- 降低主库压力
- 降低延迟

但缓存一定带来这些问题：

- 缓存更新时机
- 缓存一致性
- 热点 key
- 穿透、击穿、雪崩

### 8. 消息队列

消息队列主要解决：

- 解耦
- 异步
- 削峰
- 补偿

它并不神奇，仍然会带来：

- 重复消费
- 积压
- 顺序问题
- 死信
- 监控复杂度

### 9. 搜索系统

搜索系统主要解决：

- 全文检索
- 复杂筛选
- 相关性排序
- 高亮与倒排索引

如果你需要复杂检索，就不该只盯数据库。

## 八、数据库设计是系统设计的中轴线

很多系统设计回答最大的问题是：

**只讲组件，不讲数据。**

这会让答案非常虚。

你至少要讲清三件事：

### 1. 核心实体

有哪些关键表或对象。

例如：

- `users`
- `orders`
- `payments`
- `jobs`
- `messages`

### 2. 关键关系

它们怎么关联：

- 一对一
- 一对多
- 多对多

### 3. 关键查询模式

到底常查什么：

- 按用户查订单
- 按时间倒序查消息
- 按状态查任务
- 按关键词搜索内容

因为查询模式会反过来决定：

- 索引
- 分区
- 缓存
- 冗余字段
- 是否引入搜索系统

## 九、SQL 还是 NoSQL：不要用“信仰”，要用数据形态和访问模式判断

`system-design-primer` 对这一块的启发很直接：

**先看数据和访问模式，再选存储。**

### 1. 更适合 SQL 的场景

- 结构化数据
- 关系清晰
- 事务要求高
- 需要复杂查询和联结
- 模式相对稳定

### 2. 更适合 NoSQL 的场景

- 半结构化或动态字段
- 海量日志、埋点、时序数据
- 超大吞吐量
- 允许最终一致
- 不依赖复杂联结

### 3. 真正工程里的答案通常不是二选一

很多系统其实是：

- 主数据在 PostgreSQL / MySQL
- 热点状态在 Redis
- 检索在 Elasticsearch
- 文档在 MongoDB 或对象存储

所以系统设计更真实的表达不是“选哪个”，而是：

**什么数据放在哪一层最合适。**

## 十、复制、读写分离、分库分表、分片：它们不是同一个层面的事

这一组概念最容易混。

### 1. 复制

复制主要解决：

- 高可用
- 读扩展
- 冗余备份

常见模式：

- 主从复制
- 多主复制

问题：

- 复制延迟
- 故障切换复杂
- 副本可能读到旧数据

### 2. 读写分离

读写分离通常建立在复制上。

核心思路：

- 写请求走主库
- 读请求走从库

适合：

- 读远多于写

问题：

- 主从延迟导致读到旧数据
- 某些强一致读仍然要回主库

### 3. 分库分表 / 联合

更偏按业务边界拆数据。

例如：

- 用户库
- 订单库
- 商品库

主要解决：

- 单库职责过重
- 团队边界和业务边界不清

### 4. 分片

更偏按同一类数据的规模做横向切分。

例如：

- 用户按 `user_id` hash
- 订单按商家或时间分片

主要解决：

- 单机容量不够
- 单表过大
- 吞吐受限

问题：

- 路由复杂
- 热点倾斜
- 跨分片查询和事务复杂

一句话记忆：

**复制主要为可用和读扩展，分片主要为容量和写扩展。**

## 十一、缓存策略是系统设计高频考点

不要只说“加 Redis”，要说清楚怎么加。

### 1. 为什么要缓存

- 降低数据库压力
- 降低响应延迟
- 扛住热点流量

### 2. 缓存放在哪

- 客户端缓存
- CDN 缓存
- 反向代理缓存
- 应用缓存
- 数据库自身缓存

### 3. 常见缓存更新思路

#### Cache Aside

应用先读缓存，没命中再查库，再回填缓存。

优点：

- 简单
- 只缓存真正被访问的数据

缺点：

- 第一次 miss 慢
- 容易有短暂不一致

#### Write Through

写缓存时同步写数据库。

优点：

- 一致性更直接

缺点：

- 写链路更重

#### Write Back

先写缓存，后异步刷库。

优点：

- 写吞吐高

缺点：

- 故障恢复和可靠性复杂

### 4. 缓存设计最该会的不是命令，而是故障模式

至少要会讲：

- 缓存穿透
- 缓存击穿
- 缓存雪崩
- 热点 key
- TTL 怎么设
- 删除缓存和写库的顺序

## 十二、异步化：为什么很多操作不能放在主请求里

这是 `system-design-primer` 和实际工程都非常重视的一点。

主请求链路应该尽量只做核心同步动作。

下面这些事通常更适合异步：

- 发送通知
- 生成报表
- 大文件处理
- 搜索索引更新
- 推荐计算
- embedding / 数据清洗

### 异步的收益

- 缩短主请求延迟
- 提高吞吐
- 削峰填谷
- 解耦上下游

### 异步的代价

- 状态变复杂
- 调试更难
- 一致性变成最终一致
- 失败补偿必须设计

### 背压为什么重要

当下游处理不过来时，系统不能无止境堆任务。

所以你要考虑：

- 队列积压
- 消费速率
- 并发 worker 上限
- 重试风暴
- 熔断和拒绝策略

## 十三、通信方式：REST、RPC、消息，不是互斥关系

### 1. REST

更适合：

- 对外 API
- 资源式接口
- 浏览器 / 第三方接入

优点：

- 通用
- 可读性强

### 2. RPC

更适合：

- 内部服务间调用
- 追求更明确的接口约束和更高效率

优点：

- 接口契约更清晰
- 序列化与调用成本通常更可控

### 3. 消息

更适合：

- 异步场景
- 解耦
- 事件驱动

真正工程里经常是组合使用：

- 对外 REST
- 内部 RPC
- 旁路异步走 MQ

## 十四、安全不是附加题，而是系统设计的必答题

很多人讲系统设计只讲吞吐和缓存，这是不完整的。

至少要覆盖：

### 1. 认证

你是谁。

例如：

- Session
- JWT
- OAuth2
- OIDC

### 2. 授权

你能干什么。

例如：

- RBAC
- ABAC

### 3. 数据保护

- 敏感字段加密
- 脱敏展示
- 密钥管理
- 传输加密

### 4. 防滥用

- 限流
- 防刷
- 幂等
- 验签
- 防重放

### 5. 审计

谁在什么时候做了什么，后续能不能追到。

## 十五、可观测性：系统上线后怎么知道自己活得怎么样

系统设计只讲“怎么搭”还不够，还要讲“怎么观测”。

至少包括三类：

### 1. 日志

看离散事件和错误现场。

### 2. 指标

看趋势和告警。

例如：

- QPS
- 延迟分位数
- 错误率
- 缓存命中率
- 队列积压

### 3. Trace

看一次请求跨多个服务的完整链路。

一句话记忆：

**没有可观测性，就没有真正的可维护系统。**

## 十六、系统设计回答里最常见的基本原则

这一部分最适合背成自己的“答题价值观”。

### 1. 先主链路，后扩展点

先讲最核心请求怎么走，再讲缓存、队列、搜索、分片。

### 2. 先数据模型，后中间件选型

数据结构和查询模式没讲清，中间件选型就是空中楼阁。

### 3. 先最小可行架构，后规模化演进

不要一开始就默认上最复杂方案。

### 4. 优先解决当前瓶颈，不提前优化不存在的问题

没有流量就别先讲分库分表，没有复杂检索就别先上 ES。

### 5. 把同步链路做短，把非核心动作异步化

主流程越短，延迟和故障面通常越可控。

### 6. 对关键数据保守，对非关键副作用灵活

核心交易尽量强一致，通知、埋点、索引同步可走最终一致。

### 7. 设计时同时考虑正常流程和失败流程

不仅要讲“成功时怎么走”，还要讲：

- 超时怎么办
- 重试怎么办
- 重复提交怎么办
- 下游挂了怎么办

### 8. 尽量消灭单点

单点可能出现在：

- 单实例服务
- 单负载均衡
- 单主库
- 单 Redis
- 单机房

### 9. 能无状态就无状态

应用无状态，水平扩展会容易很多。

### 10. 每引入一个组件，都要说明它的收益和代价

这是区分“背稿”与“会设计”的关键。

## 十七、初学者最容易犯的错误

### 1. 把系统设计理解成中间件堆砌

### 2. 一上来就讲微服务和分库分表

### 3. 不讲数据模型，只讲架构图

### 4. 不讲读写比例、QPS、数据量这些约束

### 5. 不讲失败路径，只讲正常流程

### 6. 不讲一致性和幂等

### 7. 不讲安全和可观测性

### 8. 不讲演进路线，默认一步到位

## 十八、一个适合复述的系统设计总串讲

“系统设计本质上是在约束条件下，为业务设计一条可落地、可扩展、可恢复的请求和数据链路。第一步不是堆技术，而是先明确 use case、规模、读写比例、延迟目标、一致性要求和成本约束。然后围绕核心请求链路去设计入口、应用服务、数据库、缓存、消息队列和搜索等组件。性能上要区分延迟和吞吐，扩展上要区分垂直扩展和水平扩展；可靠性上要理解复制、故障切换、限流、熔断和降级；分布式场景下要理解 CAP、强一致和最终一致的取舍。数据库设计、查询模式和缓存策略是中轴线，异步化和队列用来缩短主链路并削峰，安全和可观测性则保证系统能被控制、被审计、被排障。最终系统设计不是追求最复杂方案，而是先做当前阶段最合理的方案，并给出清晰的演进路径。” 

## 这篇最重要的结论

系统设计基础知识集合，真正可以压缩成三句话：

1. 先看约束，再谈架构。
2. 先讲主链路和数据模型，再讲缓存、队列、分片和微服务。
3. 每个方案都有代价，系统设计的核心能力就是说明白“为什么这样取舍”。
