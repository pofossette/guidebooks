# 05. 限流、CORS 与安全头

这类能力经常被认为是“装个插件就完了”，但真正上线时仍然需要知道它们在解决什么问题。

## 一、限流是在保护什么

限流本质上是在保护系统资源：

- 连接数
- CPU
- 下游数据库
- 模型配额
- 第三方 API 调用额度

所以限流不是只为了防攻击，也是在防自己被正常流量打穿。

## 二、限流的常见粒度

- 按 IP
- 按用户
- 按租户
- 按接口
- 按时间窗口

如果系统是多租户或按账号计费，按用户/租户限流往往比单纯按 IP 更实用。

## 三、CORS 到底在解决什么

`CORS` 不是后端权限系统，而是浏览器跨域访问策略的一部分。

它主要回答：

- 哪些源可以访问我
- 哪些方法和头允许带过来
- 是否允许携带凭证

所以不要把 `CORS` 配置正确，误以为等于“接口安全了”。

## 四、安全头在做什么

常见安全头处理通常包括：

- 限制某些资源加载方式
- 降低点击劫持风险
- 控制浏览器安全策略

这类能力在 `Fastify` 里通常更适合用官方生态插件，而不是自己手动拼头。

## 五、为什么这些逻辑适合插件化

因为它们通常具备这些特点：

- 跨很多路由共用
- 配置项较集中
- 更偏基础设施能力
- 很少直接依赖具体业务状态

所以非常适合做成独立插件，在 `buildServer()` 时统一注册。

## 六、不要忽略顺序问题

例如：

- 限流过晚，业务已经做完才拒绝
- CORS 头设置不完整，浏览器预检先失败
- 错误响应没带上该有的头，前端排障更麻烦

这些都属于“能力有了，但放错阶段”。

## 七、面向 Node / Fastify 的务实建议

- 限流策略按用户、租户、接口分别设计，不要只有一个全局阈值。
- `CORS` 只放开明确需要的源、方法和头，不要默认全开。
- 安全头优先用成熟插件，不要到处手写魔法字符串。

## 八、这篇最重要的结论

限流、CORS 和安全头看起来像“配置题”，本质上还是中间件层的系统保护能力。
