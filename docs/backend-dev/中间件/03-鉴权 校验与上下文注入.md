# 03. 鉴权、校验与上下文注入

后端里最常见的中间件类需求，基本都集中在这三件事：

- 你是谁
- 你能不能做
- 后续代码怎样拿到你的上下文

## 一、一个典型链路

```mermaid
flowchart LR
    A[Request] --> B[parse token]
    B --> C[load user / tenant]
    C --> D[permission check]
    D --> E[validate input]
    E --> F[handler]
```

## 二、鉴权不要只理解成“校验 JWT”

鉴权通常至少拆成两层：

### 1. 认证 Authentication

回答：

- 这个请求是谁发的
- token 是否有效
- session 是否存在

### 2. 授权 Authorization

回答：

- 这个用户有没有权限访问这个资源
- 能不能执行这个动作

很多系统把这两件事写成一坨，后面会越来越难维护。

## 三、在 Fastify 里常见怎么放

常见做法是：

- 在 `onRequest` 或 `preHandler` 里解析 token
- 用 `decorate` 给 `request` 挂上 `currentUser`
- 在更靠近具体路由的位置做权限判断

这样分层的好处是：

- 基础身份解析可复用
- 具体权限规则不必全局耦合

## 四、输入校验不要晚于业务层

参数校验的目标不是“防手滑”，而是保护系统边界。

至少要防：

- 字段缺失
- 类型错误
- 非法枚举值
- 超长字符串
- 越界分页参数

在 `Fastify` 语境里，应该尽量让：

**通过校验的数据再进入 handler / service。**

## 五、上下文注入为什么重要

很多业务逻辑都需要拿到请求上下文：

- 当前用户
- 当前租户
- 当前追踪 ID
- 当前权限集合

如果这些信息每层都手动传，代码会很碎。

所以常见做法是用 `decorate` 或类型扩展，把它们稳定挂到请求对象或服务上下文上。

## 六、TypeScript 在这里的价值

如果你用了 `TypeScript`，就不要只在运行时挂值，不补类型。

坏味道是：

- 运行时有 `request.currentUser`
- 类型系统里却还是 `any`

这样后面所有中间件和 handler 都会失去类型保护。

## 七、一个务实建议

把这几类逻辑分开：

- 身份解析：谁来了
- 权限判断：能不能做
- 参数校验：带的数据对不对
- 业务校验：当前状态允不允许

不要用一个“万能中间件”全包。

## 八、这篇最重要的结论

鉴权、校验和上下文注入看起来都像“前置逻辑”，但它们职责不同。

分清边界，后面代码才不会变成只能靠复制粘贴维持的请求流水线。
