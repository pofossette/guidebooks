# 07. 锁、并发与队列模式

事务解决“这组操作要不要一起成功”，锁解决“并发事务彼此怎么协调”。

## 一、为什么并发下会出错

因为两个请求可能同时读到旧状态，然后各自按自己的理解去更新。

典型例子：

- 库存超卖
- 配额扣重
- 任务被多个 worker 同时领取

这些都不是语法问题，而是并发控制问题。

## 二、先区分几类常见锁

### 1. 行级锁

最常用。适合锁定某一行，避免并发修改冲突。

### 2. 表级锁

范围更大，日常业务开发里要谨慎使用。

### 3. 顾问锁

适合把某种业务资源抽象成锁键，但要非常清楚使用边界。

## 三、最常见的加锁方式

### 1. `FOR UPDATE`

```sql
SELECT *
FROM quotas
WHERE user_id = $1
FOR UPDATE;
```

它会锁住查到的行，适合先读再改的强一致场景。

### 2. `FOR UPDATE SKIP LOCKED`

```sql
SELECT id
FROM jobs
WHERE status = 'pending'
ORDER BY created_at
FOR UPDATE SKIP LOCKED
LIMIT 1;
```

这是 PostgreSQL 里做轻量任务队列的经典模式。

含义是：

- 选一条待处理任务
- 如果已经被别的 worker 锁住，就跳过
- 避免多人抢同一条任务

## 四、乐观锁和悲观锁怎么选

### 1. 悲观锁

就是先锁起来再改。

适合：

- 冲突频繁
- 正确性要求高
- 失败重试成本高

### 2. 乐观锁

常见做法是 `version` 字段或条件更新。

```sql
UPDATE quotas
SET remaining = remaining - 10,
    version = version + 1
WHERE user_id = $1
  AND version = $2;
```

适合：

- 冲突不算太高
- 希望减少持锁时间
- 可以接受更新失败后重试

## 五、死锁为什么会发生

典型场景是两个事务拿锁顺序相反。

比如：

- 事务 A 先锁用户，再锁订单
- 事务 B 先锁订单，再锁用户

结果双方互等。

减少死锁最常见的办法：

- 固定资源加锁顺序
- 缩短事务时间
- 减少一次事务里涉及的热点资源

## 六、任务队列为什么是 PG 的典型应用

很多中小系统不想一开始就引入 MQ，也不想先上复杂调度系统。

这时常见做法就是：

1. `jobs` 表保存待执行任务
2. worker 用 `FOR UPDATE SKIP LOCKED` 领取
3. 领取后更新状态为 `running`
4. 完成后标为 `done` 或 `failed`

它的优点是简单、事务一致、易于落地。
它的边界是吞吐和复杂调度能力有限。

## 七、并发控制排查时先看什么

1. 是否有热点行被频繁更新？
2. 是否存在长事务不释放锁？
3. 是否多个流程在抢同一批任务？
4. 是否锁顺序不一致导致死锁？

## 这篇最重要的结论

并发控制不是“数据库自己会处理好”的黑魔法。你需要主动设计锁粒度、事务边界和冲突策略，尤其是额度、库存、任务领取这类共享资源场景。
