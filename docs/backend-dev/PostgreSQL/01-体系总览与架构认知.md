# 01. 体系总览与架构认知

学 PostgreSQL，第一步不是背命令，而是先知道数据库内部大致有哪些模块。

## 一、一条 SQL 是怎么跑起来的

你发出一条 SQL 后，PostgreSQL 不是直接去读表，它大致会经过这些阶段：

```mermaid
flowchart LR
    A[客户端发 SQL] --> B[Parser 解析]
    B --> C[Analyzer 语义分析]
    C --> D[Rewriter 查询重写]
    D --> E[Planner 优化器]
    E --> F[Executor 执行器]
    F --> G[Buffer Cache / 磁盘]
    G --> H[返回结果]
```

你先不用把每个模块背透，但要建立一个意识：

**数据库的性能和行为，不只是“表里有没有数据”，而是整条执行链共同决定的。**

## 二、PostgreSQL 内部可以粗分成哪几层

### 1. SQL 处理层

负责：

- 解析 SQL
- 检查对象和字段是否合法
- 生成执行计划

### 2. 执行与存储访问层

负责：

- 真正执行扫描、排序、连接、聚合
- 从共享缓冲区或磁盘读取数据页

### 3. 事务与并发控制层

负责：

- 事务提交和回滚
- 快照隔离
- 锁管理
- 可见性判断

### 4. 日志与恢复层

负责：

- 写入 WAL
- 崩溃恢复
- 主从复制基础

## 三、理解 PostgreSQL 时最值得先建立的三组概念

### 1. 表、页、行

从业务角度看你在操作表和行，但从数据库内部看，它最终是在读写数据页。

所以你经常会看到这些说法：

- 顺序扫描很多页
- 命中缓冲区
- 页面膨胀

### 2. 逻辑 SQL 和物理执行

你写的是：

```sql
SELECT * FROM orders WHERE user_id = 1;
```

但数据库实际可能执行的是：

- 顺序扫描
- 索引扫描
- 位图扫描

这就是逻辑查询和物理执行的区别。

### 3. 一致性和性能

数据库不是只追求快，还要保证：

- 数据不乱
- 事务正确
- 崩溃后能恢复

很多“为什么数据库要这么复杂”的答案，都和这三点有关。

## 四、为什么 PostgreSQL 特别强调 MVCC 和 WAL

如果只从工程上记：

- `MVCC` 解决读写并发下的可见性问题
- `WAL` 解决崩溃恢复和复制基础问题

你后面学事务和可靠性时，会不断看到这两个概念。

## 五、从后端开发视角，该怎么理解 PG 的模块分工

可以把它粗暴类比成一个后端服务：

| PostgreSQL 模块 | 你可以先类比成什么 |
|---|---|
| Parser / Planner | 请求解析和路由决策 |
| Executor | 真正执行业务逻辑 |
| Buffer Cache | 高频热数据缓存 |
| WAL | 变更日志和恢复依据 |
| Lock / MVCC | 并发控制系统 |

类比不是完全准确，但很利于入门。

## 六、初学者先建立哪些排障问题意识

以后你遇到慢 SQL 或数据异常，先问自己：

1. 是 SQL 写法问题，还是索引问题？
2. 是执行计划选错了，还是数据量本身过大？
3. 是事务并发问题，还是代码逻辑问题？
4. 是磁盘 IO、缓存命中率、WAL 压力还是锁冲突？

这比只会问“为什么查得慢”更有效。

## 这篇最重要的结论

PostgreSQL 不是一个黑盒。只要你把 SQL 处理、执行存储、事务并发、日志恢复这四层分开看，后面的很多知识点就不会混在一起。
