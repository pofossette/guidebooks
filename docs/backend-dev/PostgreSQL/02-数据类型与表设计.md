# 02. 数据类型与表设计

很多数据库问题，根子不在 SQL，而在表设计阶段。

## 一、表设计为什么是第一优先级

因为表一旦上线：

- 字段类型很难随便改
- 主键方案会影响整个系统
- 索引和查询模式会跟着它走
- 坏设计会把业务逻辑逼得越来越绕

所以表设计不是“建个表就行”，而是业务建模。

## 二、PostgreSQL 常用数据类型怎么选

### 1. 数值

- `smallint`：范围很小才用
- `integer`：普通整数默认首选
- `bigint`：订单号、雪花 ID、计数器更常见
- `numeric`：金额、精度要求高的值

不要用浮点数保存金额。

### 2. 字符串

- `text`：最常用，简单直接
- `varchar(n)`：只在你明确需要长度约束时使用

很多项目在 PG 里更倾向直接用 `text`，把校验放在应用层或约束里。

### 3. 时间

- `timestamp with time zone`：更推荐
- `timestamp without time zone`：要非常清楚业务边界再用

工程里常见字段：

- `created_at`
- `updated_at`
- `deleted_at`

### 4. 标识

- 自增：`generated ... as identity`
- 分布式标识：`uuid`

如果系统会跨服务写入、日志追踪、离线导入导出，`uuid` 通常更稳。

### 5. 半结构化数据

- `jsonb`

适合：

- 可变元数据
- 工具调用输入输出
- 不稳定但需要保留的附加字段

不适合：

- 高频过滤的核心业务字段
- 强关系查询主链路

## 三、主键怎么选

### 1. 自增主键

优点：

- 简单
- 索引局部性好
- 便于调试

问题：

- 跨服务不方便
- 暴露递增趋势

### 2. UUID 主键

优点：

- 天然全局唯一
- 更适合分布式系统和外部暴露

问题：

- 更长
- 索引和存储成本更高

如果你是业务后台项目，可以先按这个经验判断：

- 单体后台、内部系统：自增或 `identity`
- 面向外部接口、事件流、Agent 运行日志：`uuid` 更常见

## 四、约束一定要尽量落数据库

不要把所有正确性都留给应用代码。

优先考虑这些约束：

- `NOT NULL`
- `UNIQUE`
- `CHECK`
- `FOREIGN KEY`

例如邮箱、用户名、外部唯一业务号，都应该认真考虑唯一约束。

## 五、一个通用业务表可以怎么设计

```sql
CREATE TABLE users (
  id uuid PRIMARY KEY,
  email text NOT NULL UNIQUE,
  nickname text NOT NULL,
  status text NOT NULL,
  profile jsonb NOT NULL DEFAULT '{}'::jsonb,
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now()
);
```

这里有几个关键点：

- 主键清晰
- 唯一性落库
- 时间字段统一
- `jsonb` 只装附加信息

## 六、表设计时最容易忽略的点

### 1. 状态字段

状态值不要乱写，最好收敛成有限集合。

### 2. 软删除

如果用了 `deleted_at`，你要同步考虑：

- 查询默认是否过滤
- 唯一索引是否受影响
- 归档策略怎么做

### 3. 审计字段

很多表不只需要时间，还需要：

- `created_by`
- `updated_by`

### 4. 版本字段

如果后面会做乐观锁，可以预留 `version`。

## 七、Agent 或现代后端项目里常见的 PG 表设计模式

- 主表放强结构化字段
- 扩展字段放 `jsonb`
- 时间线表按 `(业务 ID, created_at)` 查询
- 状态机表会有 `status + retry_count + next_run_at`
- 检索类表会把原文、metadata、embedding 分开建模

## 八、表设计检查清单

建表前至少过一遍：

1. 主键为什么这样选？
2. 哪些字段必须唯一？
3. 哪些字段未来一定会拿来筛选？
4. 是否需要时间排序？
5. `jsonb` 放的是附加信息还是偷懒塞一切？
6. 并发更新时需不需要版本字段？

## 这篇最重要的结论

好的表设计是在替未来的 SQL、索引、事务和排障减负。坏表设计会让后面每一层都被迫补锅。
