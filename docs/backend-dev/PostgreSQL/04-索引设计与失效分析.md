# 04. 索引设计与失效分析

索引是数据库学习的第一道坎，也是最容易产生“我明明建了索引，为什么还是慢”的地方。

## 一、索引到底在解决什么问题

本质上是在减少数据库为了找到目标数据而扫描的范围。

没有索引时，数据库更容易走全表扫描。
有合适索引时，数据库可以更快定位候选数据页和行。

## 二、PostgreSQL 先学哪几类索引

### 1. B-Tree

默认、最常见，适合：

- 等值查询
- 范围查询
- 排序

### 2. 联合索引

适合同时按多个字段过滤或过滤加排序。

典型例子：

```sql
CREATE INDEX idx_messages_conversation_created_at
ON messages (conversation_id, created_at DESC);
```

### 3. GIN

适合：

- `jsonb`
- 全文检索
- 数组

### 4. BRIN

适合大体量、按时间顺序追加的表。

比如日志、事件、监控类表。

## 三、索引设计先围绕查询模式

不要先问“我要建什么索引”，而是先问：

1. 最常查什么条件？
2. 是等值查，还是范围查？
3. 要不要排序？
4. 返回量通常多大？

索引是给查询路径服务的，不是给表“做装饰”的。

## 四、联合索引最容易踩的坑

最典型的问题是字段顺序。

例如索引：

```sql
(conversation_id, created_at)
```

更擅长这类查询：

```sql
WHERE conversation_id = $1
ORDER BY created_at DESC
```

但如果你高频查询是：

```sql
WHERE created_at > $1
```

那这个索引帮助就有限。

所以联合索引不是“字段越多越好”，而是顺序必须贴着真实查询路径。

## 五、为什么索引会失效或效果不明显

### 1. 返回行数太多

如果命中过多行，优化器可能觉得全表扫更划算。

### 2. 条件写法不利于索引

比如对索引列做复杂函数处理，可能让普通索引用不上。

### 3. 统计信息不准

优化器判断依赖统计信息，如果统计失真，计划也可能选错。

### 4. 排序和过滤没对上

你建了索引，但 SQL 的过滤顺序、排序字段和索引结构不匹配。

## 六、PostgreSQL 很有特色的几个索引玩法

### 1. 部分索引

```sql
CREATE INDEX idx_jobs_pending
ON jobs (created_at)
WHERE status = 'pending';
```

适合热点子集很明显的场景。

### 2. 表达式索引

```sql
CREATE INDEX idx_users_lower_email
ON users ((lower(email)));
```

适合查询里固定会对字段做某种表达式处理的情况。

### 3. `jsonb` 的 GIN 索引

如果你经常按元数据字段检索，这类索引会很有用，但也要注意写入成本。

## 七、索引不是越多越好

每多一个索引，都意味着：

- 写入更慢
- 更新和删除成本更高
- 占更多存储
- 维护和排障更复杂

所以索引的正确思路是：

**围绕高频关键路径做最小够用设计。**

## 八、索引设计检查清单

1. 这条索引对应哪类高频查询？
2. 过滤字段和排序字段顺序对吗？
3. 写入成本能接受吗？
4. 是否可以用部分索引减少体积？
5. 是否需要 GIN / BRIN 这类非默认索引？

## 这篇最重要的结论

索引优化不是背定义，而是把真实查询模式翻译成合适的索引结构。离开查询路径谈索引，基本都会偏。
