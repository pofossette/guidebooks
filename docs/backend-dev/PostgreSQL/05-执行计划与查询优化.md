# 05. 执行计划与查询优化

会写 SQL 只是第一步。会看执行计划，才算真正进入数据库优化。

## 一、为什么一定要看执行计划

因为你以为数据库会怎么执行，和它实际怎么执行，经常不是一回事。

你写的是一条 SQL，但数据库最终会决定：

- 走不走索引
- 用哪种扫描方式
- 用什么 join 策略
- 是否需要排序、哈希或物化

## 二、最常用的两个工具

### 1. `EXPLAIN`

看预估执行计划。

### 2. `EXPLAIN ANALYZE`

看真实执行过程和实际耗时。

排查时更常用：

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...
```

它除了时间，还能帮助你看缓存和磁盘读写情况。

## 三、先读懂哪些节点

### 1. `Seq Scan`

顺序扫描整张表或大范围数据。

不代表一定错误，但如果是小结果集查询却走了它，通常要警惕。

### 2. `Index Scan`

沿索引查找并回表拿数据。

### 3. `Bitmap Index Scan` / `Bitmap Heap Scan`

常见于命中多行但还没大到完全全表扫的情况。

### 4. `Nested Loop`

小结果集联表时很常见。

### 5. `Hash Join`

中大型联表很常见，尤其其中一侧可以先构建哈希表时。

### 6. `Sort`

如果排序代价很大，要反推是不是可以借助索引减少额外排序。

## 四、执行计划要重点看什么

### 1. 预估行数和实际行数差距大不大

差距很大，通常说明统计信息或数据分布判断出了问题。

### 2. 扫描行数是不是太多

即使最终只返回几条结果，也可能为了找它们扫了几十万行。

### 3. 最重的节点在哪里

不要平均看每个节点，先抓最耗时、最耗 IO 的部分。

### 4. 排序、聚合、连接是不是主要瓶颈

很多慢 SQL 不是慢在过滤，而是慢在 join 和 sort。

## 五、一个常见的慢 SQL 排查顺序

1. 先确认业务上是否真的需要这么查。
2. 看执行计划有没有走错扫描方式。
3. 看索引是否缺失或设计不匹配。
4. 看过滤条件是否过宽，导致返回候选集太大。
5. 看 join、sort、aggregate 哪个节点最贵。

## 六、优化 SQL 时不要只盯着“加索引”

很多时候更有效的优化是：

- 减少返回列
- 先缩小数据集再联表
- 把深分页改成游标分页
- 避免无意义排序
- 拆掉过度复杂的一条大 SQL

## 七、后端开发者最该建立的执行计划直觉

看到一条查询时，你应该能先猜：

- 大概率走什么索引
- 会不会排序
- 会不会扫很多无效行
- 哪个 join 可能最贵

然后再用 `EXPLAIN ANALYZE` 去验证，而不是完全靠猜。

## 这篇最重要的结论

查询优化的核心，不是死背节点定义，而是建立“SQL 写法 -> 执行计划 -> IO 与 CPU 成本”之间的因果关系。
