# 08. WAL、Checkpoint 与可靠性

很多人会用 PostgreSQL，但一问“数据库宕机后为什么能恢复”，就开始模糊。这一篇补的就是这个底层认知。

## 一、WAL 是什么

WAL 是 `Write-Ahead Logging`，中文常叫预写日志。

核心思想是：

**先把变更记录进日志，再把真正的数据页慢慢刷到磁盘。**

这样做的好处是：

- 崩溃恢复有依据
- 顺序写日志通常比随机写数据页更高效
- 复制也能基于日志推进

## 二、为什么不能只写数据页

如果数据库直接改内存页，再随机刷盘，宕机时可能出现：

- 数据页只写了一半
- 多个页之间状态不一致
- 无法知道哪些修改已经真正落盘

WAL 的意义就是让恢复过程有一条可靠“账本”。

## 三、Checkpoint 在干什么

Checkpoint 可以先理解成：

**把某个时间点之前的重要脏页和日志状态推进到一个更稳定的位置。**

它的作用包括：

- 降低崩溃恢复时需要重放的日志量
- 控制内存脏页向磁盘刷写的节奏

但 checkpoint 太频繁也会带来刷盘抖动。

## 四、提交成功到底意味着什么

从工程上讲，事务提交成功，代表它的关键日志记录已经达到数据库要求的持久化条件。

也就是说，提交不是“所有数据页已经全部写完”，而是“恢复这次提交所需的信息已经可靠记录”。

这就是 WAL 机制最核心的理解点。

## 五、为什么 WAL 还和复制有关

因为主库的变更先进入 WAL，备库可以持续消费这些日志并重放。

所以从架构上看：

- WAL 支撑崩溃恢复
- WAL 也支撑主从复制

很多可靠性和高可用能力，底层都绕不开它。

## 六、后端开发者为什么也要懂这一层

因为线上常见问题会直接落到这里：

- 突然写入抖动
- 大事务导致 WAL 暴涨
- 备库延迟
- 崩溃恢复时间过长

如果你完全不知道 WAL 和 checkpoint，很多现象会看起来像“玄学”。

## 七、哪些业务操作会明显增加日志压力

- 大批量更新
- 大批量删除
- 长事务
- 高频更新热点表
- 大字段频繁修改

这也是为什么很多数据修复脚本不能粗暴一把梭执行。

## 八、这一层你不用记得太底，但要知道什么

至少知道：

1. 提交依赖 WAL，不是等所有页写完。
2. Checkpoint 会影响刷盘节奏和恢复成本。
3. 大事务和高频写入会拉高日志压力。
4. 复制和恢复都依赖 WAL。

## 这篇最重要的结论

WAL 是 PostgreSQL 可靠性的底座。只要你理解“先记账，再慢慢落页”，很多崩溃恢复、复制、写入波动问题就有了统一解释框架。
