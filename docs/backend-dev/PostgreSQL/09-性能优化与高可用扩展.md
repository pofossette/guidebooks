# 09. 性能优化与高可用扩展

当你已经能写表、写 SQL、看执行计划后，下一步就是把 PostgreSQL 当成线上基础设施来理解。

## 一、性能优化不要一上来调参数

先记一个顺序：

1. 先看业务查询是否合理
2. 再看表设计和索引
3. 再看执行计划
4. 最后才是参数和资源配置

很多性能问题，根本不是靠调数据库参数解决的。

## 二、最常见的性能瓶颈有哪些

- 慢 SQL
- 缺索引或索引不匹配
- 热点行频繁更新
- 长事务拖住清理
- 排序、聚合、join 数据量过大
- 内存或磁盘 IO 不足

## 三、后端开发最值得关注的几个指标

- QPS / TPS
- 慢查询数量
- 缓冲区命中率
- 锁等待
- 活跃连接数
- 复制延迟
- 磁盘使用和 WAL 增长速度

不要看到数据库慢就只盯 CPU。很多时候真正的瓶颈是 IO、锁或者 SQL 设计。

## 四、连接管理为什么经常是隐藏问题

PostgreSQL 不是越多连接越好。

连接过多会带来：

- 内存开销
- 调度压力
- 抢占资源

真实项目里通常会配合连接池，比如应用侧池化或 `pgbouncer`。

## 五、读写分离和主从复制要怎么理解

最基础的思路是：

- 主库负责写
- 备库同步或异步接收 WAL
- 读流量可以部分分担到备库

但要注意：

- 备库可能有延迟
- 强一致读不能随便丢给备库

所以“能不能读写分离”不是架构口号，而是业务一致性要求问题。

## 六、什么时候需要分区、归档和冷热分层

当表非常大、数据明显按时间演进时，可以考虑：

- 分区表
- 历史归档
- 冷热数据分层

尤其是：

- 日志
- 事件
- 消息
- 审计记录

这类表如果一直堆在单表里，维护和查询都会越来越难。

## 七、PostgreSQL 的扩展能力为什么值得关注

PG 很有特色的一点，是扩展生态强。

常见方向：

- `pgvector`：向量检索
- 全文检索：搜索类能力
- `postgis`：地理空间
- `pg_trgm`：模糊匹配

这意味着很多项目可以在同一套数据库体系里，把主数据和部分高级检索能力合在一起。

## 八、线上优化的正确心态

不要追求“数据库永远不慢”，而要追求：

- 慢的时候能快速定位
- 热点问题可预防
- 扩容和分流路径提前想清楚

## 这篇最重要的结论

性能优化和高可用不是数据库后期“补充知识”，而是 PostgreSQL 作为生产基础设施必须理解的部分。前面几篇是在学怎么用 PG，这一篇是在学怎么把 PG 用在线上。
