# 06. 事务与 MVCC

事务和 MVCC 是 PostgreSQL 的核心能力。很多“功能能跑，但一上并发就乱”的问题，最后都落到这里。

## 一、事务到底在解决什么

事务保护的是一组操作的整体正确性。

例如转账：

1. 扣减 A 余额
2. 增加 B 余额
3. 写交易流水

这三步要么都成功，要么都失败。否则系统状态就会不一致。

## 二、ACID 怎么用工程语言理解

- `Atomicity`：要么全成，要么全不成
- `Consistency`：提交后数据要满足约束
- `Isolation`：并发事务互相不要乱影响
- `Durability`：提交后不能说没就没

别把它当背诵题，它其实就是数据库正确性的四个维度。

## 三、PostgreSQL 默认隔离级别

PG 默认是 `READ COMMITTED`。

这意味着：

- 每条语句看到的是执行开始时已提交的数据
- 同一个事务里，不同语句看到的快照可能不同

更高一级是 `REPEATABLE READ`，再往上是 `SERIALIZABLE`。

大多数业务不是隔离级别越高越好，而是要按冲突模型选。

## 四、MVCC 可以先怎么理解

MVCC 是多版本并发控制。

先记住一句话：

**它的目标，是尽量让读写并发时，不需要一上来就互相堵住。**

你可以把它粗略理解成：

- 一行数据不只有“当前值”
- 数据在事务视角下存在可见性判断
- 读事务不一定看到最新版本，而是看到自己应当看到的版本

## 五、为什么 PG 很强调旧版本清理

因为有多版本，就会有旧版本残留。

如果旧版本长期不清理，会带来：

- 表膨胀
- 索引膨胀
- 查询变慢

这就是 `VACUUM` 为什么重要。

## 六、事务学习里最值得先抓的并发异常

### 1. 脏读

读到了别人还没提交的数据。

### 2. 不可重复读

同一事务里，两次读同一行结果不同。

### 3. 幻读

同一事务里，两次按条件查询，结果集新增或减少了记录。

不要只背定义，更重要的是把它和业务问题对应起来。

## 七、业务里哪些操作必须认真设计事务边界

- 创建订单并扣库存
- 创建 run 并写消息
- 扣配额并记账
- 领取任务并改状态

事务边界的关键原则是：

**短、小、只包关键数据库状态变更。**

不要把外部模型调用、HTTP 请求、文件解析塞进长事务里。

## 八、从后端视角怎么判断这里需不需要事务

问自己两个问题：

1. 这些写操作是不是必须一起成功？
2. 中途失败会不会留下半成品状态？

如果答案是会，那通常就需要事务。

## 这篇最重要的结论

事务是在保护数据正确性，MVCC 是在平衡并发与一致性。理解了这两者的分工，你才不会把数据库并发问题只当成“代码加锁问题”。
