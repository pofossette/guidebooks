# 05. 压测、演练与高可用治理

高可用不是写在设计文档里的口号，而是要靠监控、压测和演练不断验证。

## 一、为什么高可用一定要演练

因为很多故障恢复方案只在纸面上成立。

如果从来没演练过：

- 切换流程可能根本不可用
- 告警可能没人处理
- 回滚方案可能不完整

## 二、压测和高可用有什么关系

高可用不只是“机器坏了怎么办”，也包括：

- 流量高峰时会不会崩
- 依赖变慢时会不会雪崩
- 资源打满时能不能保核心链路

所以压测其实也是高可用验证的一部分。

## 三、高可用治理通常包含哪些动作

- 监控
- 告警
- 值班
- 发布管控
- 故障演练
- 复盘改进

这说明高可用不是一个中间件能力，而是工程治理能力。

## 四、常见演练类型

### 1. 单实例故障演练

看服务多副本和负载摘除是否正常。

### 2. 数据库故障演练

看主从切换、读写降级、恢复流程是否可行。

### 3. 下游依赖异常演练

看超时、熔断、降级是否真正生效。

### 4. 流量洪峰演练

看限流、缓存、队列削峰是否有效。

## 五、故障复盘为什么重要

复盘不是追责大会，而是为了回答：

- 问题怎么发生的
- 为什么没提前发现
- 为什么影响扩大了
- 下次怎么避免

没有复盘，高可用就很难持续进化。

## 六、务实的高可用治理清单

1. 核心链路有监控和告警
2. 核心依赖有超时和降级
3. 数据有备份和恢复验证
4. 发布有灰度和回滚方案
5. 定期做故障演练
6. 每次事故后做复盘闭环

## 七、初学者最容易忽略的点

### 1. 只写方案，不做演练

### 2. 只看接口成功率，不看核心业务成功率

### 3. 只盯服务，不盯数据库、缓存和队列

### 4. 没有统一故障等级和响应流程

## 这篇最重要的结论

高可用最终靠治理落地。监控告诉你出没出事，压测告诉你边界在哪，演练告诉你方案到底能不能用，复盘决定你下次会不会再踩同一个坑。
