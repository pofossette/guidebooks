# 04. 冗余、容灾与故障转移

如果系统只有一条路可走，那这条路一断，系统就没了。

冗余、容灾和故障转移，本质上是在给系统准备“备份路线”。

## 一、冗余是在解决什么问题

冗余的核心是：

**关键资源不要只放一份。**

例如：

- 服务多实例
- 数据库主从
- 多副本缓存
- 多可用区部署

## 二、容灾是在解决什么问题

容灾不是普通故障恢复，而是针对更大范围风险：

- 机房故障
- 可用区故障
- 网络中断
- 大规模依赖异常

它关注的是：

- 更严重故障下系统还能不能活

## 三、故障转移是什么

故障转移就是：

**主路径挂了，流量或任务自动切到备路径。**

例如：

- 主库故障切到备库
- 某实例异常从负载池摘除
- 某机房故障切流到别的机房

## 四、为什么不是所有系统都要一上来就双活

因为高等级容灾的代价很高：

- 架构复杂
- 成本高
- 数据一致性更难
- 运维要求更高

所以正确思路是按业务级别做：

- 普通后台系统
- 核心交易系统
- 强实时业务

它们的容灾要求不一样。

## 五、常见冗余层次

### 1. 应用层冗余

多实例、多节点部署。

### 2. 数据层冗余

主从、副本、备份、快照。

### 3. 网络层冗余

多链路、多入口、多可用区。

### 4. 机房层冗余

同城双活、异地容灾。

## 六、备份为什么也属于高可用体系

因为有些故障不是“服务挂了”，而是：

- 数据被误删
- 数据被污染
- 发布把库写坏了

这时没有备份，就谈不上恢复。

## 七、通俗理解 RPO 和 RTO

### RPO

最多能接受丢多久的数据。

### RTO

最多能接受系统停多久。

这两个指标会直接决定：

- 你需要多重的复制
- 你要不要做异地容灾
- 你的恢复方案复杂度要多高

## 八、最容易犯的错误

### 1. 只有副本，没有演练

### 2. 有备份，但恢复流程没验证过

### 3. 只做应用多实例，忽略数据库和依赖单点

### 4. 为小系统过早上双活，成本远超收益

## 这篇最重要的结论

高可用不是一句“多机部署”就结束了。真正的关键是：关键资源有没有冗余，故障时能不能自动或快速切换，切换后数据和业务还能不能收住。
