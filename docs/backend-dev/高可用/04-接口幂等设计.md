# 04. 接口幂等设计

很多系统不是“功能不会写”，而是重复请求一来，数据就开始乱。

接口幂等设计就是在解决这个问题。

## 一、什么叫接口幂等

通俗讲就是：

**同一个请求重复执行多次，最终结果应该尽量一致。**

比如：

- 用户重复点击提交按钮
- 网络超时后客户端自动重试
- 网关或服务端重试
- 第三方回调重复发送

如果没有幂等，最常见的后果就是：

- 重复下单
- 重复扣款
- 重复发券
- 重复发消息

## 二、为什么接口会被重复调用

很多人一开始会觉得“前端不是点一次吗，为什么会重复？”

真实系统里，重复请求很常见：

- 用户手抖点了多次
- 页面卡了，用户刷新重试
- 移动网络抖动导致超时重发
- 代理层或调用方有重试机制
- 消息消费端发生重复投递

所以幂等不是锦上添花，而是线上系统很实际的基础能力。

## 三、哪些接口必须重点考虑幂等

- 创建订单
- 支付回调
- 库存扣减
- 发券
- 转账
- 任务消费
- 第三方通知接收

一句话判断：

**只要这个接口重复执行会产生副作用，就要认真考虑幂等。**

## 四、幂等不等于“返回完全一样”

幂等的重点不是所有响应字段一模一样，而是：

- 核心业务结果不能重复产生
- 重复调用不会把数据做乱

例如第一次创建订单返回：

- `order_id = 123`

第二次同请求再来，直接返回同一个订单，或者提示“已处理”，这都可以算合理幂等。

## 五、最常见的幂等实现方式

### 1. 唯一约束

最简单直接。

例如：

- 订单号唯一
- 第三方流水号唯一
- 幂等键唯一

数据库唯一约束是很强的一层保护，因为它不只依赖应用代码自觉。

### 2. 幂等键

客户端或调用方为一次请求生成一个唯一 `idempotency_key`。

服务端收到后：

1. 先检查这个 key 是否已经处理过
2. 如果处理过，直接返回之前结果
3. 如果没处理过，再执行业务逻辑

这在支付、订单创建、API 重试里很常见。

### 3. 状态机控制

例如任务状态只能按：

- `pending -> running -> done`

如果已经 `done`，再来一次相同处理就直接忽略或返回已有结果。

### 4. 去重表 / 消费记录表

消息队列消费端很常见。

例如记录：

- 消息 ID
- 业务流水号
- 处理时间

消费前先查是否处理过。

## 六、一个典型的幂等接口设计

例如创建订单接口：

1. 客户端提交订单时带 `idempotency_key`
2. 服务端先查这个 key 是否已有成功记录
3. 没有则开启事务创建订单
4. 成功后保存 key 和订单结果
5. 重复请求再来时，直接返回已有订单

## 七、幂等设计里最容易踩的坑

### 1. 只在应用层做内存去重

单机有效，多实例就不稳。

### 2. 没有设置幂等范围

同一个 key 到底对应：

- 一个用户
- 一个业务单号
- 一次支付请求

必须定义清楚。

### 3. 只防重复提交，不防重复回调

很多事故恰恰发生在第三方异步通知。

### 4. 幂等检查和业务写入不是一个原子过程

这样并发下还是可能重复成功。

## 八、幂等和防重不是完全一回事

防重更像是“别让重复请求进来”。

幂等更像是“就算重复进来了，也别把结果做乱”。

最稳的系统通常两者都做：

- 前端防连点
- 网关限流
- 后端幂等保证

## 九、一个务实的实现建议

对于大多数后端项目，可以先按这个顺序做：

1. 为关键接口识别副作用
2. 给核心业务号加唯一约束
3. 给创建类接口引入幂等键
4. 对异步消费记录去重状态
5. 把幂等检查和写入放进可控事务边界

## 这篇最重要的结论

接口幂等设计的核心不是“请求别重复”，而是“重复来了也别把业务做乱”。真正可靠的做法通常是业务约束、幂等键、状态控制和存储层唯一性一起配合。
