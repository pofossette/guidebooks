# 01. MongoDB 基础与定位

学 MongoDB 的第一步，不是背 API，而是先搞清楚：

**它在系统里适合做什么，不适合做什么。**

## 一、MongoDB 是什么

MongoDB 是一个面向文档的数据库。

它的基本组织单位可以先这样理解：

- `database`：数据库
- `collection`：集合，类似表
- `document`：文档，类似一条记录

但“类似”不等于“完全一样”。

最关键的区别是：

**文档可以天然嵌套，不需要像关系型数据库那样一上来就拆成很多张表。**

## 二、MongoDB 适合解决什么问题

### 1. 数据结构变化频繁

例如不同类型内容带不同字段。

### 2. 天然是树状或嵌套结构

例如：

- 评论树
- 配置对象
- 用户画像

### 3. 前后端经常按整块对象读写

比如一个页面一次性要拿完整资料对象，而不是跨多张表 join。

## 三、MongoDB 不适合什么问题

### 1. 强依赖复杂 join 的系统

### 2. 强事务、强一致核心交易系统

### 3. 高度规范化、跨实体关系极其复杂的业务

这不是说完全不能做，而是工程上往往没关系型数据库顺手。

## 四、MongoDB 在后端系统里常见的定位

常见角色有：

- 主业务库
- 配置数据存储
- 用户画像和元数据存储
- 日志、事件或内容类数据存储

你可以把它理解成：

**当数据更像“对象”而不是“强关系表”时，MongoDB 会更自然。**

## 五、一个最小示例

例如一个用户资料文档：

```json
{
  "_id": "u1001",
  "name": "Alice",
  "email": "alice@example.com",
  "profile": {
    "city": "Shanghai",
    "skills": ["ts", "node", "postgres"]
  },
  "createdAt": "2026-06-09T10:00:00Z"
}
```

这个结构在 MongoDB 里很自然。

如果放到关系型数据库，可能会拆成：

- `users`
- `user_profiles`
- `user_skills`

哪种更好，不是绝对的，要看访问模式。

## 六、MongoDB 学习时最该问的三个问题

1. 数据是更像对象还是更像关系网络？
2. 访问时更常整块读写，还是更常跨实体联查？
3. 一致性和事务要求有多高？

## 这篇最重要的结论

MongoDB 的价值不在“少写表”，而在它更适合某些对象化、嵌套化、变化快的数据场景。先搞清定位，比直接学语法更重要。
