# 02. 文档模型与表结构设计思路

MongoDB 最核心的一课，不是查询语法，而是建模。

## 一、MongoDB 建模和关系型建模的差别

关系型数据库更常从“实体关系”出发。

MongoDB 更常从“访问模式”和“对象结构”出发。

也就是说，你要先问：

- 这个对象通常怎么被读取？
- 这些字段会不会一起返回？
- 这些数据更新频率是不是差不多？

## 二、嵌入还是引用

这是 MongoDB 建模里最经典的问题。

### 1. 嵌入

把相关数据直接放进一个文档。

适合：

- 一起读取
- 一起更新
- 数量不大

### 2. 引用

只保存关联对象的 ID。

适合：

- 关联对象独立性强
- 需要单独维护
- 数量可能很大

## 三、一个直观例子

例如订单和订单项：

- 如果订单项数量可控，且总是跟订单一起读，可以考虑嵌入
- 如果订单项很多，或者要单独查询、统计和更新，就更适合拆开引用

## 四、MongoDB 不是“什么都塞一个文档”

很多初学者会误以为文档数据库就该把所有东西塞成一个大 JSON。

这会带来问题：

- 文档过大
- 更新粒度不清
- 索引复杂
- 局部字段频繁改动代价高

## 五、建模时优先考虑什么

1. 高频查询路径
2. 高频更新路径
3. 文档大小和增长趋势
4. 是否需要跨文档事务

## 六、务实建议

MongoDB 建模的第一原则不是“最像业务对象”，而是：

**最贴近真实访问模式。**

## 这篇最重要的结论

MongoDB 设计结构时，重点不是机械地模仿关系型表，而是根据读写模式决定哪些数据该嵌入，哪些数据该引用。
