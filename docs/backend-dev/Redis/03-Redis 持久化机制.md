# 03. Redis 持久化机制

## 一、为什么内存数据库还要持久化

Redis 的数据主要在内存里。内存读写快，但进程退出或机器故障后会丢数据。

持久化要解决的是：

**Redis 重启后，能不能把数据恢复回来。**

但要先明确一点：Redis 持久化不是传统数据库事务日志的完整替代。它能降低数据丢失范围，但不能保证任何情况下都完全不丢。

## 二、RDB

RDB 是快照持久化。

它会在某个时间点把 Redis 内存中的数据生成一个快照文件。

可以粗略理解为：

```text
某一刻的 Redis 数据 -> dump.rdb
```

优点：

- 文件紧凑
- 恢复速度通常较快
- 适合备份
- 对正常写入影响相对小

缺点：

- 两次快照之间的数据可能丢失
- fork 子进程时可能有内存压力
- 数据量很大时生成快照成本较高

RDB 更适合“允许丢失一小段时间数据，但希望恢复快”的场景。

## 三、AOF

AOF 是追加日志持久化。

Redis 会把写命令追加到 AOF 文件里，重启时重新执行这些命令恢复数据。

可以粗略理解为：

```text
SET a 1
INCR count
HSET user:1 name Alice
```

优点：

- 数据丢失窗口更小
- 日志可读性较好
- 可以通过 fsync 策略控制可靠性和性能

缺点：

- 文件通常比 RDB 大
- 恢复时要重放命令
- AOF rewrite 时也有额外成本

常见 fsync 策略：

| 策略 | 含义 | 取舍 |
|---|---|---|
| always | 每条写命令都刷盘 | 最安全，最慢 |
| everysec | 每秒刷盘 | 常用，最多丢约 1 秒 |
| no | 交给操作系统决定 | 性能好，丢失窗口更大 |

## 四、AOF 重写

AOF 文件会不断增长。Redis 会通过 AOF rewrite 生成更紧凑的新文件。

例如原来有很多命令：

```text
INCR count
INCR count
INCR count
```

重写后可以变成：

```text
SET count 3
```

重写不是简单压缩文本，而是根据当前内存状态重新生成恢复所需的最小命令集合。

## 五、RDB 和 AOF 如何选择

常见选择：

- 只做缓存：可以不开持久化，或只开 RDB
- 允许少量丢失：AOF everysec
- 需要备份恢复：RDB + AOF
- 核心业务唯一数据：不要只依赖 Redis

很多生产环境会同时开启 RDB 和 AOF。Redis 重启时通常优先使用 AOF，因为 AOF 数据更新。

## 六、持久化和缓存场景的关系

如果 Redis 只是缓存，数据源在数据库中，那么 Redis 丢数据的后果通常是缓存未命中增多。

这时重点不是“Redis 一条都不能丢”，而是：

- 数据库能否承受回源流量
- 是否会发生缓存雪崩
- 是否有预热机制
- 是否有熔断和限流

如果 Redis 保存的是验证码、会话、限流计数这类临时数据，重启后丢失会影响用户体验，但通常不会破坏核心账务。

## 七、持久化的性能风险

持久化可能带来这些问题：

- fork 子进程导致短暂停顿
- 内存大时 copy-on-write 成本高
- 磁盘 I/O 抖动影响 Redis
- AOF 文件过大导致恢复慢
- rewrite 期间写入压力增大

所以 Redis 不只是调几个配置就完事。生产环境要同时关注内存、磁盘、延迟和恢复时间。

## 八、TS 后端开发者要记住什么

写业务代码时要假设：

- Redis 可能重启
- Redis 可能丢失最近一小段写入
- Redis 恢复期间可能不可用
- Redis 不是核心数据的唯一来源

因此：

- 核心状态要落数据库
- Redis 写入失败要有业务降级
- 缓存失效后要能从数据库重建
- 临时数据要能接受过期或丢失

Redis 持久化是系统可靠性的一部分，但不是把 Redis 当数据库用的理由。
