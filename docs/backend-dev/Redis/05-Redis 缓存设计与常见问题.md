# 05. Redis 缓存设计与常见问题

## 一、缓存的基本目标

缓存的目标是减少慢资源访问。

常见慢资源：

- 数据库查询
- 第三方 API
- 复杂计算
- 文件或对象存储读取

Redis 做缓存时，通常不是为了“数据更权威”，而是为了“请求更快、数据库压力更小”。

## 二、Cache Aside

后端最常见的缓存模式是 cache-aside。

读取流程：

1. 先查 Redis
2. 命中则返回
3. 未命中则查数据库
4. 把数据库结果写入 Redis
5. 返回数据

写入流程通常是：

1. 先更新数据库
2. 再删除缓存

一般不推荐“更新数据库后直接更新缓存”，因为缓存值可能由多个表或复杂逻辑计算得到，直接更新容易遗漏。

## 三、缓存穿透

缓存穿透指请求查询的数据根本不存在，导致每次都穿过 Redis 打到数据库。

例如不断查询不存在的用户 ID。

常见处理方式：

- 缓存空值，设置较短 TTL
- 参数校验，明显非法请求直接拦截
- 布隆过滤器判断 key 是否可能存在

空值缓存示例：

```ts
const cached = await redis.get(key);

if (cached !== null) {
  return cached === "__NULL__" ? null : JSON.parse(cached);
}

const data = await db.findById(id);

await redis.set(
  key,
  data ? JSON.stringify(data) : "__NULL__",
  "EX",
  data ? 600 : 60,
);
```

## 四、缓存击穿

缓存击穿指某个热点 key 过期后，大量请求同时回源数据库。

例如爆款商品详情缓存刚好过期。

常见处理方式：

- 热点 key 设置更长 TTL
- 提前刷新缓存
- 使用互斥锁限制回源
- 使用逻辑过期，后台异步刷新

互斥锁只能减少回源并发，不能替代数据库保护。拿不到锁的请求可以短暂等待、返回旧值或降级。

## 五、缓存雪崩

缓存雪崩指大量 key 同时失效，导致数据库突然承受大量请求。

常见原因：

- 大批 key 设置了相同 TTL
- Redis 实例故障
- 缓存预热失败

常见处理方式：

- TTL 加随机抖动
- 关键数据预热
- Redis 高可用部署
- 数据库限流和熔断
- 多级缓存

TTL 抖动示例：

```ts
const ttl = 600 + Math.floor(Math.random() * 120);
await redis.set(key, JSON.stringify(data), "EX", ttl);
```

## 六、缓存和数据库一致性

缓存和数据库很难做到绝对实时一致。

常见策略是：

**先更新数据库，再删除缓存。**

为什么不是先删缓存？

如果先删缓存，然后数据库还没更新完成，另一个请求可能读到旧数据库值并重新写入缓存，导致缓存里继续保留旧数据。

更新数据库后删除缓存也不是完美的。删除失败时，缓存仍可能是旧值。

所以生产环境还要考虑：

- 删除缓存失败后的重试
- 使用消息队列做延迟删除
- 给缓存设置合理 TTL
- 对关键数据直接读数据库或做版本校验

## 七、缓存预热

缓存预热是在流量进来前，提前把热点数据写入 Redis。

适合：

- 首页推荐
- 热门商品
- 活动配置
- 排行榜

预热不是越多越好。冷数据大量写入 Redis 会浪费内存，并可能挤掉真正的热点数据。

## 八、缓存降级

Redis 也可能故障。

业务代码要区分：

- Redis 挂了是否允许接口继续查数据库
- 数据库是否能承受直接回源
- 是否需要返回默认值或旧值
- 是否要临时关闭某些非核心功能

例如“文章浏览数 +1”失败可以异步补偿；“用户权限缓存读取失败”可能必须回源数据库确认。

## 九、缓存设计检查清单

设计一个 Redis 缓存 key 时，至少回答这些问题：

- key 怎么命名
- value 用什么数据类型
- TTL 多久
- 数据源在哪里
- 未命中怎么回源
- 数据更新后如何失效
- 查不到的数据是否缓存空值
- 热点 key 如何保护
- Redis 故障时接口如何表现

缓存不是加一层 Redis 就结束。真正的难点在失效、回源、降级和一致性边界。
