# 04. Redis 线程模型与性能

## 一、Redis 真的是单线程吗

Redis 常被说成单线程，但这个说法需要限定范围。

传统 Redis 的核心命令执行主要由单线程完成：

- 解析命令
- 执行命令
- 读写内存数据结构
- 返回结果

但 Redis 还会有其他后台线程或子进程处理：

- 持久化
- AOF 重写
- 异步释放内存
- 网络 I/O 辅助线程

所以更准确的说法是：

**Redis 的命令执行路径主要是单线程串行执行。**

## 二、单线程为什么还能快

Redis 单线程仍然很快，是因为：

- 数据在内存中
- 命令执行通常很短
- 避免了多线程锁竞争
- 避免了频繁上下文切换
- 使用 I/O 多路复用处理大量连接

它不需要为每个连接创建一个线程，而是通过事件循环监听多个 socket 的可读、可写事件。

这和 Node.js 的事件循环有相似之处：都不是靠“一个请求一个线程”来支撑并发。

## 三、单线程模型的代价

单线程的核心代价是：

**一个慢命令会阻塞后面的所有命令。**

例如：

- `KEYS *`
- 对巨大 Hash 执行 `HGETALL`
- 对巨大 List 执行大范围 `LRANGE`
- 删除超大 key
- 执行复杂 Lua 脚本
- 慢磁盘导致 AOF fsync 卡顿

如果 Redis 被一个命令卡住，其他请求也会排队等待。

这就是为什么 Redis 使用规范里反复强调不要随便使用 O(n) 命令。

## 四、时间复杂度要看 n

Redis 命令文档通常会标注时间复杂度。

例如：

| 命令 | 复杂度 | 风险 |
|---|---|---|
| `GET` | O(1) | 通常安全 |
| `SET` | O(1) | 通常安全 |
| `HGET` | O(1) | 通常安全 |
| `HGETALL` | O(n) | n 大时危险 |
| `LRANGE` | O(s+n) | 范围大时危险 |
| `SMEMBERS` | O(n) | 集合大时危险 |
| `KEYS` | O(n) | 生产环境避免 |

O(n) 命令不是绝对不能用，而是必须明确 n 的上限。

例如一个 Hash 永远只有 10 个字段，`HGETALL` 可以接受；如果一个 Hash 可能有几十万个字段，就不能随便 `HGETALL`。

## 五、Pipeline

Redis 是网络服务。大量小命令的主要成本可能不是命令本身，而是网络往返。

Pipeline 可以把多个命令一次性发给 Redis，减少 RTT。

适合：

- 批量读取多个 key
- 批量写入缓存
- 批量删除有限数量 key

伪代码：

```ts
const pipeline = redis.pipeline();

for (const id of userIds) {
  pipeline.get(`user:profile:${id}`);
}

const results = await pipeline.exec();
```

注意：Pipeline 不是事务。它只是批量发送命令，不代表命令整体原子执行。

## 六、慢查询

Redis 提供 slowlog 记录执行时间较长的命令。

慢查询只统计命令执行时间，不包含网络传输和客户端排队时间。

如果接口访问 Redis 很慢，但 slowlog 没有记录，可能原因包括：

- 网络延迟
- 客户端连接池耗尽
- Redis 请求排队
- 应用自身事件循环被阻塞
- 代理层或容器网络问题

排查时不要只盯着 Redis 服务端。

## 七、大 key

大 key 指 value 非常大的 key，或者内部元素特别多的集合型 key。

常见例子：

- 一个 String 存了几 MB 的 JSON
- 一个 Hash 有几十万个 field
- 一个 Set 有上百万个 member
- 一个 List 长到几百万

大 key 的问题：

- 读写慢
- 删除慢
- 网络传输重
- 主从同步压力大
- 集群分片不均

处理方式：

- 拆分 key
- 限制集合长度
- 使用 scan 类命令渐进遍历
- 删除大 key 时使用异步删除

## 八、热 key

热 key 指访问频率异常高的 key。

例如：

- 爆款商品详情
- 热门文章计数
- 全站配置
- 秒杀活动库存

热 key 会让单个 Redis 节点或单个分片压力过高。

常见处理方式：

- 本地缓存短时间缓存
- 多副本读
- key 分片
- 提前预热
- 对写入做聚合或异步化

## 九、性能优化的核心原则

Redis 性能优化不是盲目追求更高 QPS，而是减少阻塞和抖动。

优先检查：

- 是否有慢命令
- 是否有大 key
- 是否有热 key
- 是否频繁创建连接
- 是否没有使用批量操作
- 是否把 Redis 当成复杂查询引擎

对业务开发者来说，最重要的习惯是：写 Redis 代码时同时问一句 **这个 key 最大会多大，这条命令最坏会扫多少数据**。
