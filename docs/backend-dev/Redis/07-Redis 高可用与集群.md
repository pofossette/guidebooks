# 07. Redis 高可用与集群

## 一、为什么需要高可用

单个 Redis 实例有明显风险：

- 进程崩溃会不可用
- 机器宕机会不可用
- 重启恢复需要时间
- 内存和 CPU 有上限
- 单点故障会影响依赖它的服务

如果 Redis 只是非核心缓存，短时间不可用也许可以降级。如果 Redis 承载登录态、限流、分布式锁、热点库存等能力，可用性就会直接影响业务。

## 二、主从复制

Redis 主从复制的基本结构：

```text
master -> replica
```

写请求通常发到 master，从节点复制 master 的数据。

主从复制的作用：

- 提供数据副本
- 支持读扩展
- 为故障切换做准备

但主从复制通常是异步的，因此会有复制延迟。

这意味着：

- 刚写入 master 的数据，从节点可能还读不到
- master 宕机时，最近一小段写入可能没有复制出去
- 读从库时要接受短暂旧数据

## 三、Sentinel

Sentinel 是 Redis 的哨兵机制，用来监控 Redis 主从节点并做故障转移。

它主要负责：

- 监控 master 和 replica 是否存活
- 判断 master 是否下线
- 选举新的 master
- 通知客户端新的 master 地址

Sentinel 解决的是：

**主节点故障后，系统能自动选出新的主节点。**

但它不解决水平扩容问题。所有数据仍然在一个主节点的数据集内。

## 四、主观下线和客观下线

Sentinel 判断下线通常分两层：

- 主观下线：某个 Sentinel 认为节点不可达
- 客观下线：多个 Sentinel 都认为 master 不可达

为什么要分两层？

因为单个 Sentinel 可能因为网络抖动误判。多个 Sentinel 达成判断后再故障转移，可以降低误判概率。

## 五、脑裂风险

脑裂指多个节点都认为自己是主节点，或者旧 master 在网络隔离后仍然接受写入。

脑裂可能导致：

- 两边都接收写入
- 故障恢复后数据冲突
- 旧 master 的写入被丢弃

缓解方式包括：

- 部署奇数个 Sentinel
- 合理设置故障判断时间
- 客户端正确感知主节点变化
- 配置 master 至少需要若干 replica 才继续写
- 核心业务保留数据库约束和幂等

Redis 高可用能降低故障影响，但不能让所有异常消失。

## 六、Redis Cluster

Redis Cluster 用来做数据分片和高可用。

它把 key 分布到 16384 个 hash slot 中，不同节点负责不同 slot。

可以粗略理解为：

```text
key -> hash slot -> Redis 节点
```

Cluster 解决的是：

- 单机内存上限
- 单机写入压力
- 节点故障转移
- 数据分片管理

## 七、hash tag

Redis Cluster 中，多 key 命令要求 key 位于同一个 slot。

可以用 hash tag 控制 key 的 slot：

```text
cart:{user:1001}
cart-meta:{user:1001}
```

只有 `{}` 内的部分会参与 slot 计算，所以这两个 key 会落到同一个 slot。

这对需要同时操作多个相关 key 的场景很重要。

## 八、Cluster 的限制

Redis Cluster 不是把单机 Redis 透明放大。

常见限制：

- 跨 slot 多 key 操作受限
- 客户端需要支持重定向
- 扩缩容会带来迁移成本
- 热 key 仍然可能打爆单个分片
- 大 key 会导致分片不均

所以使用 Cluster 前，要先设计 key 分布和访问模式。

## 九、客户端连接

TS 后端使用 Redis Cluster 时，客户端要支持 cluster 模式。

业务代码要关注：

- 连接池配置
- 命令重试策略
- 超时时间
- 故障切换期间的异常处理
- 是否误用跨 slot 命令

不要在每次请求里创建 Redis 连接。Redis 客户端应该作为应用级单例或连接池复用。

## 十、怎么选

| 需求 | 方案 |
|---|---|
| 单机缓存，能接受短暂不可用 | 单实例 |
| 需要自动主从切换 | 主从 + Sentinel |
| 数据量或吞吐超过单机 | Redis Cluster |
| 强一致协调 | etcd/ZooKeeper 更合适 |
| 复杂消息系统 | 专业消息队列更合适 |

高可用不是只把 Redis 部署成集群。业务侧还要有超时、重试、降级、幂等和监控。
