# 08. Redis 使用规范与排查

## 一、为什么要有使用规范

Redis 很快，但也很容易被错误用法拖垮。

一个后端服务里，很多接口可能共享同一个 Redis 实例。某个接口执行了危险命令，影响的可能不是一个功能，而是整个系统的缓存、登录态、限流和锁。

所以 Redis 的使用规范不是形式主义，而是保护共享基础设施。

## 二、连接规范

不要频繁创建和关闭 Redis 连接。

应该：

- 应用启动时创建客户端
- 多请求复用连接或连接池
- 设置合理连接超时
- 设置命令超时
- 监听连接错误
- 在应用关闭时优雅断开

不要：

- 每个 HTTP 请求创建一个 Redis 客户端
- 不设置超时无限等待
- 忽略连接错误
- 在高并发下无限制重试

## 三、key 命名规范

推荐 key 具备业务层级：

```text
业务:对象:标识:字段
```

示例：

```text
user:profile:1001
article:like-count:9527
order:lock:202606070001
rank:article:daily:2026-06-07
```

建议：

- 使用统一前缀
- 避免过长 key
- 避免无意义缩写
- 标识环境或租户时放在稳定位置
- 批量清理要有明确前缀边界

## 四、TTL 规范

缓存 key 通常应该设置 TTL。

没有 TTL 的 key 会长期占用内存，可能逐渐把 Redis 变成垃圾堆。

建议：

- 普通缓存设置明确过期时间
- 热点缓存可以设置较长 TTL 并异步刷新
- TTL 增加随机抖动，避免集中失效
- 临时 token、验证码、锁必须设置 TTL
- 长期存在的配置 key 要有清理和审计机制

## 五、命令规范

生产环境谨慎使用 O(n) 命令。

高风险命令：

- `KEYS`
- `HGETALL`
- `SMEMBERS`
- `LRANGE` 大范围读取
- `SINTER` / `SUNION` / `SDIFF`
- 长时间 Lua 脚本
- 对大 key 执行 `DEL`

替代思路：

- 用 `SCAN` 替代 `KEYS`
- 用 `HSCAN`、`SSCAN`、`ZSCAN` 渐进遍历
- 用分页限制 `LRANGE` 范围
- 用 `UNLINK` 异步删除大 key
- 在写入侧限制集合长度

## 六、批量操作规范

大量小命令会放大网络往返成本。

可以使用：

- `MGET`
- `MSET`
- Pipeline
- Lua 脚本

但批量也要有上限。

不要一次 pipeline 几十万条命令。这样会造成客户端内存、Redis 输入缓冲区和返回包都很大。

## 七、缓存 value 规范

value 要控制大小。

建议：

- JSON 字符串保持小而稳定
- 大对象拆分
- 列表类数据限制长度
- 只缓存接口真正需要的字段
- 压缩前先评估 CPU 成本

如果一个缓存对象已经大到每次传输都明显耗时，应该重新设计数据结构，而不是只调大 Redis 配置。

## 八、内存淘汰策略

Redis 内存达到上限后，会按配置的 maxmemory policy 淘汰数据或拒绝写入。

常见策略包括：

- volatile-lru
- allkeys-lru
- volatile-lfu
- allkeys-lfu
- volatile-ttl
- noeviction

选择策略要看 Redis 用途。

如果 Redis 主要做缓存，`allkeys-lru` 或 `allkeys-lfu` 常见；如果 Redis 里混有不能随便淘汰的数据，就要谨慎，最好拆分实例。

## 九、常见故障排查

Redis 慢时，可以按这个顺序排查：

1. 是否有慢查询
2. 是否有大 key
3. 是否有热 key
4. 是否连接数过高
5. 是否内存达到上限
6. 是否发生频繁淘汰
7. 是否有持久化 I/O 抖动
8. 是否主从同步延迟
9. 是否客户端超时或连接池耗尽
10. 是否应用自身事件循环阻塞

不要只看 Redis CPU。很多 Redis 问题表现为接口慢，但根因可能在网络、客户端连接池或应用代码。

## 十、监控指标

建议关注：

- QPS
- P95/P99 延迟
- 连接数
- used_memory
- 内存碎片率
- evicted_keys
- expired_keys
- blocked_clients
- slowlog
- keyspace 命中率
- 主从复制延迟

缓存命中率不是越高越好。一个不该缓存的接口命中率很高，也可能是在浪费内存。要结合业务价值判断。

## 十一、开发检查清单

提交 Redis 相关代码前，至少检查：

- 是否复用连接
- key 是否有统一命名
- 是否设置 TTL
- 是否存在无上限集合
- 是否用了危险 O(n) 命令
- 是否有批量大小限制
- Redis 失败时业务如何处理
- 缓存和数据库如何保持一致
- 是否需要监控和告警

Redis 用得好是系统加速器，用得差会变成共享故障源。规范的目标是让每个业务方都知道自己对 Redis 的最坏影响。
