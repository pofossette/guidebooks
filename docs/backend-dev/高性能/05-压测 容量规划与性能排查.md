# 05. 压测、容量规划与性能排查

高性能不是“感觉差不多挺快”，而是要能测、能估、能定位。

## 一、为什么一定要压测

因为很多问题在开发环境根本看不出来：

- 并发一高就锁冲突
- 缓存命中率一掉数据库就炸
- 外部依赖一慢，线程和连接全被占住

所以压测不是可选项，而是验证系统边界的手段。

## 二、压测在测什么

通常会关注这些：

- 吞吐量
- 响应时间
- 错误率
- CPU / 内存 / IO
- 数据库压力
- 队列堆积

## 三、容量规划是在做什么

容量规划的本质是：

**提前估算系统在业务增长后还能不能扛住。**

你要估的不是一个数字，而是一组关系：

- 峰值 QPS
- 单请求资源消耗
- 实例数
- 数据库承载能力
- 缓存命中率

## 四、一个简单的容量思路

例如：

- 峰值每秒 3000 请求
- 单实例稳定处理 300 请求

那从纯应用层看，至少要准备 10 台左右实例，再留冗余。

真实场景里还要继续看：

- 数据库是不是也能扛住
- Redis 是否成为新瓶颈
- 队列消费者是否跟得上

## 五、性能排查应该先查什么

### 1. 是所有接口都慢，还是个别接口慢

### 2. 是一直慢，还是高峰时慢

### 3. 是应用慢，还是数据库慢，还是依赖慢

### 4. 是 CPU 打满，还是 IO 打满，还是锁住了

很多排查失败，不是因为不会调优，而是因为问题定位顺序错了。

## 六、压测时的常见误区

### 1. 只测应用层，不测真实依赖

### 2. 测平均响应，不看长尾延迟

### 3. 测单接口，不测真实业务组合流量

### 4. 压出问题了，但没有指标和日志支撑定位

## 七、一个务实的性能排查路径

1. 先看监控面板和报错趋势
2. 定位最慢接口和最贵 SQL
3. 看缓存命中率和队列堆积
4. 看外部依赖超时和重试
5. 看资源使用和热点锁争用

## 八、优化后为什么还要回归压测

因为“改了代码”不代表“真的更快”。

有些优化只是把瓶颈从 A 挪到了 B。

所以正确动作是：

- 优化前测一次
- 优化后再测一次
- 做前后对比

## 这篇最重要的结论

高性能不是拍脑袋调优。压测告诉你边界在哪，容量规划告诉你未来会不会炸，性能排查告诉你现在到底慢在哪。
