# 03. 数据库优化与缓存设计

很多后端系统的第一个性能瓶颈，最终都会落到数据库。

## 一、为什么数据库最容易先扛不住

因为数据库通常承担了最多的核心读写：

- 用户数据
- 订单数据
- 状态流转
- 列表查询
- 聚合统计

只要查询写得不合理、索引不合理、缓存没设计好，数据库就会最先出问题。

## 二、数据库优化先看什么

### 1. SQL 写得对不对

不是语法对，而是：

- 有没有扫太多行
- 有没有深分页
- 有没有不必要排序

### 2. 索引建得对不对

不是“有没有索引”，而是：

- 索引是否贴合查询模式
- 是否有高频过滤字段
- 是否有排序字段支持

### 3. 表设计合不合理

例如：

- 状态字段是否清晰
- 时间维度是否方便分页
- 是否有高频联表热点

## 三、缓存是在解决什么问题

缓存的主要目标是：

**把高频读取从数据库前面挡掉。**

最常见场景：

- 用户信息
- 商品详情
- 配置项
- 热门列表

## 四、什么时候该用缓存

通常满足这些条件之一就值得考虑：

- 读远多于写
- 数据短时间内可复用
- 查询数据库成本高
- 热点明显

## 五、最常见的缓存模式

### 1. Cache Aside

最常见。

流程是：

1. 先查缓存
2. 没命中再查数据库
3. 再写回缓存

### 2. Write Through / Write Back

更偏特定缓存系统设计，中小业务里最常讲的还是 Cache Aside。

## 六、缓存不是没有代价

缓存会带来新的问题：

- 一致性怎么保证
- 过期时间怎么设
- 热点 key 怎么处理
- 雪崩、击穿、穿透怎么处理

所以缓存不是“只要加了就一定更好”。

## 七、数据库和缓存怎么配合

你可以粗暴记成：

- 数据库负责权威数据
- 缓存负责热点加速

不要把缓存当唯一事实来源，尤其是交易和账务类数据。

## 八、典型优化顺序

1. 先把 SQL 和索引调对
2. 再给高频读加缓存
3. 再做批处理、分页优化和热点治理
4. 最后才考虑读写分离、分区或分库分表

## 九、几个高频问题的通俗理解

### 缓存击穿

一个热点 key 失效后，大量请求一起打数据库。

### 缓存穿透

查的是根本不存在的数据，缓存和数据库都挡不住。

### 缓存雪崩

大量 key 在同一时间一起过期，数据库瞬间被打爆。

## 十、务实建议

1. 先不要迷信大架构，很多问题先从 SQL 和索引就能解决。
2. 缓存要围绕热点读设计，不要全量乱缓存。
3. 核心链路先保证数据库正确性，再考虑缓存一致性策略。

## 这篇最重要的结论

数据库优化和缓存设计是高性能后端的主战场。先把读写路径理顺，再谈更重的扩展方案，通常是最划算的路线。
