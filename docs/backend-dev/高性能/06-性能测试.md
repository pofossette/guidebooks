# 06. 性能测试

很多团队会说自己关注性能，但真正一问“测过没有、怎么测的、测出了什么”，往往就开始模糊。

性能测试就是把“感觉系统还行”变成“我知道系统的边界在哪”。

## 一、什么叫性能测试

性能测试不是只看一个接口快不快。

它更像是在回答：

- 系统最多能扛多少流量
- 在什么压力下开始变慢
- 变慢时先坏的是哪一层
- 优化后有没有真的变好

## 二、为什么性能测试很重要

因为开发环境太温柔了，很多问题根本暴露不出来：

- 低并发时看不出锁竞争
- 单用户访问看不出热点争抢
- 小数据量看不出 SQL 扫描问题
- 没有真实依赖时看不出队列和缓存瓶颈

## 三、性能测试常见类型

### 1. 基准测试

看系统在正常负载下的表现。

### 2. 负载测试

逐步增加请求量，看系统在预期流量下表现如何。

### 3. 压力测试

继续加压，逼近系统上限，看它什么时候开始明显异常。

### 4. 稳定性测试

长时间跑，观察内存泄漏、连接泄漏、资源累积问题。

### 5. 峰值测试

模拟突然流量暴涨，看系统能不能扛住瞬时冲击。

## 四、性能测试主要看哪些指标

- QPS / TPS
- 平均响应时间
- P95 / P99 延迟
- 错误率
- CPU 使用率
- 内存使用率
- 数据库连接数
- 缓存命中率
- 队列堆积长度

这里尤其要注意：

**平均响应时间不够，一定要看长尾延迟。**

## 五、为什么 P95 / P99 很重要

因为真实用户抱怨的，往往不是平均值，而是那批特别慢的请求。

平均 100ms 不代表体验就好。

如果 P99 已经飙到 3 秒，线上感受通常不会好。

## 六、性能测试前要先做什么准备

### 1. 明确测试目标

例如：

- 目标 QPS 是多少
- 可接受延迟是多少
- 哪条链路最关键

### 2. 明确测试环境

最好尽量接近真实部署：

- 实例规格
- 数据量级
- 缓存和数据库依赖

### 3. 明确测试数据

测试数据太少，很多 SQL 和缓存问题测不出来。

### 4. 打开监控

没有监控的性能测试，价值会大打折扣。

## 七、一个务实的性能测试流程

1. 先做基线测试
2. 逐步拉高并发
3. 观察指标拐点
4. 定位最先成为瓶颈的环节
5. 做一轮优化
6. 回归测试看是否真的提升

## 八、性能测试最常见的误区

### 1. 只压应用，不压真实依赖

### 2. 压接口时数据模型过于简单

### 3. 只看成功率，不看长尾延迟

### 4. 出现瓶颈后没有配套监控，根本定位不了

### 5. 优化后不回归复测

## 九、性能测试和压测的关系

很多团队会把它们混着说。

你可以先这样理解：

- 性能测试是大类
- 压测是其中一种更强调极限和边界的测试方式

## 十、最适合先测哪些链路

对大多数后端系统，优先测试：

1. 登录和鉴权
2. 查询列表和详情
3. 创建订单或提交表单
4. 核心异步任务入口
5. 热点读写接口

## 十一、一个现实建议

如果团队还没有完整性能测试体系，先别追求一步到位。

先做到：

1. 核心接口有基线数据
2. 发布前能做基本回归压测
3. 慢接口能定位到数据库、缓存、依赖或代码层

这已经能解决大量“上线后才发现扛不住”的问题。

## 这篇最重要的结论

性能测试的价值，不是为了产出一份漂亮报告，而是为了知道系统边界、提前发现瓶颈，并验证优化到底有没有真实收益。
