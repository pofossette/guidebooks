# 00. 微服务可观测性与治理概念速览

很多人学微服务时容易把工具看散：

- Consul 是注册中心
- Prometheus 是指标系统
- Grafana 是看板
- Loki 是日志系统
- Tempo 是追踪系统
- OpenTelemetry 是采集与标准

但真正落地时，它们解决的是同一件事：

**服务多了以后，怎样知道谁在线、谁变慢了、哪一步报错了、问题到底发生在哪一跳。**

## 一、先把 5 个问题分清

### 1. 服务在哪里

这类问题由服务注册与发现解决。

- 谁上线了
- 谁下线了
- 哪些实例健康
- 调用方应该访问哪个地址

典型组件：`Consul`、`etcd`、`Kubernetes Service`

### 2. 系统现在健不健康

这类问题通常靠指标回答。

- QPS 多大
- 错误率多少
- P95 / P99 延迟多少
- CPU、内存、队列积压怎样

典型组合：`Prometheus + Grafana`

### 3. 某次故障具体报了什么

这类问题通常靠日志回答。

- 某个请求为什么失败
- 某个 worker 为什么重试
- 某条 SQL 或下游响应长什么样

典型组件：`Loki`、`ELK`

### 4. 一个请求跨了多少服务

这类问题通常靠分布式追踪回答。

- 网关进来以后经过了哪些服务
- 哪一段最慢
- 哪个下游把整体链路拖慢了

典型组件：`Tempo`、`Jaeger`

### 5. 数据怎么统一采集

这类问题由遥测标准化解决。

如果每个服务都自己定义 trace、metrics、logs 格式，后面很难统一治理。

典型标准：`OpenTelemetry`

## 二、最常见的组合关系

可以把它们理解成下面这条链：

```text
业务服务
  ├─ 暴露 metrics -> Prometheus 抓取 -> Grafana 展示
  ├─ 输出 logs -> Agent/Collector 收集 -> Loki 检索
  ├─ 产生 traces -> OpenTelemetry SDK/Collector -> Tempo 查询
  └─ 注册服务 -> Consul -> 调用方发现实例
```

## 三、最小可用闭环

对小团队来说，第一阶段不需要上特别复杂的治理平台，先跑通这一套就够用：

1. 每个服务暴露 `/metrics`。
2. 每个服务输出结构化日志。
3. 每个服务接入 OpenTelemetry SDK。
4. Prometheus 抓指标，Grafana 看图。
5. Loki 查日志，Tempo 查 trace。
6. 服务通过 Consul 或平台 DNS 完成发现。

这样你就具备了：

- 看整体健康度的能力
- 查单次错误的能力
- 追跨服务调用链的能力
- 做基本容量规划和告警的能力

## 四、和 Kubernetes 的关系

如果你在 Kubernetes 里：

- 服务发现很多时候由 `Service + DNS` 完成
- 配置与服务治理很多时候由平台接管
- 但 Prometheus、Grafana、Loki、Tempo、OpenTelemetry 依然常见

所以不要误以为：

**上了 K8s，就不需要理解这些组件。**

K8s 只是替你做掉一部分平台层工作，不会替你回答业务问题、追踪慢调用、分析日志。

## 五、Node.js / TS 团队最务实的落地顺序

推荐顺序：

1. 先统一日志格式。
2. 再加 Prometheus 指标。
3. 再补 OpenTelemetry trace。
4. 最后按场景决定 Consul、服务网格或 K8s 原生发现。

原因很简单：

- 日志最容易立刻提升排障效率
- 指标最容易做告警
- trace 最容易建立全链路视角
- 注册发现更多取决于部署环境

## 六、面试里可以怎么开场

如果面试官让你讲微服务可观测性，可以先用一句话定框架：

> 我通常会把微服务治理拆成四个视角：服务发现解决“服务在哪里”，Prometheus 解决“系统是否健康”，Loki 解决“具体报了什么错”，Tempo + OpenTelemetry 解决“一个请求跨服务发生了什么”。

这样比上来就背工具名更有结构。
