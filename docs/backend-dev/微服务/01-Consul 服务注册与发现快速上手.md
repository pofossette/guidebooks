# 01. Consul 服务注册与发现快速上手

## 一、Consul 是干什么的

Consul 最常见的认知标签有 3 个：

- 服务注册与发现
- 健康检查
- KV 配置存储

如果只看微服务主线，先抓住前两个就够了。

它的核心价值不是“存一个服务地址”，而是：

**让调用方始终拿到当前健康的服务实例列表。**

## 二、什么场景适合先用 Consul

更适合：

- 虚拟机或物理机场景的微服务
- Docker Compose / 多节点环境，但还没上 K8s
- 想自己理解注册、健康检查、发现全链路

不一定优先：

- 已经深度运行在 Kubernetes，且主要依赖 `Service + DNS`

## 三、快速上手的最小流程

按理解顺序，Consul 快速上手只要抓 4 步：

1. 启动 Consul agent 或开发模式实例。
2. 让服务把自己注册进去。
3. 配置健康检查。
4. 让调用方按服务名查实例。

## 四、你至少要掌握的对象

### 1. Service

服务的逻辑名字，比如：

- `user-service`
- `order-service`
- `payment-service`

### 2. Instance

某个具体实例，比如：

- `10.0.1.12:3000`
- `10.0.1.13:3000`

### 3. Health Check

告诉 Consul 这个实例当前是否还能接流量。

常见方式：

- HTTP 检查
- TCP 检查
- TTL / 心跳

## 五、在 TS / Node 服务里的接入思路

典型步骤：

1. 服务启动后向 Consul 注册：
   - 服务名
   - 实例 ID
   - 地址与端口
   - 健康检查地址
2. 服务关闭前主动注销。
3. 调用方通过 Consul SDK 或 HTTP API 查健康实例。
4. 客户端或网关做负载均衡。

如果你不想引入太重的 SDK，直接通过 HTTP API 理解也够了。

## 六、落地时最重要的工程细节

### 1. 实例 ID 要唯一

不要只写服务名，否则多个实例会互相覆盖。

常见写法：

- `order-service-10.0.1.12-3000`
- `order-service-pod-7f9f8`

### 2. 健康检查不要只看进程存活

很多服务“进程还活着”，但数据库连不上、线程池打满、下游全超时，这时继续接流量反而更危险。

更务实的做法：

- `liveness` 看进程是否存活
- `readiness` 看当前是否适合接流量

### 3. 下线要优雅

实例关闭时不要直接退出：

1. 先摘注册
2. 停止接新流量
3. 等旧请求处理完
4. 再真正退出

### 4. 调用方必须有超时和重试

服务发现只解决“地址从哪来”，不解决“调用一定成功”。

所以调用方仍然要有：

- 超时
- 重试
- 熔断
- 降级

## 七、Consul vs etcd 应该怎么理解

一句话版：

- `Consul` 更像“面向服务治理的注册发现工具”
- `etcd` 更像“强一致分布式 KV / 元数据存储底座”

所以很多时候不是谁替代谁，而是定位不同。

## 八、面试回答模板

如果被问“Consul 用来做什么”，可以这样答：

> Consul 最核心的作用是服务注册发现和健康检查。服务实例启动后把自己的地址和检查方式注册进去，调用方再按服务名拿健康实例列表。这样服务地址不用写死，扩缩容和实例漂移也更容易处理。它还带 KV 能力，但在微服务场景里，我会先把它当成注册中心来理解。

如果被追问“为什么不用写死 IP”，就补：

- 实例会扩缩容
- 容器 IP 会变化
- 宕机和故障摘除需要动态感知
