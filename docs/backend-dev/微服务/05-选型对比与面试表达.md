# 05. 选型对比与面试表达

微服务这块最能拉开差距的，通常不是“你背过几个产品名”，而是：

**你能不能讲清楚为什么选它，而不是另一个。**

## 一、先给你一张面试视角表

| 选型 | 面试价值 | 展示能力 |
|---|---|---|
| Consul vs etcd | ⭐⭐⭐⭐⭐ | 对服务发现工具定位的深度理解 |
| Tempo vs Jaeger | ⭐⭐⭐⭐ | 对追踪系统的权衡思考 |
| Prometheus vs DataDog | ⭐⭐⭐⭐⭐ | 对成本和厂商锁定的考量 |
| Loki vs ELK | ⭐⭐⭐⭐ | 对运维复杂度的权衡 |
| OpenTelemetry | ⭐⭐⭐⭐⭐ | 对云原生标准的熟悉 |

## 二、Consul vs etcd

### 1. 核心定位

| 维度 | Consul | etcd |
|---|---|---|
| 典型定位 | 服务注册发现、健康检查、KV | 强一致分布式 KV、元数据存储 |
| 常见语境 | 微服务治理 | Kubernetes / 控制面底座 |
| 服务健康检查 | 强项 | 通常自己补上层逻辑 |
| 使用门槛 | 面向服务治理更直观 | 更偏基础设施组件 |

### 2. 怎么答更稳

可以这样说：

> 如果问题是“服务实例在哪里、谁健康、怎么发现”，Consul 语义更直接；如果问题是“我要一个强一致的分布式元数据存储”，etcd 更常见。两者不是简单替代关系，而是关注点不同。

### 3. 什么时候选 Consul

- 虚拟机或裸机微服务
- 希望快速落地注册发现和健康检查
- 团队不想一开始就自己补很多治理逻辑

### 4. 什么时候更偏 etcd

- 强依赖 K8s / 控制面生态
- 更关注强一致元数据存储
- 已有相关基础设施经验

## 三、Tempo vs Jaeger

### 1. 核心差异

| 维度 | Tempo | Jaeger |
|---|---|---|
| 生态结合 | Grafana 生态强 | 独立追踪体系更经典 |
| 认知普及度 | 新一些 | 更经典、更广为人知 |
| 组合方式 | 常和 Loki / Prometheus / Grafana 一起出现 | 常单独被提及或与 OTel 配合 |

### 2. 怎么答更稳

> 如果团队已经以 Grafana 为可观测性入口，Tempo 的整合体验通常更顺；如果团队已有 Jaeger 经验或希望沿用更经典的追踪系统认知，Jaeger 也完全合理。关键不是谁“绝对更高级”，而是现有生态、团队经验和集成成本。

## 四、Prometheus vs DataDog

### 1. 核心差异

| 维度 | Prometheus | DataDog |
|---|---|---|
| 交付方式 | 开源自建为主 | 商业托管平台 |
| 成本模型 | 基础设施和运维成本 | 订阅与用量成本 |
| 厂商锁定 | 低 | 相对更高 |
| 开箱即用 | 需要自己搭建 | 往往更强 |
| 灵活性 | 高 | 也高，但依赖平台能力 |

### 2. 面试高价值点

这里最能体现成熟度的，不是背功能，而是你能主动提：

- 成本
- 团队运维能力
- 数据主权
- 厂商锁定
- 合规要求

### 3. 怎么答更稳

> 如果团队希望走开源、自主可控和低锁定，Prometheus 常是默认选择；如果团队更重视托管、开箱即用、统一平台体验，并且预算充足，DataDog 会更省平台建设时间。

## 五、Loki vs ELK

### 1. 核心差异

| 维度 | Loki | ELK |
|---|---|---|
| 运维复杂度 | 相对低 | 相对高 |
| 与 Grafana 协同 | 很强 | 较弱 |
| 日志分析能力 | 足够覆盖常见场景 | 更强、更重 |
| 成本与资源占用 | 往往更轻 | 往往更重 |

### 2. 怎么答更稳

> 如果团队日志需求主要是排障检索，并且整体可观测性以 Grafana 为中心，Loki 很务实；如果需要更复杂的全文检索、分析和大规模日志平台能力，ELK 往往更强，但代价是运维复杂度更高。

## 六、为什么 OpenTelemetry 不能只当一个“工具名”

OpenTelemetry 的面试价值高，是因为它体现的是标准化思路。

你讲它时，尽量带上这 4 个点：

1. 统一埋点标准
2. 统一传输协议，常见是 OTLP
3. SDK + Collector 的分层
4. 后端可替换，降低厂商耦合

如果只说“它可以做 trace”，分数不高。

## 七、给面试官的整段回答模板

> 我会把微服务可观测性拆成三层。第一层是标准层，用 OpenTelemetry 统一指标、日志和 trace 的采集语义，避免和单一厂商强绑定。第二层是数据层，指标一般用 Prometheus，日志如果追求轻量和 Grafana 一体化会偏 Loki，追踪会偏 Tempo 或 Jaeger。第三层是治理层，服务发现如果是 VM 或非 K8s 场景我会考虑 Consul，如果是 K8s 控制面语境则更常提到 etcd。最终选型不会只看技术参数，还会看团队经验、预算、运维能力和现有基础设施。

## 八、学习建议

如果你时间有限，优先把下面 5 句话练熟：

1. Consul 偏服务治理，etcd 偏强一致元数据底座。
2. Prometheus 看趋势和告警，不替代日志。
3. Loki 查具体日志，Tempo 查完整链路。
4. OpenTelemetry 是标准，不是单一后端产品。
5. 真正的选型问题，最后一定落到成本、团队能力和生态匹配。
