# 03. 分布式锁

## 一、什么是分布式锁

分布式锁要解决的问题可以先用一句话记住：

**多个进程、多个实例、多个节点同时竞争同一份资源时，只允许一个持有者进入临界区。**

这里的关键词是“分布式”。

如果你的服务只有一个进程，那么一个进程内锁、一个 `Map`、一个内存状态位，很多时候就够了。

但只要系统开始横向扩容，本地锁就失效了。

例如：

- 订单服务部署了 4 个实例
- 用户重复点击“支付”
- 4 个请求可能被负载均衡打到不同实例
- 每个实例都以为“当前没人处理这笔订单”

这时单机锁挡不住跨实例并发。

所以分布式锁本质上是在解决：

**跨节点的互斥访问问题。**

## 二、哪些场景真的需要分布式锁

常见场景有这些：

- 防止同一订单被重复支付
- 防止同一优惠券被重复领取
- 防止定时任务在多实例下重复执行
- 防止同一库存被多个 worker 同时扣减
- 防止同一文件被多个消费者重复处理
- 防止某个聚合任务在多个节点被并发触发

但这里要先提醒一句：

**不是所有并发问题都该先想到分布式锁。**

很多业务场景更直接的方案反而是：

- 数据库唯一索引
- 乐观锁版本号
- 行锁
- 幂等 token
- 状态机约束

例如“防止重复创建订单”，很多时候唯一索引比引入 Redis 或 ZooKeeper 更靠谱。

因为唯一索引直接约束最终写入结果，而锁只是试图在前面“协调一下”。

## 三、一个靠谱的分布式锁至少要满足什么

一个能在工程里落地的分布式锁，至少要考虑下面这些能力：

| 能力 | 说明 |
|---|---|
| 互斥 | 同一时刻只能有一个持有者拿到锁 |
| 自动释放 | 持锁方挂了以后，锁不能永久不释放 |
| 归属校验 | 只能释放自己持有的锁，不能删别人的 |
| 重试/等待 | 没拿到锁时，能快速失败或按策略等待 |
| 可观测 | 能看到争抢、超时、失败、续期等情况 |

如果只满足“能加上一个 key”，那还不叫一个工程上可用的锁。

## 四、为什么很多时候优先想到 Redis

Redis 做分布式锁的原因很现实：

- 性能高
- 接入简单
- 大多数后端系统本来就已经用了 Redis
- 对“短临界区、性能优先”的场景很方便

所以在业务系统里，最常见的分布式锁方案通常是 Redis。

但“最常见”不等于“最稳妥”。

Redis 锁的核心优势是简单和快，核心问题是它很容易被误用。

## 五、Redis 分布式锁怎么做

Redis 锁最常见的基础写法是：

```text
SET lock:order:123 uniqueToken NX PX 30000
```

这条命令里有 4 个关键点：

- `lock:order:123`：锁的 key，要准确表达资源粒度
- `uniqueToken`：当前持锁方的唯一标识
- `NX`：只有 key 不存在时才设置成功
- `PX 30000`：30 秒自动过期

可以把它理解成：

“如果这把锁当前没人持有，就把它交给我，并且 30 秒后自动失效。”

### 1. 为什么不能只用 `SETNX`

很多初学者会写成两步：

1. `SETNX lockKey value`
2. `EXPIRE lockKey 30`

这有明显风险。

如果第一步成功了，第二步执行前进程崩溃，锁就没有过期时间了。

结果就是：

**这把锁可能永远不释放。**

所以加锁必须尽量一步完成，通常就是 `SET key value NX PX ttl`。

### 2. 为什么 value 不能随便写

`value` 不能写死成 `1`，也不能省略“持有者身份”。

因为释放锁时你必须判断：

**这把锁现在还是不是我的。**

如果 value 只是固定值，你无法区分：

- 是不是自己之前加的锁
- 锁是否已经过期
- 是否已经被别人重新拿走

所以通常会放一个全局唯一 token，比如：

- UUID
- 进程 ID + 线程 ID + 随机串
- 请求 ID + 随机串

## 六、Redis 锁为什么释放时不能直接 `DEL`

这是 Redis 分布式锁里最容易写错的地方之一。

错误思路：

1. 我拿到了锁
2. 业务跑完
3. 直接 `DEL lockKey`

问题在于：

1. 你拿锁时设置了 30 秒过期
2. 业务执行卡住了，实际跑了 35 秒
3. 第 30 秒锁自动过期
4. 别的客户端重新拿到了这把锁
5. 你第 35 秒恢复执行，最后 `DEL lockKey`

这时候你删掉的其实是别人的锁。

这就不是“释放锁”，而是“误删别人正在持有的锁”。

### 正确做法

释放时必须同时做两件事：

1. 先比较当前锁的 `value`
2. 只有 value 等于自己的 token，才允许删除

而且这两步必须是原子操作。

通常会用 Lua 脚本：

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
else
  return 0
end
```

这段脚本的含义很简单：

- 锁还在，而且持有者还是我
- 那我才能删
- 否则什么都不做

## 七、Redis 分布式锁的典型问题

Redis 锁常见，不代表没有坑。

实际工程里最常见的几个问题是下面这些。

### 1. 业务执行时间超过 TTL

如果你的锁 TTL 是 30 秒，但业务跑了 45 秒，就会发生：

- 锁先过期
- 别人重新拿锁
- 你和别人同时在执行临界区

这会直接破坏“互斥”的效果。

所以 Redis 锁特别依赖一个前提：

**临界区最好短、可预估、可控。**

### 2. 客户端卡顿或 GC 暂停

就算你觉得代码逻辑只要 300ms，也不代表进程一定稳定。

可能出现：

- STW GC 暂停
- 线程调度延迟
- 容器被抢占
- 网络瞬时抖动

这些都会让“我以为自己还持锁”变成错觉。

### 3. Redis 主从切换导致锁丢失

这是 Redis 锁天然比较敏感的点。

例如：

1. 客户端 A 在主节点加锁成功
2. 这条写入还没同步到从节点
3. 主节点故障
4. 从节点晋升为新主
5. 客户端 B 在新主上再次加锁成功

于是 A 和 B 都以为自己拿到了锁。

这说明 Redis 锁的“锁安全性”并不是天然绝对的。

对于“必须强协调”的场景，这一点很关键。

### 4. 锁粒度设计不合理

如果锁粒度太粗，比如：

```text
lock:order
```

那所有订单都串行化了，吞吐量会明显下降。

更合理的做法通常是针对资源实例加锁，例如：

```text
lock:order:123
lock:coupon:user:456
lock:inventory:sku:789
```

### 5. 用锁掩盖业务建模问题

这是更大的误区。

例如某个“防重复下单”场景，本来应该靠：

- 订单状态机
- 幂等请求号
- 唯一约束

结果全丢给分布式锁。

这会让系统表面上“像是做了并发控制”，但底层仍然不稳。

要记住：

**分布式锁只能降低冲突概率，不能替代最终一致性约束。**

## 八、Redis 锁的续期、可重入、等待分别在解决什么

很多人第一次看到 Redisson，会觉得它“只是一个更高级的锁库”。

其实它主要是在补 Redis 基础锁的工程能力。

### 1. 续期

如果业务时间可能超过初始 TTL，就要考虑续期。

续期的思路是：

- 锁先拿到
- 后台线程定期检查“锁还是不是我的”
- 如果还是我的，就延长过期时间

这样可以降低“业务没跑完，锁先过期”的概率。

但续期也不是无限保险。

如果进程长时间卡死，续期线程也可能一起失效。

### 2. 可重入

可重入的意思是：

同一个线程或同一个持有者，在已经拿到锁的情况下，再次进入同一把锁时不会把自己锁死。

例如：

- 方法 A 拿了锁
- A 里又调用了方法 B
- B 也尝试拿同一把锁

如果锁不支持可重入，自己就把自己卡住了。

### 3. 等待/阻塞

最基础的 Redis 锁通常是：

- 拿到就执行
- 没拿到就失败

但实际业务有时希望：

- 等一会儿再试
- 在超时时间内阻塞等待
- 减少无意义的自旋轮询

这类能力更多是客户端框架在补，不是 Redis 原生命令天然提供的。

## 九、TS/Node 风格的 Redis 锁伪代码

下面给一个表达思路的简化伪代码：

```ts
async function withLock<T>(
  key: string,
  ttlMs: number,
  task: () => Promise<T>,
): Promise<T> {
  const token = crypto.randomUUID();
  const result = await redis.set(key, token, "NX", "PX", ttlMs);

  if (result !== "OK") {
    throw new Error("resource is locked");
  }

  try {
    return await task();
  } finally {
    await releaseLockIfOwner(key, token);
  }
}
```

释放锁的逻辑应该走 Lua：

```ts
async function releaseLockIfOwner(key: string, token: string) {
  await redis.eval(
    `
      if redis.call("GET", KEYS[1]) == ARGV[1] then
        return redis.call("DEL", KEYS[1])
      else
        return 0
      end
    `,
    1,
    key,
    token,
  );
}
```

这段代码只是表达最小正确思路，不是完整生产实现。

生产环境里通常还要补：

- 超时监控
- 续期机制
- 获取失败重试策略
- 指标埋点
- 业务幂等

## 十、Redisson 解决了什么

Redisson 是 Java 生态里很常见的 Redis 客户端框架。

它不是一个新锁算法，而是把很多 Redis 锁的工程细节封装起来了。

它重点解决的是：

- 自动续期
- 可重入
- 阻塞等待
- 比较完整的锁 API

所以你可以把它理解成：

**Redis 分布式锁的工程化封装。**

它不是在改变 Redis 的本质边界，只是在帮助你更稳地使用 Redis 锁。

## 十一、Redlock 是什么，为什么有争议

Redlock 是 Redis 官方文档里提出的一种多节点锁思路。

核心做法是：

- 准备多个相互独立的 Redis 节点
- 客户端向多个节点尝试加锁
- 在多数节点加锁成功，且总耗时仍在有效期内时，认为锁成功

它想解决的问题很明确：

**单 Redis 节点故障时，锁可能不够可靠。**

但 Redlock 一直有争议。

争议点主要在于：

- 网络分区
- 时钟与超时假设
- 故障时多节点状态不一致
- 是否真的能提供足够强的锁安全性

所以对初学者来说，更重要的不是站队，而是先理解定位：

- 单 Redis 锁：简单、快、常用，但边界清楚
- Redlock：试图增强容错，但假设更复杂
- 真正强协调场景：很多时候会转向 ZooKeeper 或 etcd

## 十二、为什么还要讲 ZooKeeper 锁

如果说 Redis 锁更偏“高性能的工程互斥工具”，那 ZooKeeper 锁更偏“强协调工具”。

它们解决的问题看起来相似，但设计目标不完全一样。

ZooKeeper 常被用于：

- 分布式锁
- 主节点选举
- 配置协调
- 服务注册发现

这类场景的共同点是：

**对状态一致性和协调顺序要求更高。**

所以讨论分布式锁时，只讲 Redis 不够。

## 十三、ZooKeeper 分布式锁怎么做

ZooKeeper 做锁，经典思路不是“写一个固定节点表示谁拿到锁”，而是：

**临时顺序节点 + 监听前驱节点。**

可以按下面步骤理解。

### 1. 在约定目录下创建临时顺序节点

假设锁目录是：

```text
/locks/order-123
```

每个竞争者都会在这个目录下创建一个临时顺序节点，例如：

```text
/locks/order-123/lock-000000001
/locks/order-123/lock-000000002
/locks/order-123/lock-000000003
```

这里有两个关键词：

- **临时节点**：客户端会话断开后，节点会自动删除
- **顺序节点**：ZooKeeper 会自动追加递增序号

### 2. 判断自己是不是最小节点

创建完节点后，客户端会拿到当前目录下的所有子节点，然后排序。

如果自己是最小节点，比如：

```text
lock-000000001
```

那就表示自己拿到了锁。

### 3. 如果不是最小节点，就监听前一个节点

假设自己是：

```text
lock-000000003
```

那它不会监听整个目录，而是只监听前一个节点：

```text
lock-000000002
```

当前驱节点被删除时，自己再重新判断是不是最小节点。

如果变成最小节点，才正式获得锁。

## 十四、为什么 ZooKeeper 锁要监听前驱节点

这是 ZooKeeper 锁的一个很关键的工程细节。

如果所有等待者都监听整个锁目录，那么一旦锁释放：

- 全部等待者都会被唤醒
- 大家一起去抢锁
- 会造成明显的无效竞争

这就是典型的惊群问题。

而“只监听前一个节点”的好处是：

- 当前一个节点释放时，只唤醒它后面的那个等待者
- 唤醒链路更平滑
- 更接近一个有序排队的效果

所以 ZooKeeper 锁天然比较适合表达“排队等锁”的语义。

## 十五、ZooKeeper 锁为什么通常比 Redis 更强

这里的“更强”，主要是指协调一致性层面，而不是性能更强。

ZooKeeper 锁通常被认为更强，原因主要有这几个。

### 1. 它建立在强一致协调系统上

ZooKeeper 本质上不是一个普通缓存。

它是一个为协调而设计的分布式系统。

这意味着它从设计目标上就更偏向：

- 一致状态
- 有序更新
- 会话语义
- 监听机制

### 2. 临时节点天然适合处理客户端宕机

客户端一旦真正与 ZooKeeper 会话断开，临时节点会被删除。

这就相当于：

**锁的释放和客户端会话生命周期绑定在一起。**

这类语义通常比“依赖 TTL 猜测客户端是不是死了”更强一些。

### 3. 顺序节点天然适合排队

Redis 基础锁更像“谁抢到算谁的”。

ZooKeeper 锁更容易表达：

- 谁先来
- 谁排在前面
- 谁应该下一个获得锁

所以在需要严格协调、等待顺序、排队语义的场景下，ZooKeeper 往往更合适。

## 十六、ZooKeeper 锁也不是没有代价

不要把 ZooKeeper 理解成“比 Redis 更高级，所以总是更好”。

它的代价也很明显。

### 1. 性能通常不如 Redis

Redis 的优势是极快。

ZooKeeper 的目标不是极限低延迟缓存，而是分布式协调。

所以如果你的场景是：

- 锁竞争非常频繁
- 临界区很短
- 对延迟非常敏感

Redis 往往更有优势。

### 2. 使用复杂度更高

ZooKeeper 锁要理解：

- 会话
- 临时节点
- 顺序节点
- watch
- 前驱节点监听

实现和排查难度通常都高于 Redis 基础锁。

### 3. 不适合把所有热点都堆到它身上

ZooKeeper 更适合做“协调控制面”。

如果你把大量高频热点互斥都压给它，通常不是一个理想设计。

## 十七、Redis 和 ZooKeeper 怎么选

可以先看这个对比表。

| 维度 | Redis 锁 | ZooKeeper 锁 |
|---|---|---|
| 核心机制 | `SET NX PX` + Lua 校验删除 | 临时顺序节点 + 监听前驱节点 |
| 自动释放 | 依赖 TTL | 依赖临时节点和会话失效 |
| 等待语义 | 原生较弱，通常靠客户端封装 | 天然支持排队等待 |
| 一致性强度 | 较依赖部署和故障场景 | 通常更强 |
| 性能/延迟 | 更高、更低延迟 | 一般低于 Redis |
| 实现复杂度 | 入门简单，细节易踩坑 | 理解和实现更复杂 |
| 适用场景 | 高频、短临界区、性能优先 | 强协调、顺序等待、控制面场景 |
| 主要风险 | 超时、误删、主从切换 | 复杂度高、吞吐不如 Redis |

可以进一步记成几句判断。

### 更偏 Redis 的场景

- 临界区很短
- 性能优先
- 系统本来就已经重度使用 Redis
- 业务能接受“锁只是协调手段，不是最终兜底”

### 更偏 ZooKeeper 的场景

- 更强调一致性和协调顺序
- 需要更明确的排队等待语义
- 锁本身属于系统控制面的一部分
- 不希望过度依赖 TTL 推断客户端存活

## 十八、etcd 和数据库方案怎么看

除了 Redis 和 ZooKeeper，常见还会提到 etcd 和数据库。

### 1. etcd

etcd 和 ZooKeeper 很像，都是强一致协调系统。

它常见的锁实现基础是：

- lease
- compare-and-swap
- watch

在云原生体系里，etcd 很常见。

如果你的基础设施更偏 Kubernetes 生态，etcd 往往比 ZooKeeper 更自然。

### 2. 数据库

很多场景其实不需要“真正的分布式锁系统”，而是直接用数据库能力：

- 唯一索引
- 乐观锁版本号
- `SELECT ... FOR UPDATE`
- 状态机条件更新

例如：

- 防止重复创建订单
- 防止重复领取奖励
- 保证某状态只能从 A 迁移到 B 一次

这类问题很多时候直接用数据库约束最有效。

因为它约束的是最终结果，而不是先做一层“外部协调”。

## 十九、实战里怎么选

一个比较稳妥的优先级通常是：

1. 先问自己是不是根本不需要分布式锁
2. 能用唯一约束、幂等、状态机解决，就先不用锁
3. 需要跨实例互斥且性能优先，再考虑 Redis
4. 需要更强协调和排队语义，再考虑 ZooKeeper 或 etcd
5. 对关键业务，无论选哪种锁，都要保留业务兜底约束

这最后一点最重要。

**分布式锁不是业务正确性的唯一来源。**

真正稳的系统通常是：

- 锁做前置协调
- 幂等做重复请求兜底
- 数据库约束守住最终结果
- 失败后有补偿和重试

## 二十、面试高频问题速答

### 1. Redis 锁为什么要用 Lua 释放

因为“先 `GET` 再 `DEL`”不是原子操作。

锁可能在你 `GET` 之后过期并被别人重新拿走，所以要把“比较 value”和“删除”放进同一个 Lua 脚本里。

### 2. Redis 锁为什么要有唯一 token

因为释放锁时要判断当前锁是不是自己的。

没有唯一 token，就没法安全地避免误删别人的锁。

### 3. 锁过期了但业务没执行完怎么办

这是 Redis 锁的典型风险。

解决思路通常有：

- 缩短临界区
- 合理设置 TTL
- 加续期机制
- 用业务幂等和数据库约束兜底

### 4. ZooKeeper 锁为什么常用临时顺序节点

临时节点可以在会话失效时自动释放锁，顺序节点可以形成等待队列。

两者结合，比较适合实现可排队的分布式锁。

### 5. 为什么要监听前驱节点，而不是监听整个目录

为了避免惊群。

只监听前一个节点，可以让等待者按顺序被唤醒，而不是所有人同时冲上来抢锁。

### 6. Redis 和 ZooKeeper 锁怎么选

Redis 更偏性能优先、短临界区、工程使用广。

ZooKeeper 更偏强协调、顺序等待、控制面场景。

### 7. 分布式锁能彻底解决重复下单吗

不能。

它只能降低并发冲突概率。

真正要稳住结果，还是要靠：

- 幂等
- 唯一约束
- 状态流转约束
- 事务或补偿机制

## 二十一、这一章你最该记住什么

如果你只记 6 句话，记下面这些：

1. 本地锁解决不了多实例并发，分布式锁解决的是跨节点互斥。
2. Redis 锁最小正确姿势是：`SET NX PX` + 唯一 token + Lua 释放。
3. Redis 锁的典型风险是超时、误删和主从切换。
4. Redisson 是 Redis 锁的工程化封装，不是新的共识算法。
5. ZooKeeper 锁的核心机制是临时顺序节点 + 监听前驱节点。
6. 分布式锁不是幂等、唯一约束和事务的替代品。
