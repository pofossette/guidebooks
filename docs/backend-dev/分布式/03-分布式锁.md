# 03. 分布式锁

## 一、为什么需要分布式锁

单进程里，你可以用内存锁控制并发。但当 Node.js 服务部署多个实例后，本地锁只对当前实例有效。

例如：

- 订单服务部署了 4 个实例
- 每个实例都有自己的内存
- 用户重复点击支付
- 请求可能落到不同实例上

这时本地 `Map`、变量、进程内锁都挡不住跨实例并发。

分布式锁要解决的是：

**多个节点同时竞争同一个资源时，只允许一个节点获得操作权。**

## 二、典型场景

- 防止重复下单
- 防止优惠券重复领取
- 防止定时任务多实例重复执行
- 防止同一库存被并发扣减
- 防止同一文件被多个 worker 同时处理

## 三、分布式锁应该具备什么

一个靠谱的分布式锁通常要考虑：

| 能力 | 说明 |
|---|---|
| 互斥 | 同一时刻只能一个客户端拿到锁 |
| 过期 | 持锁方崩溃后，锁能自动释放 |
| 唯一标识 | 只能释放自己加的锁 |
| 可重试 | 没拿到锁时可以等待或失败 |
| 可观测 | 能看到锁争用、超时、失败情况 |

## 四、Redis 锁的基本思路

Redis 锁最常见的基础命令思路：

```text
SET lock:order:123 uniqueValue NX PX 30000
```

含义：

- `NX`：只有 key 不存在时才设置成功
- `PX 30000`：30 秒后自动过期
- `uniqueValue`：当前持锁方的唯一标识

释放锁时不能简单 `DEL key`，因为锁可能已经过期并被别人拿走。

正确思路是：

1. 读取锁里的值
2. 判断是不是自己的 `uniqueValue`
3. 是自己的才删除

这个判断和删除通常要用 Lua 脚本保证原子性。

## 五、Redis 锁的风险

Redis 锁不是银弹，常见问题包括：

- 业务执行时间超过锁过期时间
- Redis 主从切换导致锁丢失
- 客户端卡顿后误删别人的锁
- 锁粒度太大导致吞吐下降

所以你要记住：

**分布式锁只能降低并发冲突概率，不能替代业务幂等和数据库约束。**

## 六、Redlock

Redlock 是 Redis 官方文档中提出的一种多 Redis 节点锁算法思路。

它的核心是：

- 向多个独立 Redis 节点尝试加锁
- 在多数节点加锁成功且耗时在有效期内时，认为加锁成功

它的争议也很多，因为真实网络和时钟问题会让“锁安全性”很难绝对保证。

初学者不需要一开始陷进争论，先记住：

- 单 Redis 锁简单，但故障安全性有限
- Redlock 尝试提高可靠性，但实现和假设更复杂
- 核心业务不要只依赖锁，还要做幂等和数据约束

## 七、ZooKeeper/etcd 锁

ZooKeeper 和 etcd 也可以实现分布式锁。

它们通常依赖：

- 临时节点或租约
- 有序节点
- watch/监听机制
- 共识协议保证元数据一致

这类锁一致性通常更强，但性能和使用复杂度也更高。

## 八、数据库锁

有些场景可以直接用数据库能力：

- 唯一索引
- 行级锁
- 乐观锁版本号
- `SELECT ... FOR UPDATE`

例如防止重复创建订单时，一个唯一索引往往比引入分布式锁更直接。

## 九、TS 后端中的简单示例

下面是一个表达思路的伪代码，不是完整生产实现：

```ts
async function withLock<T>(
  key: string,
  ttlMs: number,
  task: () => Promise<T>,
): Promise<T> {
  const token = crypto.randomUUID();
  const locked = await redis.set(key, token, "PX", ttlMs, "NX");

  if (!locked) {
    throw new Error("资源正在处理中");
  }

  try {
    return await task();
  } finally {
    await releaseLockIfOwner(key, token);
  }
}
```

生产环境要补：

- Lua 脚本释放锁
- 超时监控
- 失败重试策略
- 业务幂等

## 十、实战建议

优先级通常是：

1. 能用数据库唯一约束解决，就先用数据库约束
2. 需要跨实例互斥时，再考虑 Redis/etcd/ZooKeeper 锁
3. 对关键业务，锁之外必须有幂等和补偿
4. 不要用锁掩盖数据模型设计问题
