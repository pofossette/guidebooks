# 01. 分布式基础理论

## 一、什么是分布式系统

最通俗的定义：

**分布式系统，就是多个节点通过网络协作，对外表现得像一个整体。**

这里的节点可以是：

- 一台服务器
- 一个容器实例
- 一个数据库副本
- 一个 Node.js 服务进程
- 一个 Redis/Kafka/etcd 节点

比如一个最常见的 TS 后端部署：

- Nginx 或负载均衡器接收请求
- 多个 Node.js API 实例处理业务
- Redis 做缓存和会话
- PostgreSQL 做主库和只读副本
- Worker 从消息队列消费任务

这已经是分布式系统，不需要等到“微服务”才算。

## 二、分布式不等于微服务

这两个概念要分开：

- **分布式**：强调系统部署在多台机器或多个进程上协同工作
- **微服务**：强调按业务边界把系统拆成多个服务

所以：

- 单体应用部署多个副本，也是分布式
- 微服务系统通常也是分布式
- 不要把“分布式能力”和“微服务拆分”混为一谈

对初学者来说，建议先理解多实例部署、缓存、队列、数据库主从，再讨论微服务拆分。

## 三、为什么分布式会复杂

单机系统里，你通常默认：

- 函数调用能直接返回
- 内存状态只有一份
- 数据库写入后马上能读到
- 一个定时任务只会跑一次

分布式系统里，这些默认前提都会失效：

- 网络可能超时
- 节点可能宕机
- 请求可能重复
- 消息可能重复投递
- 不同节点可能看到不同数据
- 本地内存状态不能在多实例之间共享

所以分布式的难点不是“多写几个服务”，而是：

**网络、故障、时间顺序和多副本数据会让系统行为变得不确定。**

## 四、分布式系统追求什么

分布式通常是为了获得这些能力：

| 目标 | 通俗解释 | 典型做法 |
|---|---|---|
| 高性能 | 多台机器一起处理请求 | 多实例部署、负载均衡 |
| 高可用 | 部分节点挂了，系统还能工作 | 副本、故障转移、健康检查 |
| 可扩展 | 流量变大后可以继续加机器 | 水平扩容、分片 |
| 容灾 | 某个机房或节点出问题后能恢复 | 多副本、多可用区 |

代价也很明确：

- 架构更复杂
- 运维更复杂
- 数据一致性更难
- 问题排查更困难

所以不要把分布式当成“更高级的默认选项”。单体能稳定解决的问题，先用单体。

## 五、基础术语

## 5.1 节点

节点就是分布式系统里的一个参与者。它可以提供服务、保存数据、参与选主或转发请求。

## 5.2 副本

副本是同一份数据的多个拷贝。

例如：

- 一个主库和两个从库
- 三个 etcd 节点保存同一份配置

副本提高可用性和读取能力，但会带来一致性问题。

## 5.3 分片

分片是把数据拆成多份，放到不同节点上。

例如：

- 用户 ID `1-1000000` 放到分片 A
- 用户 ID `1000001-2000000` 放到分片 B

分片解决容量和写入压力问题，但会带来跨分片查询、扩容迁移、事务处理等问题。

## 5.4 网络分区

网络分区不是“数据分片”，而是：

**节点之间因为网络故障互相联系不上。**

这时系统可能出现：

- A 节点以为 B 节点挂了
- B 节点其实还活着
- 两边都继续对外服务

CAP 理论里的 `P` 说的就是这种网络分区。

## 5.5 一致性

一致性可以先理解成：

**多个节点看到的数据是不是对得上。**

例如你把订单改成“已支付”：

- 如果所有副本立刻都能读到“已支付”，一致性很强
- 如果有些副本短时间内还是“待支付”，一致性较弱
- 如果最终都同步成“已支付”，就是最终一致

## 5.6 可用性

可用性指：

**请求来了，系统能不能给出响应。**

注意，可用性不等于“响应一定是最新数据”。一个系统可能返回旧数据，但它仍然是可用的。

## 六、CAP 理论

CAP 是分布式系统最基础的理论之一：

- **C: Consistency，一致性**
- **A: Availability，可用性**
- **P: Partition Tolerance，分区容错性**

CAP 的核心结论：

**发生网络分区时，一个分布式系统无法同时完美满足一致性和可用性。**

现实里网络分区不能完全避免，所以 `P` 通常是默认要接受的。真正的取舍是：

- 分区发生时，优先保证一致性，还是优先保证可用性

## 七、用库存例子理解 CAP

假设北京和上海两个节点都保存库存数据，现在网络断了。

这时北京节点收到“购买最后一件商品”的请求。

### 选择一致性

北京节点说：

> 我联系不上上海，不能确认是否还有库存，所以先拒绝请求。

结果：

- 不容易超卖
- 但用户暂时无法下单

这更偏 `CP`。

### 选择可用性

北京节点说：

> 我先接受请求，之后再和上海同步。

结果：

- 用户能继续下单
- 但可能北京和上海都卖出了最后一件

这更偏 `AP`。

所以 CAP 不是抽象口号，它是在问：

**网络出问题时，你宁愿系统拒绝部分请求，还是宁愿先返回但接受短暂不一致？**

## 八、BASE 理论

BASE 是很多互联网系统面对 CAP 时的工程化选择：

- **Basically Available**：基本可用
- **Soft State**：软状态
- **Eventually Consistent**：最终一致性

通俗理解：

> 不追求每一秒所有节点都绝对一致，而是允许短时间不一致，但最终要同步回来。

例如：

- 下单成功后，积分稍后到账
- 支付成功后，通知稍后发送
- 数据写入数据库后，搜索索引几秒后更新

这就是最终一致性的常见业务表现。

## 九、PACELC

CAP 主要讨论“发生网络分区时怎么办”。但现实中，即使没有网络分区，系统也要在延迟和一致性之间取舍。

PACELC 可以粗略理解成：

- 如果发生分区，取舍 `A` 和 `C`
- 否则，取舍 `L` 和 `C`

其中：

- `L` 是 Latency，延迟
- `C` 是 Consistency，一致性

例如写数据库时：

- 等所有副本都确认再返回，一致性更强，但延迟更高
- 主节点写成功就返回，延迟更低，但副本可能暂时落后

## 十、对 TS 后端的现实影响

你不一定会手写分布式算法，但一定会碰到这些现象：

- 多个 Node.js 实例之间不能共享内存
- 本地缓存只在当前实例有效
- Redis 主从切换后可能丢少量数据
- PostgreSQL 主从复制有延迟
- Elasticsearch 写入后短时间搜不到
- 消息队列可能重复投递消息

所以分布式基础理论不是只为面试服务，它直接影响你写业务代码时能不能做出正确假设。
