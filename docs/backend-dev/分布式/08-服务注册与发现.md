# 08. 服务注册与发现

## 一、为什么需要服务注册与发现

在单体系统里，调用目标通常很固定。

分布式系统里，服务实例会动态变化：

- 新实例启动
- 旧实例下线
- 实例宕机
- 扩容缩容
- 容器 IP 变化

客户端不能把所有服务地址写死。

服务注册与发现要解决的是：

**服务实例在哪里，以及当前哪些实例是可用的。**

## 二、服务注册

服务注册就是服务启动后，把自己的地址上报给注册中心。

例如订单服务启动后注册：

- 服务名：`order-service`
- 地址：`10.0.1.23:3000`
- 健康检查地址：`/health`
- 版本：`v1.2.0`

## 三、服务发现

服务发现就是调用方根据服务名找到可用实例。

例如支付服务要调用订单服务：

1. 查询 `order-service`
2. 注册中心返回多个实例地址
3. 客户端或网关选择其中一个实例调用

## 四、客户端发现和服务端发现

## 4.1 客户端发现

客户端自己查询注册中心，并自己做负载均衡。

优点：

- 少一层代理
- 调用链路更直接

缺点：

- 客户端复杂
- 每种语言都要实现发现和负载均衡逻辑

## 4.2 服务端发现

客户端请求负载均衡器或网关，由它转发到后端实例。

优点：

- 客户端简单
- 治理逻辑集中

缺点：

- 网关或负载均衡器成为关键路径
- 需要维护代理层

## 五、健康检查

注册中心不能只知道“谁注册过”，还要知道“谁现在还健康”。

健康检查通常包括：

- 心跳
- HTTP health check
- TCP check
- 租约过期

如果服务没有及时续约，注册中心会把它从可用实例列表移除。

## 六、常见组件

| 组件 | 常见用途 |
|---|---|
| Nacos | 服务发现、配置中心 |
| Eureka | Spring Cloud 生态服务发现 |
| Consul | 服务发现、健康检查、KV |
| etcd | 强一致元数据存储，Kubernetes 依赖它 |
| Kubernetes Service | K8s 内置服务发现和负载均衡入口 |

## 七、和配置中心的区别

| 组件 | 关注点 |
|---|---|
| 配置中心 | 配置值是什么 |
| 注册中心 | 服务实例在哪里 |

很多产品会同时提供两种能力，比如 Nacos 和 Consul。

## 八、TS 后端中的常见形态

在 Node.js 项目里，你可能不直接接触传统注册中心，而是通过平台能力完成：

- Docker Compose 用服务名互相访问
- Kubernetes 用 Service 和 DNS 做服务发现
- 云厂商负载均衡做实例发现
- API 网关做统一转发

但理解注册发现仍然重要，因为你要知道：

- 为什么服务地址不能写死
- 为什么健康检查很关键
- 为什么实例下线要优雅关闭
- 为什么服务调用要有超时和重试

## 九、初学者建议

学习路径：

1. 先理解服务名和实例地址的区别
2. 再理解健康检查和心跳
3. 然后学负载均衡策略
4. 最后看 Kubernetes Service、Nacos、Consul 这类具体实现
