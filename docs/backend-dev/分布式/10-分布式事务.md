# 10. 分布式事务

分布式事务解决的问题很直接：

**一笔业务跨多个服务、多个存储时，如何尽量保证状态别做乱。**

## 一、为什么会有分布式事务问题

在单体系统里，很多操作可以放进一个数据库事务：

- 写订单
- 扣库存
- 记账

但分布式系统里，这几步可能分别落在：

- 订单服务
- 库存服务
- 支付服务

这时就很难靠一个本地事务包住全流程。

## 二、为什么不能简单照搬单库事务思路

因为跨节点事务会带来：

- 网络失败
- 超时
- 部分成功
- 部分失败
- 协调成本高

所以工程上更常见的思路，不是追求绝对完美的一步原子提交，而是按业务级别选方案。

## 三、常见思路

### 1. 强一致分布式事务

理论上更严格，但成本高、复杂度高。

### 2. 最终一致性

先让主流程完成，再通过消息、重试和补偿把其他系统状态慢慢对齐。

### 3. Saga / 补偿事务

每一步本地事务成功后继续往下走，某一步失败时执行补偿动作。

## 四、为什么大多数业务更常用最终一致性

因为它更贴近现实系统：

- 复杂度更可控
- 可用性更好
- 更适合高并发业务

代价是：

- 会有短时间不一致
- 需要补偿和审计

## 五、最常见的落地组件

在 TS / Node 语境下，常见会配合：

- PostgreSQL / MySQL 本地事务
- RabbitMQ / Kafka / Redis Streams / BullMQ
- 幂等表
- 状态机
- 审计日志

## 六、学习这一块先抓什么

1. 哪些链路必须强一致
2. 哪些链路允许最终一致
3. 失败后靠什么重试和补偿
4. 如何避免重复执行副作用

## 这篇最重要的结论

分布式事务的核心，不是记住几个模式名字，而是识别跨服务状态变更的边界，然后在强一致、最终一致和补偿成本之间做取舍。
