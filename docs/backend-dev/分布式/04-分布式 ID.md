# 04. 分布式 ID

## 一、为什么需要分布式 ID

单机系统里，数据库自增 ID 很好用。

但分布式系统里会遇到问题：

- 多个服务实例同时创建数据
- 多个数据库分片都要生成 ID
- 不能依赖单一数据库自增
- 需要 ID 大致有序，方便排序和索引

分布式 ID 要解决的是：

**在多节点环境下生成全局唯一的标识。**

## 二、分布式 ID 常见要求

| 要求 | 说明 |
|---|---|
| 全局唯一 | 不同节点生成的 ID 不能冲突 |
| 高性能 | 生成 ID 不能成为瓶颈 |
| 高可用 | 某个节点挂了仍能生成 |
| 趋势递增 | 对数据库索引更友好 |
| 可解析 | 最好能看出时间、机器等信息 |

不是每个业务都要求全部满足，要按场景取舍。

## 三、UUID

UUID 的优点：

- 本地生成
- 不依赖中心服务
- 几乎不会重复

缺点：

- 字符串较长
- 通常无序
- 做数据库主键时索引局部性较差
- 不方便人工排查

适合：

- 外部公开 ID
- 请求追踪 ID
- 对排序不敏感的场景

## 四、数据库自增 ID

优点：

- 简单
- 有序
- 查询和索引友好

缺点：

- 单点依赖数据库
- 分库分表后容易冲突
- 暴露业务规模

适合：

- 单库单表或早期单体系统
- 内部主键

## 五、号段模式

号段模式的思路：

1. 中心服务或数据库一次分配一段 ID
2. 业务服务拿到号段后在本地递增使用
3. 用完后再申请下一段

例如：

- 服务 A 拿到 `1000-1999`
- 服务 B 拿到 `2000-2999`

优点：

- 性能高，本地生成
- 中心服务压力低

缺点：

- 实现比自增 ID 复杂
- 机器宕机可能浪费一段 ID
- 需要处理号段预取和切换

## 六、Snowflake

Snowflake 是很经典的分布式 ID 方案。

一个 ID 通常由几部分组成：

- 时间戳
- 机器 ID
- 序列号

通俗理解：

> 用时间区分大范围顺序，用机器 ID 区分节点，用序列号处理同一毫秒内的并发。

优点：

- 本地生成
- 性能高
- 趋势递增
- 可以解析出时间信息

缺点：

- 依赖机器时钟
- 机器 ID 分配要管理好
- 时钟回拨会带来风险

## 七、为什么时钟回拨危险

Snowflake 依赖时间戳。如果机器时间突然往回跳，可能出现：

- 新生成 ID 的时间部分小于之前
- 同一机器同一时间片序列号重复
- ID 冲突风险增加

常见处理方式：

- 检测到回拨后短暂等待
- 回拨超过阈值直接拒绝生成
- 引入备用 workerId 或逻辑时钟

## 八、TS 后端怎么选

| 场景 | 推荐 |
|---|---|
| 请求追踪 ID | UUID/ULID |
| 外部公开资源 ID | UUID/ULID/NanoID |
| 数据库内部主键 | 自增 ID、Snowflake、号段 |
| 分库分表主键 | Snowflake、号段 |
| 需要按时间排序 | Snowflake、ULID |

## 九、初学者建议

早期项目不要过度设计 ID 系统：

- 单库项目用数据库自增 ID 完全可以
- 需要公开 ID 时可以额外加 UUID 字段
- 进入分库分表或多写节点后，再考虑 Snowflake/号段

最重要的是明确：

**ID 方案不是越复杂越好，而是要匹配你的数据规模、部署形态和查询模式。**
