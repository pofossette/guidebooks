# 05. 配置中心

## 一、什么是配置中心

配置中心是集中管理应用配置的系统。

它解决的问题是：

**多个服务、多个环境、多个实例的配置如何统一管理、动态下发和审计。**

常见配置包括：

- 数据库连接地址
- Redis 地址
- 第三方 API endpoint
- feature flag
- 限流阈值
- 日志级别
- 灰度策略

## 二、为什么不能只靠 `.env`

`.env` 适合本地开发和小项目，但系统变大后会有问题：

- 多环境配置难管理
- 多实例更新麻烦
- 配置修改缺少审计
- 敏感配置容易泄漏
- 运行中无法动态更新

配置中心不是替代所有环境变量，而是管理更复杂、更动态的配置。

## 三、配置中心通常提供什么能力

| 能力 | 说明 |
|---|---|
| 集中管理 | 所有服务配置统一查看和修改 |
| 环境隔离 | dev/test/staging/prod 使用不同配置 |
| 动态刷新 | 配置修改后服务可以感知 |
| 权限控制 | 只有授权人员能改生产配置 |
| 版本记录 | 能回滚和审计 |
| 灰度发布 | 只让部分实例使用新配置 |

## 四、配置和密钥要区分

配置中心经常管理普通配置，但密钥要更谨慎。

例如：

- 普通配置：分页大小、限流阈值、开关
- 敏感密钥：数据库密码、JWT 私钥、支付密钥

密钥更适合放在专门的 Secret Manager 或 KMS 系统里，至少要保证：

- 加密存储
- 访问审计
- 权限最小化
- 支持轮换

## 五、常见产品

| 产品 | 常见定位 |
|---|---|
| Apollo | 配置管理、灰度、审计 |
| Nacos | 配置中心和服务发现 |
| Consul | 服务发现、KV 配置 |
| etcd | 强一致 KV，常用于基础设施元数据 |
| Kubernetes ConfigMap/Secret | K8s 环境里的配置和密钥 |

## 六、TS 后端中的使用方式

一个常见封装方式：

```ts
type AppConfig = {
  redisUrl: string;
  enableNewCheckout: boolean;
  paymentTimeoutMs: number;
};

interface ConfigClient {
  getConfig(): Promise<AppConfig>;
  watch(onChange: (config: AppConfig) => void): void;
}
```

业务代码不应该到处直接读远程配置中心，而是通过统一的配置模块：

- 启动时加载配置
- 校验配置格式
- 提供类型安全访问
- 处理默认值和回滚

## 七、动态配置的风险

动态配置看起来方便，但风险很大：

- 改错配置可能立刻影响线上
- 多实例刷新时间不同，造成行为不一致
- 配置格式错误可能导致服务异常
- 业务代码如果没有兜底，会直接炸

所以动态配置必须配合：

- schema 校验
- 灰度发布
- 回滚机制
- 变更审计
- 监控告警

## 八、配置中心和 CAP

配置中心通常更偏一致性。

原因是：

- 配置错了可能影响整个系统
- 多实例读到不同关键配置会造成混乱
- 基础设施元数据通常不能随便不一致

例如 etcd 这类系统会通过 Raft 保证强一致元数据。

## 九、初学者建议

早期 TS 项目可以先这样做：

1. 本地用 `.env`
2. 生产环境用平台环境变量或 Secret 管理
3. 配置读取集中封装到 `config` 模块
4. 用 Zod 这类库校验配置
5. 系统变复杂后再引入配置中心

不要让业务代码到处直接读 `process.env`。这会让配置校验、测试和迁移都变困难。
