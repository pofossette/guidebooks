# 09. 消息队列与最终一致性

## 一、消息队列解决什么问题

消息队列用于在系统之间异步传递消息。

它最常解决这些问题：

- 削峰填谷
- 异步处理
- 服务解耦
- 重试补偿
- 最终一致性

例如下单后不一定要同步完成所有事情：

- 创建订单
- 扣库存
- 发通知
- 加积分
- 更新推荐画像

其中很多步骤可以通过消息异步处理。

## 二、同步调用和异步消息

同步调用：

```text
订单服务 -> 积分服务 -> 返回结果
```

优点：

- 流程直观
- 调用方立刻知道结果

缺点：

- 被调用方慢会拖慢主流程
- 被调用方挂了会影响下单

异步消息：

```text
订单服务 -> 消息队列 -> 积分服务消费
```

优点：

- 主流程更快返回
- 服务解耦
- 消费失败可以重试

缺点：

- 状态短时间不一致
- 排查链路更复杂
- 需要处理重复消费

## 三、最终一致性

最终一致性的意思是：

**系统允许短时间内状态不完全一致，但经过重试、补偿和同步后，最终达到一致。**

例如：

1. 用户下单成功
2. 订单状态立即变成已创建
3. 积分消息稍后消费
4. 几秒后积分到账

这期间订单和积分系统短暂不一致，但最终会对齐。

## 四、消息队列的核心概念

| 概念 | 解释 |
|---|---|
| Producer | 生产者，发送消息 |
| Consumer | 消费者，处理消息 |
| Topic/Queue | 消息存放的逻辑通道 |
| Ack | 消费者确认消息已处理 |
| Retry | 处理失败后重试 |
| Dead Letter | 多次失败后进入死信队列 |

## 五、常见语义

消息系统经常讨论投递语义：

| 语义 | 含义 |
|---|---|
| At most once | 最多一次，可能丢消息 |
| At least once | 至少一次，可能重复 |
| Exactly once | 精确一次，成本和限制很高 |

业务系统里最常见的是 **至少一次**。

这意味着：

**消费者必须能处理重复消息。**

## 六、幂等

幂等是分布式业务里非常重要的概念。

通俗理解：

**同一个操作执行一次和执行多次，最终结果一样。**

例如发放积分：

- 消息 ID 是 `msg_123`
- 消费前先检查 `msg_123` 是否处理过
- 处理过就直接跳过
- 没处理过才发积分并记录处理日志

常见幂等手段：

- 唯一索引
- 幂等表
- 状态机校验
- 去重 key
- 乐观锁版本号

## 七、本地消息表

本地消息表是解决“数据库写入”和“消息发送”一致性的常见方案。

下单时在同一个数据库事务里：

1. 写订单表
2. 写消息表

事务提交后，后台任务扫描消息表并投递到 MQ。

这样可以避免：

- 订单写成功了，但消息发送失败

后续通过重试把消息发出去，实现最终一致。

## 八、事务消息

一些消息队列提供事务消息能力。

大致思路是：

1. 先发送半消息
2. 执行业务本地事务
3. 根据本地事务结果提交或回滚消息
4. 如果状态不明，MQ 回查本地事务状态

它也是在解决本地事务和消息投递之间的一致性问题。

## 九、常见消息队列

| 产品 | 常见特点 |
|---|---|
| RabbitMQ | 传统消息队列，路由能力强 |
| Kafka | 高吞吐日志流，适合事件流和大数据管道 |
| RocketMQ | 事务消息、延迟消息等能力较强 |
| Redis Streams | Redis 生态里的轻量流式消息 |

## 十、TS 后端实践建议

写消费者时，至少要考虑：

- 消息会重复
- 消息可能乱序
- 消费可能失败
- 下游服务可能超时
- 消息堆积需要监控

一个消费者的基本结构通常是：

```ts
async function handleOrderPaid(event: OrderPaidEvent) {
  if (await processedMessageRepo.exists(event.messageId)) {
    return;
  }

  await database.transaction(async (tx) => {
    await pointsService.addPoints(tx, event.userId, event.points);
    await processedMessageRepo.markProcessed(tx, event.messageId);
  });
}
```

核心不是这段代码本身，而是背后的原则：

- 消费逻辑要幂等
- 状态变更和去重记录最好在同一事务里
- 失败后允许重试

## 十一、初学者建议

不要一开始就把所有流程都异步化。

更稳的顺序：

1. 先写清楚同步业务流程
2. 找出慢操作和非核心操作
3. 把通知、积分、日志、索引同步等改成异步
4. 补幂等、重试、死信和监控

消息队列的价值不是“显得架构复杂”，而是让系统在流量和故障下更稳。
