在 TypeScript (TS) 环境下开发 AI Agent 时，工具描述（Tool Description / Function Calling Schema）的编写本质上是**针对工具的 Prompt Engineering**。大模型无法“看懂”你的代码逻辑，它完全依赖你提供的文本描述来决定**何时调用**、**不该何时调用**以及**如何提取参数**。

为了让大模型准确无误地调用工具，你需要从**命名、功能描述、参数定义**三个维度进行精细化设计。以下是编写高质量工具描述的最佳实践与具体方法：

### 1. 工具命名规范 (Name)
名字是模型匹配工具的第一道关卡。命名应当清晰、无歧义，且符合动作直觉。
*   **最佳格式**：`动词_名词` 或 `动词_宾语`（蛇形命名法 `snake_case` 最受各大模型原生支持）。
*   **✅ 推荐**：`get_current_weather`, `search_company_knowledge_base`, `create_jira_ticket`
*   **❌ 避免**：`tool_1`, `weather`, `do_search`（过于宽泛或缺乏动词）

### 2. 工具描述的核心结构 (Description)
一个能让模型“秒懂”的 `description` 应当包含以下 4 个核心要素：

*   **功能简述 (What)**：一句话说明这个工具是干什么的。
*   **触发场景 (When to use)**：明确告诉模型在遇到什么样的问题时调用它（可以举例说明）。
*   **使用禁忌 (When NOT to use)**：如果有容易混淆的工具，或者该工具不支持某些查询，必须明确指出其边界。
*   **行为指引 (How to process)**：如果需要模型在拿到结果后做特定处理，可以在这里声明。

**优秀的描述模板**：
> "获取[XXX]信息。当用户询问[A]、[B]时调用此工具。注意：该工具不支持查询[C]，如果用户查询[C]请引导用户使用[另外的方法/工具]。返回的数据为[JSON/文本格式]，请在获取后提炼核心重点回答用户。"

### 3. 参数描述的深度刻画 (Parameters)
很多开发者只写工具层面的 description，却忽略了**参数层面的 description**。模型在提取参数时极其容易产生幻觉（比如瞎编格式），因此必须对每个参数进行强约束。

*   **为每一个参数写 description**：不仅要定义类型（String/Number），还要说明参数的语义、格式要求甚至示例（e.g., `"日期，必须是 YYYY-MM-DD 格式，如 2026-05-14"`）。
*   **善用枚举 (Enum)**：如果参数值是固定的几个选项，强烈建议使用 Enum，彻底杜绝模型瞎编参数值。
*   **明确必填项 (Required)**：通过类型系统明确标记哪些是必需的，哪些是可选的。

### 4. TS Agent 开发代码示例 (结合 Zod)
在目前的 TS Agent 开发生态中（如 Vercel AI SDK、LangChain.js 或原生 OpenAI Node.js SDK），使用 `Zod` 来定义参数 Schema 是最主流且最稳健的做法。

```typescript
import { z } from "zod";

// 定义一个查询天气的工具
export const weatherTool = {
  name: "get_current_weather",
  
  // 核心：精心编写的整体 Description
  description: 
    "获取指定城市的当前实时天气情况。" +
    "当用户询问“今天天气如何”、“外面冷吗”或特定地点的当前气温时调用此工具。" +
    "【注意】：1. 仅支持查询实时天气，绝不能用于查询历史天气或未来预报；" +
    "2. 如果用户没有提供具体城市，请先反问用户所在城市，不要自行编造。",

  // 核心：利用 Zod 为每个参数编写带有深度约束的 Schema
  parameters: z.object({
    location: z
      .string()
      .describe(
        "需要查询天气的具体城市名称。必须包含省份或国家信息以防重名。" +
        "例如：'中国, 广东省, 深圳市' 或 'San Francisco, CA'。"
      ),
    unit: z
      .enum(["celsius", "fahrenheit"]) // 善用 Enum 限制模型的发挥
      .optional()
      .describe(
        "温度单位。如果是中国城市请默认传入 'celsius'，美国城市传入 'fahrenheit'。"
      ),
    include_details: z
      .boolean()
      .default(false)
      .describe("是否需要返回湿度、风速等详细信息。除非用户特别要求，否则传 false。")
  }),

  // 工具的实际执行逻辑
  execute: async (args: { location: string; unit?: string; include_details?: boolean }) => {
    // args 将会被强类型推导，并且大模型传递过来的参数会严格符合上述描述
    console.log(`Searching weather for ${args.location}...`);
    // return await fetchWeatherApi(args);
    return { temperature: 28, condition: "Sunny" }; 
  },
};
```

### 5. 进阶调优技巧 (Agent 踩坑经验)

1.  **防止工具冲突 (Namespace/Overlap Avoidance)**：
    如果你有两个相似的工具（例如 `search_internal_db` 和 `search_google`），模型很容易调错。
    **解法**：在两个工具的 description 中进行**互斥声明**。
    *在 google 搜索的描述中写*：“仅用于查询公开新闻和常识。如果要查询公司内部员工或规章制度，请使用 `search_internal_db` 工具。”
2.  **让模型“思考”后再提取参数 (Chain of Thought 提示)**：
    对于非常复杂的参数（比如需要大模型写一段 SQL 或者复杂的 JSON），如果模型直接输出很容易错。可以在参数里加一个“废弃的思考字段”。
    ```typescript
    parameters: z.object({
      _reasoning: z.string().describe("在提取后面的具体参数前，先在这里简述你的分析逻辑。"),
      complex_data: z.string().describe("复杂的业务字段...")
    })
    ```
    *（这种做法迫使模型先输出 `_reasoning` 文本，利用其自回归特性提高后续参数生成的准确率。）*
3.  **处理大模型“编造参数”的兜底逻辑**：
    即便你写得很清楚，大模型偶尔还是会传错格式。建议在你的 `execute` 函数里做一层拦截，如果发现外部 API 报错，**不要直接崩溃，而是把报错信息作为字符串返回给模型**（例如返回：`{"error": "城市名称不合法，请使用拼音重试"}`），聪明的 Agent 大模型会自动根据错误信息**自我纠错并重新调用工具**。
