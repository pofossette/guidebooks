# 选题与写作提示

这里暂存尚未并入正式栏目的写作提示、任务提示词模板和待整理想法。下面两组模板优先服务于 AI coding agent 工作流：一组用于在 `plan mode` 里产出完整大计划，一组用于新项目初始化时生成 `README.md` 与 `AGENTS.md`。

归档 plan.md ,将新计划写入，注意要包含用于追踪进度的复选框和对应的文档、测试更新要求。plan作为一个目录性质的索引，包含总体要求和目标等，相对路径指向docs/todos 下的对
  应细则计划。目的是实现更优雅和易于管理的两种后端构建目标。另外客户端增加一个配置项，用于区分轻重后端

## 用于出 Plan 的 Plan 提示词

### 适用场景

- 需要 agent 进入 `plan mode` 先做一版完整大计划
- 计划产物不只是一个 `plan.md`，还包括一个目录文件和一组详细内容文件
- 希望计划天然可执行、可审计、可继续由后续 agent 直接消费

### 使用前最好补充的输入

- 项目目标和边界
- 当前仓库状态与已知约束
- 希望输出到哪些文件
- 是否已有旧 `plan.md` 需要归档
- 技术栈、测试命令、文档入口、关键模块入口

### 模板

```text
先阅读与任务相关的 `README.md`、`AGENTS.md`、`docs/`、现有 `plan.md` 和关键代码，再产出一版可直接执行的大计划。

要求：
1. 先检查是否有旧的活跃 `plan.md`；如果有，按仓库约定归档，并在新计划里写清归档位置。
2. 输出至少包括：
   - `plan.md` 作为总控执行计划，阐明背景，如果篇幅过长拆分并指向相关的子计划
   - 一个计划目录索引文件
   - 一组按主题或阶段拆分的详细计划文件
3. `plan.md` 必须使用复选框跟踪进度。
4. 每个阶段必须写清：目标、范围、主要修改文件、完成标准、文档更新、测试 / eval 更新、必要示例。
5. 计划里要区分：当前事实、要做的变更、明确不做的 non-goals。
6. 如果仓库已有 `docs/plans`、`docs/archived/archived-plans`、`docs/superpowers/plans` 等约定，直接沿用，并在索引里写清边界。
7. 基于真实仓库结构写，不要写成脱离上下文的通用模板；信息不足时显式标注 assumption / open questions。

直接把结果写入目标文件，不要只在对话里给摘要。完成后简短汇报新增了哪些计划文件、旧计划归档位置，以及后续执行 agent 应先读哪个文件。
```

### 可追加的一段约束

```text
这份计划将被后续 agent 直接执行，因此请把每个阶段写到“拿来就能做”的粒度。凡是会影响 README、AGENTS.md、架构文档、测试、eval、目录结构、脚本命令的改动，都必须在对应阶段明确登记，不能只写代码任务。
```

## 项目初始化提示词

### 适用场景

- 新建仓库后需要快速补齐项目说明
- 需要先把 `README.md`、`AGENTS.md` 作为项目入口建立起来
- 希望初始化结果适合人类开发者和 AI agent 共用

### 目标

- 产出一个能让首次进入仓库的人快速理解项目的 `README.md`
- 产出一个能让 AI agent 和贡献者快速进入正确阅读路径的 `AGENTS.md`
- 两个文件分工清晰，不重复堆砌内容

### 模板

```text
你现在要做的是“项目初始化文档搭建”，重点完成 `README.md` 和 `AGENTS.md`。其中 `AGENTS.md` 要被设计成一个稳定入口文件：先写基本原则，再指向开发细则和项目文档；不要把所有规范直接塞进 `AGENTS.md`。

先阅读当前仓库的目录结构、已有代码、配置文件、包管理文件、脚本命令和已有文档。基于真实仓库内容完成初始化，不要凭空编造不存在的能力。

本次初始化的核心原则：
1. `README.md` 面向首次进入项目的人，回答“这是什么、为什么存在、怎么跑、仓库怎么组织”
2. `AGENTS.md` 面向 AI agent 和贡献者，回答“开始工作前先读什么、有哪些基本原则、按任务类型去哪里”
3. `README.md` 和 `AGENTS.md` 只保留各自最该承载的内容，避免复制粘贴同一套说明
4. 长说明优先放在 `docs/` 下，`README.md` 和 `AGENTS.md` 主要做入口与导航
5. 初始化时要同时建立清晰的目录结构约束，避免根目录堆积临时文档和重复入口

请完成以下工作：

一、生成或重写 `README.md`
要求至少包含：
1. 项目一句话定位
2. 项目解决的问题 / 为什么存在
3. 核心能力或主要特性
4. 快速开始
5. 环境要求
6. 安装与运行命令
7. 常用命令
8. 配置方式或最小配置示例
9. 仓库结构概览
10. 开发与测试命令
11. 文档入口或后续阅读路径

写 `README.md` 时注意：
1. 不要把尚未实现的目标状态写成已完成事实
2. 命令、目录、技术栈都尽量基于仓库现状
3. 如果项目还在早期，可明确区分“当前已实现”和“规划方向”
4. 让一个陌生开发者看完后能成功完成第一次运行

二、生成或重写 `AGENTS.md`
要求至少包含：
1. 文件作用说明
2. 项目速写
3. 基本原则
4. 推荐阅读顺序
5. 按任务类型的补充阅读路径
6. 关键代码入口
7. 常用命令
8. 变更纪律
9. 文档同步要求

写 `AGENTS.md` 时注意：
1. 参考 Trap-Map 的组织方式：入口文件短、稳定、可导航，不承载完整细则
2. 开头先写“基本原则”，例如：
   - DDD / 分层架构开发前先读哪些文档
   - 出计划时必须包含必要的复选框，用于跟踪阶段进度和完成状态
   - 每轮开发完成时，必须同步更新对应文档和测试代码，不能只改实现
   - 改契约前先读哪些文件
   - 改高风险边界前先读哪些约束文档
3. 再给“推荐阅读顺序”和“按任务跳转”
4. 要告诉 agent 改某类内容时必须同步哪些文档
5. 如果仓库里有架构文档、设计文档、测试文档、运行手册，要把入口链路组织清楚
6. 如果有高风险边界，例如状态机、审批链路、数据库 schema、prompt 规范、权限模型，要明确提醒先读哪里

三、补齐目录结构要求
要求至少明确：
1. 根目录允许长期存在哪些说明文件，例如 `README.md`、`AGENTS.md`、`plan.md`
2. 长文档默认进入 `docs/`，并为 `docs/README.md` 或等价索引预留入口
3. 当前执行计划、参考计划、归档计划分别放在哪里
4. 临时草稿、历史方案、运行手册、架构文档、开发指南分别应该落在哪些目录
5. 是否需要在初始化阶段直接创建最小目录，例如：
   - `docs/`
   - `docs/guides/`
   - `docs/architecture/` 或等价架构文档位置
   - `docs/operations/`
   - `docs/plans/`
   - `docs/archived/` 或等价归档目录

写目录结构要求时注意：
1. 要结合当前仓库规模，避免一开始就过度设计
2. 但必须先明确“哪些内容不应该继续堆在根目录”
3. 如果已经存在目录约定，要沿用并写清边界
4. 如果计划使用目录结构守护文档，也要在初始化结果里给出入口

`AGENTS.md` 推荐结构参考：
1. 标题 + 文件作用说明
2. 基本情况
3. 基本原则
4. 推荐阅读顺序
5. 按任务跳转
6. 常用命令
7. 变更前检查 / 变更纪律
8. 文档结构或目录守护入口（如果有）

四、处理两份文件之间的分工
请显式保证：
1. `README.md` 负责项目对外总览和上手
2. `AGENTS.md` 负责开发/agent 工作流入口
3. 不要让 `AGENTS.md` 复制一整份 `README.md`
4. 不要让 `README.md` 承担过多仅对 agent 有意义的流程细节

五、如果仓库信息不足
1. 可以基于现有结构做最小合理推断
2. 对不确定内容要保守表述
3. 不要编造不存在的命令、模块或特性
4. 必要时用“当前仓库可见”“现阶段已落地”“计划中”这类措辞区分事实与目标

最终交付要求：
1. 直接写入或更新 `README.md` 与 `AGENTS.md`
2. 若新增了 `docs/README.md`、目录结构说明或其他文档入口，也一并写入
3. 输出简短总结：
   - `README.md` 强化了什么
   - `AGENTS.md` 的基本原则和导航结构是什么
   - 目录结构规则如何划分
   - 还缺哪些后续文档值得补
```

### 更严格的版本

```text
请把 `README.md` 和 `AGENTS.md` 当成“项目初始化的第一层协议”，要求它们在今天就能支撑新贡献者和 AI agent 正常进入仓库，而不是只写成占位文案。任何一句关于功能、命令、目录、架构的描述，都必须能在当前仓库里找到依据，或明确标注为规划中。
```

## 补充想法

### 选型分析提示

详细分析项目的技术选项。对于项目中每一个包或关键依赖，给出合理的选择理由，包括为什么不选择同类型的其他包、当前方案的优势、代价和未来替换成本。

### 旧计划归档与新计划生成提示

归档旧的 `plan.md`，使用 `writing-plans` 将新计划写入 `plan.md`。新 plan 要求：

- 用复选框跟踪任务进度
- 写清每个阶段的完成标准
- 写清每个阶段要做的文档更新
- 写清每个阶段要做的测试 / eval 更新
- 提供必要的示例结构或代码
